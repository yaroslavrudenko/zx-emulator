# The recipe for every cartridge on the shelf. Read by `tools/forge.sh`; see that file's header
# for what a cartridge is and why this table exists.
#
# ## The target is the MENU, not the game
#
# A cartridge comes up on **the game's own options screen** — the one where the player picks the
# control scheme (KEYBOARD / KEMPSTON / CURSOR / INTERFACE II / SINCLAIR) and the mode (one
# player, two players, define keys) — and it stops there. Not in play.
#
# That is not a preference, it is the difference between a cartridge and a save game. A shelf that
# opens mid-level has already chosen the control scheme for the player — whichever one this
# table's key script happened to select — and has skipped the screen a person wants when they plug
# something in. So each recipe below presses exactly what is needed to *reach* the menu, and not
# the key that would leave it: *Cybernoid* stops before `1 START GAME`, *R-Type* stops on the
# trainer menu rather than pressing `3`, *Bomb Jack* stops before `K` picks the keyboard.
#
# ## Why a `|`-delimited table and not TOML or JSON
#
# Because `tools/forge.sh` is `/bin/sh` and this is the only format it can read without inventing
# a parser. `while IFS='|' read -r ...` is one line of shell and has no failure mode; a TOML file
# would need something to read it, that something would be a dependency this repository does not
# have, and a hand-rolled shell TOML reader is a parser written to avoid writing a parser.
#
# The delimiter is `|` and not whitespace because **the source names contain spaces, brackets and
# parentheses** — `Batty (1987)(Hit-Pak)[t].tap`, `Head Over Heels .tap` with the trailing space
# its owner gave it — and a whitespace-split table would silently mangle over half of these rows.
# Leading and trailing spaces around a field are stripped so the columns can be lined up to be
# read.
#
# `#` starts a comment, blank lines are ignored, and one game is one line.
#
# ## The columns
#
#   slug        the file names: `<slug>.z80` is the cartridge, `<slug>.png` the cover
#   title       what a picker would print. Kept short — the contact sheet draws it on the tile
#   source      the game file, relative to the directory `forge.sh` is pointed at. A `repo:`
#               prefix names a file in this repository instead; one row needs it, and says why
#   model       48 or 128. It is the count of ROMs, and for a `.z80` it must match the file
#   keys        `--keys`: typed at the ROM, before PLAY. `LOAD` is the `LOAD ""` script
#   settle      `--settle`: frames after the last key, and the gap either side of `keys-after`
#   hold        `--hold`: frames each key is held
#   keys-after  `--keys-after`: typed once the drive has stopped. Empty for none
#   verdict     menu | title | blocked — WHAT THE CARTRIDGE OPENS ON, decided by opening it
#   menu        what that screen offers: the control schemes and the mode options. A picker
#               prints it, and it is the evidence the cartridge reached its target
#   cover-keys  the `--keys-after` script for the SECOND run, the one that makes the picture.
#               It replaces the cartridge's after-keys rather than extending them, so a row
#               whose best picture is its loading artwork writes nothing here and lets
#               `cover-settle` stop the run mid-cassette
#   cover-settle  the `--settle` for that second run
#   cover-shows what is in the picture, written by somebody who opened it
#   note        anything else worth knowing, and for a gap, what stopped it
#
# ## The cover is a picture of the game, and that is a gate rather than a preference
#
# A cover is a frame of the game being played, or the game's own drawn artwork — the commissioned
# loading screen it paints while it loads, or a title screen that is a picture. **A menu is not a
# cover.** Neither is a poke list, a plain text screen, loading stripes, a blank screen or a
# publisher's logo: nobody recognises a game from a list of choices, and a cover nobody recognises
# does not do the one job a cover has.
#
# The test is one question asked while looking at the PNG: *would a person who has never seen this
# game recognise it from this picture?* If the answer is no the row is not finished, and the
# remedy is to get further in — more starting keys, a longer settle, the other dump.
#
# ## A source can be a member of an archive
#
# `zip:ARCHIVE.zip!MEMBER` unpacks that member into a scratch directory and loads it from there.
# The owner's folder is only ever read. The member is named rather than guessed because several
# archives carry a `SCRSHOT/*.SCR`, an `INFO/*.TXT` and a `POKES/*.POK` beside the tape, and one
# holds both sides of *Freddy Hardest* — picking by extension would have to choose between them.
# `repo:` names a file in this repository instead, which one row needs and explains.
#
# `--play-tape` is not a column. It is not a choice: a tape needs PLAY and a snapshot is already
# running, so `forge.sh` derives it from the source's extension using the same rule the emulator
# uses to decide what the file is. A column would only be a way to get it wrong.
#
# ## Wait for the tape; do not guess how long it is
#
# `--keys-after` **asks the cassette**: it runs frames until the pulse train is spent, prints *"the
# tape ran out at frame N"*, and only then types. That number is a reading of the file in the drive
# and it is what `forge.sh` records as `tape_frames`. Every row that types after its load therefore
# carries a small `--settle` — 600, 800, 2000 — that is only the gap either side of the keys.
#
# **Eight rows type nothing after their load, because their menu comes up on its own**, and those
# carry a `--settle` past the end of the cassette instead. Those numbers are readings too, taken
# from a run of the same row that did print one: *Bomb Jack* ends at 14,061 and its menu is up at
# 15,000; *Rex* side 1 ends at 31,728 and its menu is up at 32,100. Where a screen cycles — *Bomb
# Jack* alternates its menu with a high-score table, *Cybernoid* with a hall of fame — the number
# was swept until the menu was the frame, which is the loop `docs/images/README.md` publishes.
#
# ## Two things that were measured here rather than assumed
#
# **A game's menu drops taps that arrive too close together.** `--hold 30` gives 30 frames held and
# 30 released, and *Head Over Heels* answers roughly one tap in three at that spacing. That is why
# a script that needs a key to land repeats it rather than trusting one tap.
#
# **`--hold` has an upper edge on a 48K and none on a 128.** Past 35 frames the 48K editor types
# every tap in the script a second time, so `LOAD ""` never parses — reproduced by accident at
# `--hold 100`, which put `LOAD LOAD LOAD LOAD…` on the screen and loaded nothing. A 128 booted to
# its own menu never reaches that editor, so the `r-type` row could hold a key 200 frames if it
# needed to. It no longer needs to: under the menu target it stops at the trainer screen.
#
# ## The three gaps, and what is behind each
#
# `batty` reaches its menu from a snapshot rather than from its cassette, and the row says so. The
# forge gets a long way — `--pause-tape-at` holds the head still while the crack draws over the
# game's own header, and the game then loads and puts its trainer's `Poke?` prompt on its own
# loading screen — and then stops: **every key tried at that prompt abandons the load** and drops
# the machine back to the editor with `Program: !Speccy` on the screen. Six keys were tried at the
# frame where the prompt is live, and all six did it.
#
# `r-type-tap` and `r-type-tap-cz` are stopped by their own dumps rather than by this tool. Both
# hold their levels in alternating 20-byte and ~13,000-byte blocks — a custom loader's own format,
# not the ROM's — and `.tap` stores bytes with no timing, so a loader that reads at its own speed
# has nothing to read. `r-type` itself is on the shelf, from the `.tzx`, which is the dump that
# works.
#
