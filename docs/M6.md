# M6 — snapshots and tape

Design for `crates/spectrum`. `MACHINE.md`'s milestone table **said** *"`.z80`/`.sna` snapshots,
`.tap` tape — gate: a real game runs"* when this document was written. **It no longer does**: the
row now reads **T1 + T2 + T3**, corrected in the M6 merge on the argument Decision 8 makes below,
and *"a real game runs"* is named there as T4. The old wording is kept in this sentence because the
whole document is written against it — Decision 4 and Decision 8 exist to argue it down, and a
design document whose premise is silently edited to match its conclusion has stopped being evidence
of anything.

Each decision below carries the class of evidence behind the claim that forced it, using the four
names the README already defines — **proven**, **measured**, **derived**, **observed** — plus
**ruling** for a choice that no evidence forces and that is recorded so it is not re-litigated. A
ruling is not evidence, and where one is doing load-bearing work this document says what would
replace it.

> **Every byte-level format detail below is a pointer, not a specification.** Offsets, page
> numbers, flag-bit positions and the T-state encoding are named here because the *design* turns on
> them — on which fields exist, which are irregular, and which are unrepresentable — and they are
> written from familiarity with the formats rather than from the formats. The implementer
> transcribes each one from the format description, which is the same act the hand-transcribed
> vectors of Decision 7 require anyway. A number in this document that disagrees with the format
> description is a defect in this document.

## The two things that make M6 different from M5

**M6 has an oracle, and M5 did not.** Not for the machine — for the *files*. `MACHINE.md` opens
with *"there is no oracle here"*, and for contention and timing that is still exactly true.

> 2026-09-01, before this milestone merged.** It is corrected here rather than quietly narrowed,
> because the sentence's whole job is to say what M6 has that M5 lacked, and it now overstates the
> gap in M5's favour.
>
> `crates/spectrum/tests/timing_oracle.rs` grades the 48K contention model against Richard Butler's
> timing test suite: **70 rows measured on real Spectrums, 0 disagreements.** Sixteen mutations
> bound it, each verified to have landed before its verdict was trusted, and
> `FIRST_CONTENDED_T_STATE` at 14333, 14334, 14336 and 14337 all go red while **only 14335 is
> green**. So contention is no longer graded by observation, and the machine layer has one external
> oracle that is not a file format.
>
> **State the scope, because the obvious reading is too strong.** What is established is that **the
> first contended T-state falls exactly 14335 T-states after `/INT`**, given that this machine
> asserts `/INT` at frame T-state 0. Three mutations came back *green*, and each marks something the
> corpus cannot settle: the frame's **origin** is a convention (moving `/INT` and the window together
> passes), the interrupt window's **length** is unmeasured (32 → 24 passes), and the `64 × 224`
> **factorisation** is not measured — its *product* is, so any compensating pair landing on 14335
> passes identically. All three are rows in `STATUS.md`'s register.
>
> **The paragraph's actual argument survives untouched**, which is why only the clause is corrected.
> A snapshot format is still an interoperation contract with dozens of independent implementations,

> reading of a **specification**, not the machine's behaviour. What changes is only that "M5 had no
> oracle at all" is no longer the contrast being drawn. *Timing* is still the right word in one
> narrow place the oracle does not reach: nothing here grades the tape's pulse timings against
> hardware, only against the ROM — see *What is still ungraded*, at the end of this document.
>
> The same superseded claim also stood in `README.md`, `ARCHITECTURE.md` and
> `crates/spectrum/src/lib.rs`'s coverage table. The first two are corrected; the third is another
> agent's file and is named here rather than left to be rediscovered.

Resuming the original paragraph: but a
snapshot format is an interoperation contract with dozens of independent implementations: a `.z80`
we write either loads in somebody else's emulator or it does not, and a `.z80` they wrote either
loads here or it does not. That is a real external check on our *reading of the format*, and it is
the one place in the machine layer where an independent implementation exists to be checked
against. M6 should use it deliberately rather than stumble into it.

**M6's stated gate grades the wrong thing, if the tape is built the obvious way.** "A real game
runs" is `MACHINE.md`'s verification item 5 — *known-demanding software*, explicitly labelled
observation. Built one way it is observation of the machine. Built the other way it is observation
of a shortcut that bypasses the machine entirely. Decision 4 is that fork, and it is the largest
decision in this document.

## Decision 1 — modules in `crates/spectrum`, not a new crate — **ruling**, with one measurable consequence

`ARCHITECTURE.md`'s crate table already answers half of this in its own text:

```
crates/spectrum/    the machine: paged memory, ULA, contention, keyboard, tape, AY.
```

The tape is named as part of this crate, and the reason holds: a tape is a peripheral that reads
the frame clock and drives a bus line. It cannot be anywhere else without exporting the clock.

The snapshot half is the real question, because a parser genuinely needs no machine. The argument
that settles it is not taste and not layering — it is the **public API delta**, which is the cost
this project treats as permanent.

A snapshot applier needs to do three things the machine does not currently expose:

| It must | Today |
|---|---|
| set the border without performing an `OUT` | only `Ula::out_port`, which charges an I/O machine cycle |
| set the frame position | `Clock::advance` is `pub(crate)`, and `Ula::clock()` returns a `Copy` **by value** |
| write RAM banks | `Memory::write` — sufficient at M6, see below |

A separate crate would have to reach those through `spectrum`'s **public** surface, so all three
become public items, permanently, for one in-workspace caller. As modules inside `spectrum` they
are `pub(crate)` and the public surface grows by **zero** items on `Ula`, `Memory` and `Clock`.
That is the whole argument, and it is checkable rather than aesthetic.

The purity that a crate boundary is usually bought for is achieved by the *signature* instead, and
this workspace already has the pattern: `crates/testsupport` splits `absence_verdict` (a pure
function of its inputs) from `skip_absent_corpus` (the shell that reads the environment), and its
own documentation says why — *"every rule has a failing case that costs microseconds on every
`cargo test`"*. M6 takes the same shape:

- **Pure:** `parse(&[u8]) -> Result<Snapshot, Error>` and `write(&Snapshot) -> Vec<u8>`. No
  filesystem, no machine, no clock. Exhaustively testable, fuzzable, and unchanged under WASM at
  M8 because they never touch `std::fs`.
- **Shell:** `Spectrum::restore` / `Spectrum::snapshot`, which are the only code that touches a
  machine.

Nothing here reads a file. `Spectrum::new(&rom)` already takes bytes rather than a path, and every
new entry point matches it.

**Layout:**

```
crates/spectrum/src/snapshot/mod.rs   Snapshot, Error, Spectrum::restore / ::snapshot
crates/spectrum/src/snapshot/reader.rs  the cursor every parser consumes through (Decision 6)
crates/spectrum/src/snapshot/z80.rs   .z80 v1/v2/v3 read, v3 write
crates/spectrum/src/snapshot/sna.rs   .sna read
crates/spectrum/src/tape/mod.rs       Tape: the pulse train and its playback
crates/spectrum/src/tape/tap.rs       .tap -> pulse train
```

**Rejected: a `crates/snapshot` crate.** It inverts the cost calculus above, and the boundary it
would draw has no analogue to the one that justifies `z80` / `spectrum` — *"the CPU does not own
memory"* is a statement about ownership on the hot path. A snapshot is not a layer of the machine;
it is the machine's own state written down.

**Rejected: a cargo feature.** A feature flag is a second build configuration that nothing tests,
and `cargo test` would only ever exercise one of them.

## Decision 2 — the canonical representation is the machine's state, not a file format — **ruling**

`.z80` v3 is the richest format, and making it the internal representation is tempting for exactly
that reason. It is wrong: every quirk then leaks inward — the "byte 12 = 255 means version 1"
compatibility hack, the `PC = 0` sentinel that marks v2+, the hardware-mode byte, the three-way
split of the T-state counter. The machine would end up storing a file.

So there is one native type, and the two formats are two lossy encodings of it:

```rust
/// Everything a snapshot restores, in the machine's own terms.
pub struct Snapshot {
    /// The CPU, exactly as `Cpu::state()` reports it.
    pub cpu: CpuState,
    /// The colour last written to the border.
    pub border: Colour,
    /// T-states into the frame. Values at or above `T_STATES_PER_FRAME` roll over when
    /// applied, as the clock does everywhere else.
    pub frame_t_state: u32,
    banks: [Option<Box<[u8; PAGE_SIZE]>>; BANK_COUNT],
}
```

Three design points, each with a reason:

**The memory image is keyed by bank, not by address.** This is `ARCHITECTURE.md` Decision 5
applied where it happens to also be the *cheaper* choice today, not only the future-proof one.
`.z80` v2/v3 stores pages by number, and the 48K's three page numbers are **neither contiguous nor
derivable from the 128's rule**: a 128 file numbers page *N* as RAM bank *N − 3*, and a 48K file
uses pages 4, 5 and 8 for `0x8000`, `0xC000` and `0x4000` — which in this crate's bank numbering
are banks 2, 0 and 5. Only the last of those satisfies *N − 3*. So the mapping is a three-entry
table with an exception in it, and an address-keyed `Snapshot` forces that table to exist twice —
once in the parser and once in the writer — with nothing tying them together and a known-irregular
rule to get wrong in both. Bank-keyed, it is one table in one place. That is an SSOT argument in
the present tense; that M7 needs it anyway is a bonus, not the reason.

**That irregularity is also the reason the table is transcribed rather than computed.** It is
exactly the shape that invites a formula — `page = bank + 3` is right for the 128 and right for one
of the 48K's three entries — and a formula that is right two thirds of the time passes any test
built from itself.

**Public fields where there is no invariant, following `CpuState`'s own precedent** — *"Every
combination of these values is a state a real Z80 can be in, so the fields are public and carry no
invariants to protect."* The same test passes here for three of the four: `CpuState` is already
such a type, `Colour::new` wraps into range, and an out-of-range `frame_t_state` is absorbed by
`Clock::advance`'s documented rollover. The banks are private because *which* bank indices are
meaningful is a property of the model, and the parser is where that is decided (Decision 6).

**`Debug` is written, not derived** — `Memory` already had to solve this, for the same reason:
*"a derived `Debug` prints 160 KB of page contents, which makes every failing assertion involving
a machine unreadable."* `Snapshot`'s `Debug` prints the CPU state, the border, the frame position,
and a per-bank checksum, so an `assert_eq!` failure names *which bank* diverged instead of
emitting 96 KB of hex. The gate then reports the first differing address itself.

### What `restore` does, and what it must not do

`restore` sets state. It steps nothing, ticks nothing, and charges no contention:

1. `cpu.set_state(snapshot.cpu)` — which already clears `ei_pending`, and already documents why
   (*"it belongs to an instruction that is no longer running"*).
2. `ula.set_border(snapshot.border)` — **not** `out_port`. Routing a restore through the bus would
   charge a four-T-state I/O cycle that never happened and, worse, would leave `Ula`'s
   `covered_t_states` armed at 4, so the first four ticks of the *next* instruction would be
   charged as an open cycle and skip their contention. That is a concrete defect, not a
   preference, and it is why this setter is unavoidable.
3. `ula.set_frame_t_state(snapshot.frame_t_state)` — the frame **counter** is left alone.
   `frames()` is the machine's uptime since power-on: the boot gate asserts on it and the FLASH
   phase derives from it, and rewinding it on a load would make one number mean two things. **This
   is a convention** — no format carries a frame count — and its cost is stated under *What
   nothing covers*.
4. RAM, bank by bank, through `Memory::write` at the addresses the **slot map** puts each bank at.

Point 4 is the one to look at twice, because it decides whether `Memory` grows public API.

**It does not, at M6.** The three banks a 48K snapshot carries — 5, 2 and 0 — are exactly the three
the 48K slot map exposes, at `0x4000`, `0x8000` and `0xC000`. Reaching them through `Memory::slots()`
(which is already public) rather than through hard-coded addresses means the code is derived from
the slot map rather than from the 48K's particular one. `Memory::bank` / `bank_mut` become
**unavoidable at M7**, where a 128 snapshot carries banks that are not paged in and therefore have
no address at all — and adding them now would be one semver commitment made without a caller.

The seam that could hide a bug here is a bank present in the snapshot and absent from the slot map,
which would be silently dropped. It cannot happen at M6 because the parser rejects any page the
model does not have, and that is **asserted rather than reasoned**: a test compares the parser's
bank set against the set the slot map exposes and fails if they ever diverge.

## Decision 3 — `.z80` is read and written; `.sna` is read only — **ruling**

`.sna` has no `PC` field. The program counter lives **on the guest's stack**, at the address `SP`
points to, and a `.sna` writer must therefore *push it*, destroying two bytes of the machine's RAM
to record the machine's state. A save that modifies what it is saving is not a save, and nothing
in M6's gate needs one.

Reading `.sna` is straightforward and stays, because the milestone names the format and because
plenty of software is only distributed that way. Three consequences follow from the format and are
recorded here so they are not rediscovered as bugs:

| `.sna` property | Consequence |
|---|---|
| `PC` popped from the RAM image at `SP`, then `SP += 2` | the parser reads it out of its **own** bank image, so it needs no machine |
| `SP` below `0x4000`, or `0xFFFF` (the second byte wraps into ROM) | the bytes are not in the image at all — a parse **error**, not a guess |
| only `IFF2` is stored | `iff1 = iff2` is a **convention**, wrong only for a snapshot taken inside an NMI handler, which no `.sna` writer produces |
| no T-state counter | `frame_t_state = 0`, which is the top of the frame — the interrupt window. See *What nothing covers* |

The two stale stack bytes are left in place after `PC` is popped, which is what every other
implementation does; the snapshot's RAM genuinely contained them.

**The `.z80` writer emits v3, with compressed pages.** Two reasons, and neither is file size:

- **v3 is the only version that carries the frame position.** v1 has no T-state field, and the
  additional header a v2 file declares (23 bytes, covering offsets 32–54) stops one byte short of
  it. Writing v1 or v2 would make `frame_t_state` unrecoverable through our own writer, so the
  state round trip in Decision 7 could not see it.
- **Compression gives the decompressor a symmetric partner to test against.** Without a
  compressor, `decompress` can only be graded by hand-built vectors. With one,
  `decompress(compress(page)) == page` is a property test over arbitrary pages, which is the
  strongest cheap instrument available for a codec. Its blind spot — a compressor and decompressor
  that agree on a *wrong* encoding — is the subject of Decision 7 and is closed the same way
  everything else in that decision is.

## Decision 4 — the tape is a signal, not a ROM trap — **ruling, forced by what the gate would then grade**

This is the architectural fork the milestone turns on.

**The trap.** Watch for `PC` reaching the ROM's `LD-BYTES` entry at `0x0556`, take the next block
from the tape, write it straight into the buffer `IX`/`DE` describe, set the flags the routine
would have set, and return. Perhaps fifty lines. It works today.

**The signal.** Model the `EAR` input — bit 6 of a read from port `0xFE` — as a real level that
changes on a schedule of T-states, and let the ROM's own edge-counting loop read it.

The trap is rejected, on four grounds in descending order of importance.

**1. It makes M6's gate grade the trap.** The trap bypasses the ULA, the contention model, the
frame clock, the interrupt window and the port decoding — every part of the machine M5 could not
grade. "A real game runs" would then mean "the injection works and the ROM's post-load code runs",
which says nothing about the machine. `STATUS.md` records **three gates that nothing ran** — the
M3 `zexdoc` job, the CI workflow that could not be pushed, and the M5 boot gate as an `examples/`
binary — under *A gate that nothing runs, for the third time*, and `MACHINE.md` calls the third
*"the worst form so far"*. Choosing the trap would be the fourth, **with the reason known in
advance**, which is a different and worse category than the first three.

> **Two corrections, and the second is the interesting one.** This said *"three occasions where
> this project shipped **evidence that graded less than it appeared to**"* and attributed *"the
> worst form so far"* to `STATUS.md`. Checked against both files on 2026-09-01: `STATUS.md`
> contains the word *worst* **nowhere** — the phrase is `MACHINE.md:141 the worst form so far`'s
> — and the three it counts are gates that *nothing ran*, which is narrower than *evidence that
> graded less than it appeared to*. The broader family is recorded in `STATUS.md` many times
> over and **counted nowhere**, so the count was right and the noun it was attached to was too
> wide.
>
> **A phrase quoted from the wrong document is the same defect as a figure quoted from one.** It
> looks checkable, it survives casual reading, and the one thing it prevents is anybody going to
> look. Three further copies of this exact misattribution were found and are listed at the end of
> [`M8.md`](M8.md); two are in files this document does not own.

**2. It does not cover the software it is for.** The trap works only for programs that call the
ROM routine. Most commercial games use their own loader, precisely to be faster and harder to
copy, and those loaders read `0xFE` directly. So the trap is not a cheaper version of the job; it
is a different job, after which the real one is still undone.

**3. The signal path is what the rest of the machine needs anyway.** `ula.rs` already names the
`EAR` bit as *"the tape port M6 brings"*, and names the issue-2/issue-3 detection that depends on
it. There is nothing to build twice.

**4. It is not expensive.** A pulse train, an advance hooked to the same place the clock advances,
and one bit in `in_port`. The `.tap` → pulse-train conversion is a fixed set of published
timings — pilot, sync, and two bit lengths. It is smaller than the contention model already
shipped.

**The risk of choosing the signal, stated plainly:** if it does not work, there is no fallback and
the milestone stalls. The mitigation is that the signal path is gradeable **below** the level of a
game, and corpus-free — see Decision 8. That mitigation is what makes this decision affordable;
without it the trap would be the pragmatic choice and the milestone's claim would have to be
weakened to match.

**A trap is not forbidden forever.** As a debugging convenience — "skip this loader, I am testing
something else" — it is legitimate. If it ever lands, two rules apply: it is **off by default**,
and the tape gates **assert that it is off**. Otherwise a gate silently starts passing through the
shortcut, which is this failure class exactly.

The related hazard is auto-start: sniffing `PC` to begin playback when the ROM starts listening.
That is a real convenience and it is a trap in disguise if it is allowed to grow. Rule: if it is
added, it may **start playback and nothing else** — never supply data — and the distinction is
stated at the site. At M6 playback is started explicitly and nothing sniffs `PC`.

## Decision 5 — the tape's internal form is a pulse train; `.tap` is a converter into it — **derived**

The obvious internal representation of a `.tap` is its own structure: a list of blocks. That is
wrong for the same reason storing a `.z80` was wrong in Decision 2, and here the consequence is
concrete rather than stylistic.

**`.tap` cannot represent a custom loader's tape at all.** It is block data with the ROM's standard
timings implied; nothing in it can say "this loader uses 700-T-state bits". `.tzx` exists for
exactly that, and it is what most commercial games are actually distributed as. A block-list
internal form would make `.tzx` a rewrite of the tape subsystem; a pulse-train internal form makes
it a second converter, with the ULA side untouched.

```rust
pub struct Tape {
    /// Lengths in T-states of successive half-periods of the EAR signal.
    pulses: Vec<u32>,
    index: usize,
    remaining: u32,
    level: bool,
    playing: bool,
}
```

Materialising every pulse costs about 16 `u32`s per data byte plus the pilot tone, so a 48 KB tape
is under a million entries — a few megabytes (**derived**, not measured; it is also irrelevant,
since `ARCHITECTURE.md` makes performance a non-goal and this is not on any hot path). A lazy
generator would save that and cost a state machine; the flat vector is simple enough to assert
exactly — a one-byte block's pulse train can be written out in a test — and that is worth more.

**The tape advances wherever the clock advances.** Contention means the clock does not advance one
T-state at a time, so the tape cannot be driven from `tick` alone. `Ula` gains one private
`fn advance(&mut self, t: u32)` that moves the clock *and* the tape, and the three existing
`self.clock.advance(..)` call sites — in `contend`, `begin_port_cycle` and `tick` — route through
it. One place, so the two clocks cannot drift.

Two deliberate non-events:

- `Ula::set_frame_t_state` (Decision 2) does **not** advance the tape. Restoring a snapshot is not
  elapsed time.
- `Ula::reset` does **not** rewind the tape. Pressing reset does not rewind a cassette.

**With no tape inserted, bit 6 reads low, exactly as it does today.** `UNDRIVEN_INPUT_BITS` is
already `0xA0` — bits 7 and 5 — so bit 6 is already clear and the constant does not change. The
assertion that M5's behaviour is untouched already exists and is external to `ula.rs`:
`tests/common/mod.rs` pins `IDLE_HALF_ROW = 0xBF` as *"the literal a real `IN A,(0xFE)` returns"*,
and `keyboard_matrix.rs` checks it across the full membrane. If inserting no tape ever changes bit
6, that gate goes red.

**The sampling point is an approximation and its size is known.** `Ula::in_port` runs after the
cycle's contention stall is charged and before its four nominal T-states arrive as ticks, so the
level is sampled up to four T-states early relative to where real hardware latches it. The ROM's
loader distinguishes a 855-T-state half-bit from a 1710-T-state one, so four T-states is far inside
its tolerance. A turbo loader with tighter margins is where it could matter, and a turbo loader
failing is what would decide it. One now exists — `crates/spectrum/tests/tzx_turbo_load.rs` runs a
loader of our own against half-periods as short as 220 T-states — and it has not failed for this
reason at any rate tried: every limit it met was traced to a constant inside its own Z80 code. That
is the absence of a distinguishing failure rather than a measurement, so the approximation stands
where it stood; what has changed is that the condition named here has been attempted instead of
merely proposed.

## Decision 6 — the parser consumes; it never indexes — **ruling, with a structural argument**

This crate builds with `panic = "abort"` in release, so a panic is not a recoverable error — it
kills the process, and `catch_unwind` is not available as a backstop. A snapshot parser reads
attacker-controlled lengths, counts and page numbers. So the requirement is not "do not panic on
the inputs we tested"; it is **remove the constructs that can panic**.

With `unsafe_code = "forbid"` there are exactly three panic sources in safe Rust that a hostile
file can reach: slice indexing, arithmetic overflow, and explicit `panic!`/`unwrap`/`expect`. Each
is closed by construction rather than by care:

| Source | How it is made unreachable |
|---|---|
| slice indexing | **there is no indexing.** One private `Reader<'a>` cursor; `u8()`, `u16_le()` and `take(n)` each return `Result`, and the single slice operation in the module is inside `Reader::take`, written once with `split_at_checked`. Nothing else in `snapshot/` touches a `[..]` |
| arithmetic overflow | every quantity derived from the file is widened (`usize::from(u16)`, `usize::from(u8)`) or combined with `checked_add`. **`overflow-checks = true` in every profile makes an overflow an abort, not a wrap** — and this project has already shipped exactly that defect once, the `u8` T-state accumulator a 63-byte prefix run overflowed |
| unbounded allocation | **no allocation is ever sized from the file.** Decompression fills a fixed `[u8; PAGE_SIZE]` through a write cursor; a write past the end is `PageOverrun`, not a `Vec` growing to whatever the file asked for |
| non-termination | every loop iteration consumes at least one input byte, so progress is structural. A run-length count of zero emits nothing and still consumes its four bytes |
| `unwrap` / `expect` | none in `snapshot/` or `tape/`. This is the one item on the list that a grep enforces rather than a type, and it belongs in the milestone's review checklist |

**How this is proven rather than asserted**, since the project's own doctrine is that prose
claiming a protection is a hypothesis and not a guarantee:

- **An exhaustive truncation sweep.** For a valid file of length *N*, `parse(&file[..k])` for
  **every** `k` in `0..N` must return `Err`, never panic, never `Ok`. This is cheap only if *N* is
  small, so the fixture is built to be small: a snapshot whose banks are uniform compresses to a
  few dozen bytes per page, giving a whole file of a few hundred bytes. Exhaustive over the axis
  that matters, deterministic, and it runs on every `cargo test`.
- **A `proptest` over arbitrary `Vec<u8>`** and over byte-level mutations of a valid file,
  asserting only that `parse` returns. `proptest` is already a dev-dependency of `spectrum`.
- **`cargo fuzz` is the right long-run instrument and is not the gate**, because it needs nightly
  and a corpus that grows outside the repository. The two above are the committed substitute, and
  saying which is which matters more than having both.

### The `.z80` compression scheme, and every hostile case in it

The scheme is one escape: `ED ED <count> <byte>` means `<byte>` repeated `<count>` times. A lone
`ED` is literal. v1 encodes the whole 48 KB image as one block terminated by `00 ED ED 00`; v2 and
v3 encode each 16 KB page separately, with a two-byte length prefix, and the length `0xFFFF` means
"16384 bytes, uncompressed" rather than a length.

> **CORRECTION — this description is missing two of the four rules, and one of them decides
> whether the files we write are readable anywhere else.** Every sentence above is true; the
> paragraph is nonetheless not a specification of the encoder, and building one from it produces
> files that round-trip perfectly here and are misread by every other emulator. The format
> description's own four rules, quoted:
>
> 1. *"it replaces repetitions of at least five equal bytes by a four-byte code `ED ED xx yy` …
>    Only sequences of length at least 5 are coded."* — **the minimum run length is absent above.**
> 2. *"The exception is sequences consisting of ED's; if they are encountered, even two ED's are
>    encoded into `ED ED 02 ED`."*
> 3. *"Finally, every byte directly following a single ED is not taken into a block, for example
>    `ED 6*00` is not encoded into `ED ED ED 06 00` but into `ED 00 ED ED 05 00`."*
> 4. The `00 ED ED 00` end marker, v1 only — which the paragraph does have.
>
> **Rule 3 is the dangerous omission.** Without it an encoder emits a literal `ED` immediately
> followed by an `ED ED` escape, and any decoder reading that stream takes the *next two bytes* as
> a count and a value. Note what class of defect this is: it is **not** one a round trip hides,
> because our own decoder misreads it too — so `decompress(compress(page)) == page` does catch it,
> **but only on a page that actually contains an `ED` before a run**, which uniform random bytes
> essentially never produce. The named adversarial pages this document already asks for are what
> make it certain, and the spec's own example is asserted byte for byte.
>
> Also implied and not stated: `xx` is one byte, so a run longer than 255 is emitted as
> consecutive escapes.

| Input | Verdict |
|---|---|
| `count` large enough to overrun the page | `PageOverrun`. The destination is fixed-size, so this is a cursor bound and not a length check |
| `count == 0` | legal; emits nothing, consumes four bytes, loop still progresses |
| `ED ED` with fewer than two bytes after it | `Truncated` |
| v1 block with no `00 ED ED 00` terminator | `Truncated` |
| decompressed output shorter than the page | `PageUnderrun` — **strict**, deliberately. Zero-filling would produce a wrong machine that every round trip then agrees is right. What would change this ruling: an observed real-world file that is legitimately short |
| declared page length longer than the remaining input | `Truncated` |
| page length `0xFFFF` | 16384 raw bytes. Must not be read as a 65535-byte length |
| duplicate page number | `DuplicatePage` — the alternative is a silent last-write-wins |
| page number the model does not have | `UnknownPage`. This is the parse-don't-validate boundary: a `Snapshot` that reaches `restore` cannot name a bank the machine lacks |
| hardware mode byte that is not a 48K | `UnsupportedHardware { mode }` |
| v1, uncompressed, with trailing bytes after the 49152 | error — **strict**, same ruling and same escape hatch as the underrun |

### The error type

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, thiserror::Error)]
#[non_exhaustive]
pub enum Error { /* Truncated, UnsupportedVersion, UnsupportedHardware, ... */ }
```

`Copy`, allocation-free, `#[non_exhaustive]` — matching `StepError`, `RomSizeError` and
`InvalidInterruptMode`, the three error types this workspace already has. `thiserror` is already a
dependency of `spectrum`. Every variant names the byte or offset that failed, because a parse
error a user cannot act on is a stack trace with better formatting.

Two error types, not one: `snapshot::Error` and `tape::Error`. A malformed tape is not a malformed
snapshot, and the siblings here are all small and specific rather than one crate-wide enum.

## Decision 7 — the round trip is three round trips, and each one alone is a lie — **derived; this corrects `MACHINE.md`**

`MACHINE.md` ranks this third in its verification plan:

> **A snapshot round trip.** Load a `.z80`, run zero frames, save, compare. Byte-identical or the
> state model is wrong. Cheap, deterministic, and independent of timing.

It is the strongest instrument M6 has and the ranking is right. **The sentence, as written, is not
achievable, and believing it is would corrupt the design.** Two reasons:

- **A foreign file carries bits the machine does not model.** `.z80` v1's byte 12 packs the border
  into bits 1–3 and the high bit of `R` into bit 0 — and also a flag for hardware this machine does
  not have, and bits with no defined meaning. Our writer emits zero there. Byte-identity over a
  foreign file would therefore force `Snapshot` to carry bits that are not machine state, which is
  precisely what Decision 2 exists to prevent. (`R` split across two bytes is worth noticing for a
  second reason: it is the archetype of a field a symmetric bug hides, since a parser that forgets
  bit 12.0 and a writer that never sets it round-trip perfectly and lose the top bit of `R`.)
- **A foreign file is in a foreign encoding.** A v1 compressed file re-serialised as v3 compressed
  is a different byte string for the same machine, and that is correct behaviour.

So byte-identity holds only over files in our own canonical encoding — which makes it a check of
the codec against *itself*. Decomposed honestly, there are three round trips and they grade three
different things:

| | Round trip | Grades | Blind to |
|---|---|---|---|
| **R1** | `snapshot(restore(s)) == s` for a `Snapshot` built in code | the applier: every field reaching the machine and coming back | fields no format carries; a field the machine drops symmetrically |
| **R2** | `parse(write(s)) == s` over arbitrary `Snapshot`s | the codec: header offsets, page framing, compression | a header offset that `parse` and `write` get **equally** wrong |
| **R3** | `write(parse(f)) == f` for `f` in canonical form | that R1 and R2 compose | everything R2 is blind to, plus foreign encodings |

**R1 is the strongest and the cheapest, and it needs no format at all.** It is `Snapshot` →
`restore` → `snapshot()` → compare. It runs on a bare clone with no corpus and no file, and it is
the test that catches `restore` forgetting a field.

### What no round trip can see, and what does see it

Every one of the three compares a value against a value that came from the same code. A symmetric
error survives all three:

- a field **permuted** with another of the same width — `parse` swaps `de` and `hl`, `write` swaps
  them back
- a field read from the **wrong offset** by both sides
- a field **dropped in both directions** — `parse` leaves it at its default and `write` always
  emits that default. **The round trip is then green because both sides agreed to lose it.**

That last one is not hypothetical here. It is the M4 defect, verbatim, in a different file:
`STATUS.md` records the FUSE harness defaulting `q` to zero, and the finding that *"zero is the one
value that makes a positive false claim"*. A snapshot loader is the same shape — a state-restoring
harness with a field nothing else looks at.

Only two things break the symmetry, and both are required:

**1. One hand-transcribed vector per format and version.** A small file written out as a
`const [u8; N]` in the source, **byte by byte, each with a comment naming its offset and its
meaning from the format description**, and its expected `Snapshot` written out separately, field by
field. Neither is derived from the other. This is the `MEMBRANE` pattern from
`tests/common/mod.rs`, and that table's own documentation records what it was worth: under a review
that permuted the keyboard map, *"38 of the 40 keys moved and the suite stayed at 72 passed with a
green boot gate"*. A derived expectation gets the wrong answer right in both places at once.

**2. The fixture's fields must be pairwise distinct and none of them zero** — otherwise a
permutation is invisible even to a hand-written expectation, and a dropped field looks like a
correct default. **The test asserts this about its own fixture**, so the fixture cannot quietly
decay into one that cannot separate anything.

### The one field with the highest risk, named

The `.z80` v3 T-state counter is **not** a plain frame position. It is reported to be split across
a low word and a high byte, where the high byte selects which third of the frame and the low word
counts *down* within it. That means the conversion is a small non-linear function with an inverse,
and it is the single field where a confident-sounding formula is most dangerous.

- It must be **one function with its inverse beside it**, and graded exhaustively over all 69888
  frame positions. That is cheap and genuinely exhaustive: one input, one output, no other axis —
  which is worth saying explicitly, because `STATUS.md` records the opposite case, where an
  exhaustive sweep on one axis was *narrower* than the sample it replaced on another.
- **The exhaustive test cannot tell you the formula is right.** It grades the pair against each
  other. If both halves encode the same wrong scheme it is green and every `.z80` we write is
  unreadable elsewhere.
- What settles it: the hand-transcribed vector's own T-state field, and the external oracle below.

**Do not take the shape above as verified.** It is the strongest single hazard in this design and
the implementer must read it out of the format description rather than out of this paragraph.

> **CORRECTION — the shape above is wrong, and the instruction attached to it is what caught
> it.** The paragraph says the high byte *"selects which third of the frame"*. It is **quarters,
> modulo 4**, and there is a second irregularity the paragraph does not mention at all. From the
> format description, quoted:
>
> > *"The hi T state counter counts up modulo 4. Just after the ULA generates its
> > once-in-every-20-ms interrupt, it is 3, and is increased by one every 5 emulated milliseconds.
> > In these 1/200s intervals, the low T state counter counts down from 17471 to 0 (17726 in 128K
> > modes), which make a total of 69888 (70908) T states per frame."*
>
> So a frame is **four** quarters — of **17472** T-states on a 48K and **17727** on a 128, because
> the counter runs down to zero inclusive and `(17471 + 1) × 4 = 69888` while
> `(17726 + 1) × 4 = 70908`; the low word counts down within the quarter, exactly as the paragraph
> says; and the high byte is the quarter's index **shifted by three**, because it reads 3 at the top
> of the frame rather than 0. Writing it as thirds would have produced 23296-T-state quarters that
> do not tile the 48K frame, and a high byte off by one position in a four-cycle rotation — a file
> that looks plausible and loads into the wrong 5 ms of the frame everywhere else.
>
> **Every figure in that sentence is a pair, and taking the first of each is its own defect.** The
> format describes two machines in one breath — `17471`/`17726`, `69888`/`70908` — and a reader who
> wants only the 48K's number can have it by stopping at the opening bracket. That is not a
> hypothetical here: `snapshot/z80.rs` divided both machines' frames by 17472 for exactly that
> reason, and because our own reader divided by the same wrong quarter, every round trip in this
> milestone stayed green while every 128 file we wrote landed 255, 510, 765 or 1020 T-states away
> for anyone else. This document describes the 128 too — Decision 2's bank-keyed `Snapshot` exists
> for it — so a figure written here without its partner is an invitation to the arithmetic that
> `quarter_t_states(model)` now replaces. Both halves, every time, or neither.
>
> **What settled it, since the exhaustive self-round-trip provably cannot.** Three things, and all
> three agree:
>
> 1. **Six positions worked out by hand from the sentence above**, on a 48K — position 0 encodes as
>    `(low 17471, high 3)`, each of the three later quarter boundaries as `(17471, 0)`,
>    `(17471, 1)` and `(17471, 2)`, position 69887 as `(0, 2)`, and position 1 as `(17470, 3)`. The
>    128's six are the same six read out of the sentence's other half, and
>    `the_counter_matches_the_format_descriptions_own_sentence` asserts both sets **and that the
>    two disagree at position 0** — the one assertion a loop over a single machine cannot make.
>
>    *This list said "three positions" while
>    `the_counter_matches_the_format_descriptions_own_sentence` asserted six, and*
>    `crates/spectrum/src/lib.rs`'s coverage table said three as well. Understated rather than
>    false, and corrected in both places in one pass: a correction that leaves another copy
>    standing has not corrected anything, it has added a disagreement.
> 2. **`libspectrum`, the FUSE project's snapshot library**, writes
>    `low = quarter − (t mod quarter) − 1` and `high = ((t / quarter) + 3) mod 4`, and reads back
>    `(((high + 1) mod 4) + 1) × quarter − (low + 1)`. That is an **independent implementation** of
>    the same paragraph; the shipped functions are algebraically identical to it, and its
>    expressions are transcribed into the suite and compared at every position of the frame rather
>    than paraphrased — and its `quarter_states` is a parameter of the machine there, which is the
>    detail worth transcribing along with the expressions.
> 3. **The hand-transcribed version 3 vector's own T-state field.** `snapshot_common`'s
>    `v3_vector()` writes `12415` at offset 55 and `1` at 57, worked out from the format
>    description for frame position 40000 — *"40000 falls in the third quarter, so the low
>    counter has 17471 − (40000 − 2 × 17472) = 12415 left, and the high counter reads
>    (2 + 3) mod 4 = 1"* — and `snapshot_vectors.rs` compares the parse against it.
>
>    *The list said "three things, and all three agree" and then gave two, while the mutation
>    table at the end of this document names three red instruments. The evidence was never
>    missing; the enumeration was. It is the defect this section is about — a corroboration
>    count stated above what is shown — occurring inside the section that names it.*
>
> All three were **proven able to fail**, not assumed to be able to: shifting the high byte's
> origin from three to zero in *both* directions — a symmetric change, verified present in the
> file before its verdict was trusted — left the exhaustive sweep green over all 69888 positions
> and turned all three of them red.
>
> **That run is M6's, and 69888 is M6's range.** The sweep graded a 48K-only function then; it now
> runs each machine over its own frame, 69888 **and** 70908, and nothing records a mutation taken
> since. The verdict stands for what it was taken on, and re-stating it against the wider gate
> would claim a run nobody made. The requirement written above this correction — *"graded
> exhaustively over all 69888 frame positions"* — is the same half-of-a-sentence reading the
> correction is about, arriving in the instruction rather than in the code; what shipped grades
> both frames.
>
> **A third-party file does *not* settle this, and that was measured rather than assumed.** Under
> the same mutation `tests/snapshot_corpus.rs` stayed **green**: everything it asserts about a
> foreign file — that it parses, and that `parse(write(parse(f))) == parse(f)` — is symmetric in
> exactly the way the formula is. A foreign file proves the field is *readable*, not that our
> arithmetic on it is right. Only a human loading one of our files in another emulator would, and
> that is T4 observation, not automated, and not done.
>
> One thing the paragraph did **not** anticipate: a hostile file can hold any `u16` in the low word,
> and the natural decode subtracts it. Under `overflow-checks = true` that is an abort, not a wrap,
> so the shipped decoder adds a whole frame before subtracting and takes the remainder — total over
> all 2^24 pairs, which is asserted rather than argued.

### The external oracle, which M6 has and M5 did not

Loading one of our own `.z80` files in a third-party emulator, and one of theirs here, are two
checks against an **independent implementation**. They are manual and they are observation — a
human looks at a screen — but they are observation of a different codebase's reading of the same
document, which is a materially different thing from observing our own. It is the only instrument
that grades a symmetric misreading of the format, and it costs one file and five minutes.

It belongs in the record, with the emulator named and the date, for the same reason every
re-measured row in `ARCHITECTURE.md` now ships with the command that produced it.

## Decision 8 — the gate is corpus-free by construction, and a corpus can only strengthen it — **ruling**

`MACHINE.md` ranks *known-demanding software* fifth and labels it observation. `STATUS.md` records
three gates that ran nowhere, the last of which — the M5 boot gate as an `examples/` binary —
`MACHINE.md` calls the worst form so far. (That attribution said `STATUS.md`; the phrase is
`MACHINE.md:141 the worst form so far`'s, and the count is `STATUS.md`'s. Corrected 2026-09-01
against both files, and re-anchored on 2026-09-02 when the bare number had drifted nine lines.)
M6's stated gate depends on files that **may not be redistributed**,
so by default its corpus is absent, and a gate whose corpus is absent by default is a gate that
runs nowhere. Proposing that and hoping would be the fourth instance.

The way out is not a better opt-out policy — `crates/testsupport` already implements the right one,
and M6 uses it unchanged rather than inventing a second convention. The way out is to **design the
gate so its data is data we authored**, and then to be exact about the residue that genuinely
cannot be.

### Four tiers

| Tier | What it is | Evidence class | Corpus | Runs |
|---|---|---|---|---|
| **T1** | R1/R2/R3, the truncation sweep, the codec property tests, the hand-transcribed vectors | **proven** — deterministic, self-contained | none: the fixtures are built in code and the vectors are bytes we wrote | every clone, every CI run |
| **T2** | The real ROM's `LD-BYTES` loads a synthetic tape through the `EAR` bit | **measured** — binary pass/fail against a program we did not write | `testdata/roms/48.rom`, already committed | wherever the M5 boot gate runs |
| **T3** | A program **we wrote** is loaded from tape by the ROM and then executes and writes a signature into RAM | **measured** | the same committed ROM | same |
| **T4** | A real game loads and reaches its title screen; one of our `.z80` files opens in a third-party emulator | **observed** | user-supplied, absent by default | manually, recorded in `STATUS.md` |

**T2 is the load-bearing one and it is worth being precise about.** The real ROM's loader is
entered at `0x0556` with `IX` as the destination, `DE` as the length, `A'` as the expected flag
byte and carry set for load-rather-than-verify; it does its own `DI`. Give it a tape we generated
from bytes we chose, run the machine until it returns to a sentinel return address or a step budget
expires, and assert the bytes landed and that carry came back set. That exercises the pulse
timings, the `EAR` bit position, the ULA port decoding, the clock's absolute progression, and the
memory map — **through the real machine, against a loader we did not write, with only a committed
corpus.**

What it does *not* grade, which must be said in the same breath: the ROM's edge detection has wide
tolerances, so **timings that are some way off still load**. T2 grades the mechanism, not the
precision. Nothing in M6 grades the precision, and `MACHINE.md`'s verification item 2 — a
known-timing test program — remains the only thing that would.

**T3 is what replaces "a real game runs" as the *gate*.** A few dozen bytes of Z80, assembled as a
byte array in the test, loaded from tape by the ROM, executed, and observed to have run. It is
genuinely "a program loads from tape and runs", it is deterministic, and it commits, because we
wrote it. What it does not cover is the sheer breadth of behaviour a commercial game exercises,
which only T4 reaches. A **custom turbo loader** was written here as belonging to that same
residue, and it does not: the construction T3 uses — bytes we assembled, run on the real machine —
extends to the *loader* as readily as to the program it loads, and
`crates/spectrum/tests/tzx_turbo_load.rs` is that extension. What stays at T4 is a turbo **game**.

### So what is M6's gate, in the project's own vocabulary

**M6's gate is T1 + T2 + T3. `MACHINE.md`'s "a real game runs" is T4, and T4 is observation that
cannot be automated in a repository that may not carry games.** That is a correction to the
milestone table, made in the open rather than by quietly narrowing what the row meant.

The residue is real and is not apologised for: T4 is the only tier that will run a program written
by someone who did not know how our emulator works. It was written here as the only tier that
grades a turbo loader as well, and that half has since been shrunk rather than removed. A turbo
**loader** is graded by `crates/spectrum/tests/tzx_turbo_load.rs`, which commits precisely because
we wrote both the tape and the loader; a turbo **game** is what cannot be committed, and it is what
is left. Nothing shrinks the remainder to zero. What M6 does is shrink it from *the whole gate* to
*the part that genuinely cannot be committed*.

### The corpus tier, when it exists

If a user has files, they should be swept, and the sweep uses the existing policy verbatim:

- `testdata/snapshots/*.z80`, `*.sna` and `testdata/games/*.tap` are **directory sweeps**, not named
  files. Every file present must parse; every `.z80` must survive R3.
- Absent → `testsupport::skip_absent_corpus` decides: **fail** when undeclared, skip under
  `ZX_CORPUS_ALLOW_MISSING`, **refused** under `CI`. One convention, not one per corpus, which is
  the thing `testdata/README.md` already promises.
- **It is a `#[test]`.** Not an example, not a binary, not a `main` that prints a verdict. That
  sentence exists because it is the M5 finding and it is the cheapest possible way not to repeat
  it.

### One thing worth noticing about what M6 unlocks

`MACHINE.md`'s verification item 2 — the community timing-test programs that report measured
T-state counts — is *"the closest thing to an oracle available, and it is a real one"*, and it is
the settling condition for the open `FIRST_CONTENDED_T_STATE` question. Those programs are
distributed as tapes and snapshots. **M6 is the milestone that makes running them possible at all.**
Whether any of them may be committed to `testdata/` is a licensing question this document does not
answer; if one may, it becomes the first genuine machine-level oracle this project has, and it
belongs under the same policy as everything else there.

## Decision 9 — no `.szx` — **ruling (YAGNI)**

`.szx` is a better format than `.z80`: chunked, extensible, and it carries CPU state the others do
not — including `MEMPTR`, which is the one field Decision 7 identifies as unpreservable.

It is still out of scope, for three reasons:

1. Its extensibility pays off at **M7**, where the AY registers, the paging port and the second ROM
   all need somewhere to live and `.z80` v3 carries them awkwardly. Adding it now is building for a
   milestone whose requirements are not yet fixed.
2. Its `MEMPTR` advantage buys nothing **measurable** today: nothing in this project can grade
   `wz`, so preserving it would be an unverifiable improvement to an unverifiable field.
3. A third parser triples the hostile-input surface of Decision 6 for no additional gate.

M6 already cut scope once, in Decision 3, by making `.sna` read-only. Adding a third format while
the second is deliberately half-implemented would be incoherent.

## Implementation order

## What this document could not settle

- **The exact `.z80` v3 T-state encoding.** Its shape is described in Decision 7 and flagged as the
  highest-risk field in the design. Nothing in this repository can adjudicate it, and neither can
  the exhaustive test that will be written for it. Reading the format description, and then loading
  one of our files elsewhere, is what settles it.
- **Whether a third-party-produced `.z80` or `.sna` may be committed.** It is the only instrument
  that separates *the format* from *our reading of the format*, and it is one small file. This is a
  licensing and policy call for the user, not a design decision.
- **Whether `.tap` is sufficient for T4 at all.** If the games available are turbo-loader titles —
  and most commercial ones are — then no `.tap` can carry them and T4 cannot pass at M6 regardless
  of how correct the machine is. This bears directly on whether the milestone can be declared done,
  and it is answered by looking at the actual files, not by more design. If the answer is no,
  `.tzx` moves from *later* to *required*, and Decision 5 is what makes that cheap.
- **Whether `restore` should reset `frames()`.** It is left alone, for a stated reason (uptime
  means one thing), but the alternative is defensible and the FLASH-phase discontinuity is the
  visible cost. A user noticing the flash jump after a load is what would decide it.
- **The `EAR` sampling point within an `IN` cycle.** Approximated to the start; the error is at
  most four T-states and is far inside the ROM's tolerance. A specific turbo loader failing is what
  would decide it, and there is nothing to be gained from guessing sooner. A turbo loader now runs
  here and has not failed for this reason, which leaves the question where it was rather than
  answering it — see Decision 5, where the same absence is recorded as an absence.

## What the implementation found — the pure half, built 2026-09-01

This section is appended by the implementer of `crates/spectrum/src/snapshot/`. It records
which of this document's numbers were **verified against the format description**, which were
**falsified**, which remain **unverified**, and the three rulings that were open when it was
written and are now settled. Nothing above is deleted; the two defects found are corrected
inline, at the paragraph that carries them, so a reader who acts on that paragraph finds out.

### The three rulings that were open, now settled

**1. Third-party snapshots are fetched, never committed.** The document left this as a
licensing call. The answer follows this repository's existing convention exactly: the corpus
lives in gitignored `testdata/snapshots/` with a documented SHA-256 and provenance per file,
fetched by whoever runs the tests, gated through `crates/testsupport`'s absence policy
unchanged — fail when undeclared, skip under `ZX_CORPUS_ALLOW_MISSING`, **refused under `CI`**.
The 48K ROM remains the single committed exception, on the strength of the permission now quoted
in full — text, author, forum, date, conditions and hedged scope — in `testdata/README.md`, which
is the one place that carries it. *(This sentence read "because Amstrad permits it" and was one of
five unsourced copies of that claim; the sourcing landed 2026-09-01.)* Nothing is
redistributed and the instrument exists. `testdata/README.md` documents the four files the
way the FUSE and `zex` corpora are documented.

**2. M6's gate is T1 + T2 + T3, and "a real game runs" does not gate it.** Decision 8 already
argued this; it is now a ruling rather than a proposal. T4 is *observation* in this project's
vocabulary and cannot be automated in a repository that may not carry games. **`MACHINE.md`'s
and `ARCHITECTURE.md`'s milestone tables still carry the old wording** — neither file is the
implementer's to edit, so this is flagged rather than fixed: both rows should read *"gate:
T1+T2+T3; a real game running is T4, observation, recorded in `STATUS.md`"*.

**3. `.tzx` stays deferred**, `restore` does not reset `frames()`, and the `EAR` sampling
point stands as chosen. Unchanged, and none of them is touched by this half.

### Every byte-level number in this document, checked against the format description

The document's own warning — *"every byte offset, page number and flag-bit position was
written from familiarity, not transcribed"* — was worth heeding: it was **right about most of
them and wrong about two**, and one of the two would have shipped unreadable files.

| Claim | Verdict |
|---|---|
| 48K pages are 4, 5 and 8, for `0x8000`, `0xC000` and `0x4000` | **verified** — *"In 48K mode, pages 4,5 and 8 are saved"*, page 4 at `8000-bfff`, page 5 at `c000-ffff`, page 8 at `4000-7fff` |
| Those are banks 2, 0 and 5 here, and **only bank 5 satisfies `N − 3`** | **verified**, and it is asserted as a test rather than a comment. The mid-draft catch was correct |
| 128 files number page *N* as bank *N − 3* | **verified** — pages 3–10 map to banks 0–7 |
| v1 byte 12 packs the border into bits 1–3 and `R`'s high bit into bit 0 | **verified**, along with *"bit 4 SamRom"* (hardware we do not have) and *"bits 6-7 no meaning"* |
| "byte 12 = 255 means 1" | **verified**, quoted |
| `PC = 0` at offset 6 is the v2/v3 sentinel | **verified** |
| A v2 additional header is 23 bytes covering offsets 32–54, **one short** of the T-state field at 55 | **verified** — this is the load-bearing reason the writer emits v3, and it holds exactly |
| v1's block is terminated by `00 ED ED 00` | **verified** |
| Page length `0xFFFF` means 16384 raw bytes, not a length | **verified** |
| A run-length count of zero is legal and consumes four bytes | **verified** by construction; it is what makes termination structural |
| **The v3 T-state high byte selects a *third* of the frame** | **FALSIFIED** — quarters, modulo 4, and offset by three. Corrected inline at Decision 7 |
| **The compression scheme "is one escape; a lone `ED` is literal"** | **INCOMPLETE** — two of the four rules are missing, including the one that makes our files readable elsewhere. Corrected inline at Decision 6 |
| Hardware mode "not a 48K" is one rejection | **incomplete, and the gap is a trap** — the two versions **renumber** the modes. | `.sna` is a 27-byte header then 49152 bytes; `PC` on the stack; only `IFF2`; no T-state counter | **verified**, field by field, and the whole file is exactly 49179 bytes |

**Unverified, and named as such:** every hardware-specific byte at offsets 35–38 and 58–86 is
written as zero and ignored on read. They describe an Interface I, a Multiface, a sound chip
and joystick maps that a 48K does not have; nothing here grades them, and nothing in this
milestone could.

### The layout deviates from Decision 1 by one module, and why

Decision 1 puts the codec in `snapshot/z80.rs`. It is `snapshot/rle.rs` instead. The reason is
cohesion: header parsing and a run-length codec are two tasks with two separate hostile-input
tables and two separate styles of test — a property test for one, transcribed offsets for the
other — and keeping them in one ~600-line file would have been one module with two jobs.
`snapshot/reader.rs` also holds the **`Writer`** as well as the `Reader`, which Decision 1 does
not mention, because the property being enforced is about *slicing* and putting both cursors in
one file makes the gate a count over one file.

### What is deliberately not built here, and what it needs

`Spectrum::restore` and `Spectrum::snapshot` are **not built**. Everything in `snapshot/` is
pure — `parse(&[u8]) -> Result<Snapshot, Error>` and `write(&Snapshot) -> Vec<u8>`, no
filesystem, no machine, no clock — which is Decision 1's purity achieved by signature, and it
is why this half could be built while `ula.rs` was held elsewhere. The applier needs exactly
the four `pub(crate)` items Decision 1 predicted, and no more:

| `ula.rs` must expose | Used for | Why not an existing method |
|---|---|---|
| `pub(crate) fn set_border(&mut self, Colour)` | `snapshot.border` | `out_port` charges a four-T-state I/O cycle that never happened **and** leaves `covered_t_states` armed at 4, so the next instruction's first four ticks would be charged as an open cycle and skip their contention. A concrete defect, not a preference |
| `pub(crate) fn set_frame_t_state(&mut self, u32)` | `snapshot.frame_t_state` | `Clock::advance` is `pub(crate)` and `Ula::clock()` returns a `Copy` **by value**, so there is no route to the clock that is not a no-op |
| `pub(crate) fn clock_frames(&self) -> u64`, or nothing | leaving `frames()` alone | Nothing needed: the ruling is that `restore` does **not** touch the frame counter |
| RAM, via `Memory::write` at the addresses `Memory::slots()` puts each bank at | `snapshot.banks()` | `Memory::bank`/`bank_mut` are **not** needed at M6 and become unavoidable at M7. Adding them now is a semver commitment with no caller |

`Snapshot::banks()` and `Snapshot::set_bank` are already `pub(crate)` and iterate in ascending
bank order, so the writer and the applier cannot disagree about which banks a snapshot carries.
The seam Decision 2 names — a bank present in the snapshot and absent from the slot map — is
closed by a test that compares the parser's bank set against `Memory::slots()` and fails if
they diverge, so it is asserted rather than reasoned.

### The external oracle ran, and it found something

All four third-party files parse: a v1, a v2, a v3 and a `.sna`, from three independent
emulator projects. Each survives `parse(write(parse(f))) == parse(f)`.

The `fire.z80` / `fire.sna` pair — one machine state saved by a third party in both formats —
is the strongest instrument in the milestone, because `.sna` has no writer and therefore no
round trip of its own. It **immediately caught a wrong expectation**: `SP`. A `.sna` writer
*pushes* `PC`, so its stored `SP` is two below the machine's, and a correct pop restores the
**same** `SP` the `.z80` carries as a plain field — not one two higher. The parser was right and
the expectation was wrong, which is exactly what an external oracle is for and exactly what no
test built from our own code could have told us.

## What the implementation found — the applier and the tape, built 2026-09-01

Appended by the implementer of `Spectrum::restore` / `Spectrum::snapshot` and
`crates/spectrum/src/tape/`. It records what this document predicted correctly, the **two
places it is wrong**, and the measurements that decide which is which. Nothing above is
deleted; corrections are attached at the paragraph that carries the claim.

### The public API delta, item by item

`Ula`, `Memory`, `Clock` and `CpuState` grew **no public items**, which was Decision 1's whole
argument and is the only hard evidence in it. What did grow:

| New public item | Why it is unavoidable |
|---|---|
| `Spectrum::snapshot()` / `Spectrum::restore()` | the applier; nothing else can reach the machine's state as a value |
| `pub mod tape` | the milestone's second subject |
| `tape::Tape` + `new` / `play` / `stop` / `rewind` / `level` / `pulses` | the minimum a consumer needs, plus the two accessors the gates need to grade the signal without owning the encoder |
| `tape::Error` (`#[non_exhaustive]`) | a parser of untrusted input returns typed failures |
| `tape::tap::parse` | the milestone names the format |
| `Spectrum::insert_tape()` / `Spectrum::tape_mut()` | the tape lives on the `Ula`, which the machine owns |

**Two deviations from Decision 1's list, both deliberate.**

`Tape::new` and `Tape::pulses` are **public** where the plan implied only `play`/`stop`/`rewind`.
The reason is the gates rather than a consumer: `tests/tape_signal.rs` has to build a square wave
by hand to grade the `EAR` wiring independently of `.tap`, and it has to read a train back with a
decoder it owns — an expectation computed by its subject is a tautology, which is
`docs/STATUS.md`'s keyboard-matrix finding. Both are also what makes `.tzx` a converter at M7
rather than a rewrite, which is Decision 5's stated payoff. `Tape::is_finished`,
`Tape::position` and `Spectrum::eject_tape` stay absent as planned.

**`Spectrum::tape_mut` returns `&mut Tape`, not `Option<&mut Tape>`.** A drive with no cassette
and a cassette with nothing recorded on it drive the `EAR` line identically, so there is no state
for a caller to distinguish and no option to unwrap. `Tape::default()` is the empty drive.

**New `pub(crate)` items** — public surface unchanged: `Ula::set_border`,
`Ula::set_frame_t_state`, `Ula::insert_tape`, `Ula::tape_mut`, `Clock::set_frame_t_state`, and
one private `Ula::advance`. Decision 1 predicted four of these and did not anticipate
`Clock::set_frame_t_state`: `Clock`'s fields are private and `advance` cannot express "move
within the frame without adding time", so the setter had to exist one level down. It carries the
same `pub(crate)` footgun warning `advance` does, for the same reason — `Ula::clock()` returns a
`Copy` by value, so a public version would auto-ref a temporary and silently do nothing.

### Decision 2's stated reason for `set_border` is half wrong, and the half that survives is a different mechanism

This document says routing a restore through `out_port` *"would leave `Ula`'s `covered_t_states`
armed at 4, so the first four ticks of the **next instruction** would be charged as an open cycle
and skip their contention."*

**The "next instruction" clause is false, and it was measured.** Every instruction begins with an
opcode fetch, and `begin_memory_cycle` assigns `covered_t_states` unconditionally — so a stale 4
is overwritten before it can be spent. Nothing reachable through `Spectrum::step` can see it.
The clock damage is masked too, because `restore` sets the frame position *after* the border.

Two things do survive, and the mutation table below is what separates them from the claim:

- **A bare-tick sequence.** The interrupt acknowledge is seven `Bus::tick` calls with **no
  transfer** to reset the count, so a stale 4 would silently cover four of them.
  `a_restore_leaves_no_machine_cycle_half_open` drives one tick directly, which is the smallest
  thing that can see it.
- **The tape.** A port cycle advances the clock by its contention stall, and the tape advances
  with the clock, so a restore through the bus **moves the head**. That one survives whatever
  order the setters run in, which makes it the more durable of the two.

So the setter is still unavoidable and the reason is still concrete — it is just not the reason
written down. **Positioning matters:** `a_restore_does_not_move_the_tape` could not fail until the
machine's clock was inside the display window when `restore` ran, because a ULA port access is
only stalled there and the border is set before the frame position. The first version of that test
was green under the mutation it exists for.

### The tape: what the `EAR` model is, and what T3 proves that a trap would not

The signal is a **pulse train** — a `Vec<u32>` of half-period lengths in T-states. During
`pulses[i]` the line holds one level; at the end of it the line flips. That is the quantity the
ROM's loader actually measures, and it is why the internal form carries no notion of a byte.

One private `Ula::advance` moves the clock and the tape together, and the three `Clock::advance`
call sites route through it. **Contention is elapsed time**, so a tape driven from `Bus::tick`
alone would run slow by exactly the contention a loader suffers — measured: 32 `NOP`s cost 128
T-states out of the contended bank and **194** in it, from the same frame position.

**T3 loads a program we wrote from a `.tap`, by the ROM's own `LD-BYTES`, and runs it.** The
program adds `0x1234` and `0x1111` and stores `0x2345` — a value that appears **nowhere in its own
bytes**, asserted by the test — so "the bytes arrived" and "the program executed" are separated.
Everything in between is the real machine: thousands of `IN A,($FE)` port cycles, each contended
by the four-case I/O rule, each reading bit 6 of a level that is a function of the frame clock's
absolute position. A trap would have graded none of it.

`no_shortcut_exists_past_the_ear_bit` is the standing assertion Decision 4 asks for: the same
tape, the same stub, the same budget, with the motor **stopped**. The loader spins in `LD-START`
waiting for an edge that never comes, nothing reaches the destination, and the machine is asserted
to still be inside the ROM — which distinguishes *waiting* from *wandered off*, since both look
like an expired budget.

### The external instrument the document asked for, and what it found

Decision 8 leaves the tape's timings graded only by *"the ROM's tolerance, not by measurement"*.
That row is now narrower. `tests/tape_rom_timings.rs` runs **`SA-BYTES`, the ROM's own tape
writer**, on the real machine behind a recording `Bus`, and measures the intervals between the
edges it puts on the `MIC` line. The ROM is code this project did not write, its timings *are*
what a `.tap` means, and it is committed — so this is an oracle that runs on every `cargo test`.

**3305 half-periods, two implementations, no shared code, compared by value and in order.** It
found three things:

1. **The ROM's writer does not emit a uniform train.** Within a byte every half-period is exactly
   855 or 1710. The interval spanning a **byte boundary** is three T-states *shorter*
   (`LD B,$31` at `0x052D` under-compensates the per-byte housekeeping), and the first
   half-period after the sync is one T-state *longer* (entered with `B = 0x3B` from
   `LD BC,$3B0E` rather than the loop's `0x3E`). Both are asserted by value rather than absorbed
   into a tolerance.
2. **The boundary before the parity byte is a third case**, at one T-state short rather than
   three, because `SA-PARITY` reaches the bit loop by a path two T-states longer than
   `LD L,(IX+0)`. **This is the one the derivation got wrong** — it was written as an ordinary
   byte boundary, the measurement disagreed by exactly two T-states, and the ROM's instruction
   stream explained the difference. Derive first, then measure, then reconcile: the derivation
   was wrong and it was wrong *legibly*, which is the whole value of having written it down.
3. **The ULA contends the writer's own `OUT`s.** Port `0xFE` is a ULA port, so on real hardware
   the emitted signal jitters by 0–6 T-states during the display window. The measurement
   subtracts it — using the contention model, which four other gates grade — so the comparison
   is an equality rather than a range.

### Decision 5's payoff, cashed and measured

This document's largest bet was that a **pulse train** internal form would make `.tzx` a second

argument:

| | |
|---|---|
| Fields, methods or variants added to `Tape` | **zero** |

| Lines changed in `crates/spectrum/src/lib.rs` | **zero** — `pub mod tape` already existed |

**If the internal form had been a block list, none of those would be zero.** `.tzx`'s pure-tone,

### The public API delta

| New public item | Why it is unavoidable |
|---|---|
| `pub mod tzx` | the format this document deferred and `STATUS.md` names as *"the first thing to add if T4 is ever attempted"* |
| `tzx::parse(&[u8], Model) -> Result<Tape, Error>` | the converter |
| **Nine new `tape::Error` variants** | the enum is already `#[non_exhaustive]`, so adding them is **semver-additive** — which is the reason that attribute was put there |

**`parse` takes a `Model`, and that is the one design decision in this half worth arguing.**
`ID 2A` stops the tape *only* on a 48K, and this machine now has both models. The cost of
getting it wrong is **not symmetric**: wrongly continuing past a stop is nearly harmless, because
the loader has stopped listening by then, while wrongly stopping truncates a 128 multiload at its
first level. So the machine is an input to the conversion rather than a default to pick, and the
alternative — a second entry point — is refused for the reason `crates/frontend/src/media.rs`
already gives about its own: it would mean *"two places that decide what a machine is"*.

`.tap` is untouched at the surface: `tap::parse` keeps its signature. Its **behaviour** changes
in one way, recorded here rather than left to be discovered — it can now return
`Error::TapeTooLong`. That is a fix rather than a new restriction: a `.tap` byte is sixteen
half-periods, so a 1 GB file used to be a 4 GB allocation with nothing to stop it.

> **CORRECTED (tape findings, 2026-09-01) — the sentence above is wrong twice, and the same
> wording had been copied into `tap.rs` and `signal.rs`.** Sixteen `u32` half-periods per byte is
> 64 bytes per byte, so its own premise gives **64 GB**, not 4 — wrong by 16×. And the premise is
> the wrong axis: what binds a `.tap` is the **block count**, not the byte count, because a
> block's pilot tone is a fixed cost its payload does not pay for. The cheapest legal block is
> three bytes — a length word and a lone flag — and it buys 8082 half-periods, so the real
> amplification is **2694 per input byte** and a 1 GB file is **10.8 TB**. The derivation now
> lives once, as `tap::MINIMAL_BLOCK_PULSES`, pinned by `const` assertions, and
> `the_ceiling_is_reached_by_block_count_rather_than_by_file_size` is the failing case the
> variant went without.

### The allocation bound, and the one that is not structural

Decision 6 requires that no allocation be sized from the file and that every loop terminate.
**`.tzx` is the first parser here where neither is free**, and the two problems are genuinely
different rather than one problem twice:

| | Bound | Why it exists | What proves it |
|---|---|---|---|
| **Memory** | `MAX_PULSES = 2^24` half-periods, 64 MB | a loop block asks for its body up to 65535 times while costing three bytes — a loop count times a block length **is** an allocation sized from the file | a 24-byte file demanding 4.2 billion half-periods returns `TapeTooLong`, and the ceiling's boundary is asserted from both sides |
| **Termination** | `MAX_BLOCKS_PLAYED`, equal to `MAX_PULSES` | *"Jump 0 = 'Loop Forever' - this should never happen"*, says the description, of a file it also permits | a jump to itself returns `TooManyBlocksPlayed` instead of hanging |

**The ceiling is derived, not chosen.** A tape recording the machine's whole 48 KB address space
is 789,657 half-periods — asserted in the test rather than cited from this document — and the
ceiling is twenty-one times that.

> **CORRECTED (tape findings, 2026-09-01) — it is chosen, and "twenty-one" is the giveaway.**
> Nobody picked twenty-one. It is `1 << 24` divided by 789,657 and rounded down: the conclusion
> read backwards into its own premise. A round number is a choice, and the honest form is to say
> so and to put the choice in the units the choice is about — the constant is now
> `MAX_TAPE_BYTES / size_of::<u32>()` with a **64 MiB memory budget** named as the thing that was
> decided. **The value is unchanged at 16,777,216**, asserted against both `1 << 24` and the
> literal so that spelling it honestly cannot have moved it.
>
> What is genuinely derived is the **headroom**, and on both axes, because they are different
> axes and only one of them is the file's size: the **block** axis (`tap::MAX_PLAYABLE_BLOCKS`,
> 2075 — reached by a 6,228-byte file, which is the worst case) and the **byte** axis (one
> mebibyte of block payload, which is what a real tape spends it on). Every tape in `testdata/` is
> four to six blocks, so both have room to spare; the 48 KB figure above still stands and its test
> is kept, now labelled as grading headroom rather than producing the ceiling.

**The budget equals the ceiling, and that equality is derived from both sides.** Below it, the
budget could refuse a file the memory ceiling permits: a loop body of sixteen blocks each
emitting one half-period stays well inside the tape's size limit while executing over a million
blocks. Above it, it buys nothing, because a file can only exceed the ceiling's worth of
executions by being almost entirely silent.

**Progress is not structural here, and that is said out loud.** Everywhere else in this workspace
a parse loop consumes at least one input byte per iteration, so termination is a property of the
code. A jump revisits a block without consuming anything, so this one is a **budget** — and a
budget called a budget is honest in a way that one dressed up as a proof is not.

## What the turbo gate found — a loader of our own, 2026-09-02

`crates/spectrum/tests/tzx_turbo_load.rs`, sixteen tests, closes a hole this document named and
then carried through every landing since: `.tzx`'s entire reason for existing — that `.tap` cannot represent a
custom loader's tape at any speed — had never been exercised, because the ROM cannot read a turbo
block and nothing here could either. The pilot, sync and bit fields of `ID 11` were therefore
graded only **at the ROM's own values**, where they are indistinguishable from constants.

The missing half was never the format. It was the other end of the wire: a **loader**. So the gate
supplies one — 124 bytes of hand-assembled Z80 running from RAM on a blank ROM page, counting edges
on `IN A,($FE)` itself, decoding a block at pilot 1400 / sync 500 / bit0 500 / bit1 1200 against the
ROM's 2168 / 667 / 855 / 1710. It never calls the ROM at all; the machine is entered with `PC` set
into RAM and the test asserts it stayed there. The same signal is then reached by three further
routes — `ID 12 + ID 13 + ID 14`, an `ID 15` direct recording, and an `ID 30 / 21 / 23` tape that
arrives at the primitives only by following a jump — and all four produce one identical
112,594-pulse train. Four encodings sharing no field layout cannot be wrong the same way by
accident.

### The distinction this puts into the document, and it is not a hedge

**The turbo *format* is graded. A turbo *game* is not, and cannot be.** No commercial turbo-loaded
title is present, `testdata/games/` is gitignored so none can be committed, and that is what remains
of the **turbo** part of T4 — the tier's other residents, a program written by somebody who did not
know how this emulator works and our arithmetic on a format's fields, are untouched by any of this.
`tzx_rom_timings.rs` draws the same line from the other side and is the wording
to follow rather than to paraphrase: the turbo gate *"grades a turbo tape the way this file grades a
standard one — by running a loader and measuring what it makes of the signal — with a loader written
in this repository rather than Sinclair's, because no ROM will do it. What it cannot borrow from
here is the **oracle**"*, since there is no third party for turbo timings the way the ROM is one for
standard ones. The two files are complementary, not overlapping: one has the better oracle and the
other the wider reach.

### Three measurements, and the second is the one to read twice

**No ceiling was found.** At **3.56×** the ROM's data rate — 600 / 220 / 220 / 500, the fastest
tried — the emulator plays a tape that a guest loader reads byte-perfect. Every failure met was the
*test loader's* resolution and not the emulator's, and that is proved rather than asserted: each
failing rate is played back byte for byte unchanged and the only thing altered is an immediate
inside the guest's own Z80 code, after which all of them read the whole screen. If any limit
belonged to the emulator — to a rounding step in the pulse train, to a floor on how short a pulse
may be — editing a constant in the guest could not have lifted it. Half-periods are exact `u32`
T-state counts with no rounding anywhere in the path.

**2.08× fails silently, and that is the finding worth recording.** At 1050 / 380 / 380 / 850 the
loader painted its border **green over 1244 wrong bytes**. A one bit's poll count lands *on* the
loader's threshold, and the ULA's I/O contention moves the cost of a poll across the frame, so bits
drop from the same position in scattered bytes, each removing the same value from the fold, and an
even number of them cancels. The loader folds, agrees with itself, and reports success. **It is the
all-zeros hole met from the other side** — the one this gate had already caught in itself, when an
expected checksum carried *on the tape* let a loader that decoded nothing compute zero, read zero,
and pass. The file asserts the marginal row **structurally** rather than by the count: the claim is
*the fold agreed and the bytes did not*, which is a property of `XOR`, where 1244 is a property of
this payload landing on this frame.

**A source-level mutation matrix says which kinds of gate see what.** Run in an isolated clone
against a deliberately broken `ID 11` handler, each mutation's landing proved by diff and hash
before its verdict was read:

| mutation of the `ID 11` handler | `tzx_turbo_load` | `tzx_vectors` | `tzx_rom_load` | `tzx_rom_timings` |
|---|---|---|---|---|
| the bit-one field ignored, the ROM's 1710 emitted instead | **red**, 5 of 16 | **red**, 5 of 10 | green | green |
| the pilot and first-sync fields transposed | **red**, 9 of 16 | **red**, 4 of 10 | **red**, 3 of 7 | **red**, 2 of 5 |
| the pilot-count field ignored, the ROM's 3223 emitted instead | **red**, 6 of 16 | **red**, 5 of 10 | green | green |

**Rows one and three are the point.** Substituting the ROM's own value for a field is invisible to
every gate whose tape carries the ROM's own value — there is nothing left to disagree with — so
both gates that grade by **running a machine with the ROM in it** stayed green, and until this gate
existed the only instrument that caught those fields was the vector-level one, which compares
against pulse trains a human transcribed from the format description. The middle row is different
in kind: a transposition is wrong at *every* speed, so it breaks the standard tapes too and all
four see it.

**The tempting generalisation is that a gate which grades by running a machine was blind, and it is
wrong** — this file runs a machine too, and reddens on all three rows. What separates the two
columns is not whether a machine runs but **whose loader is reading**: a loader that only knows the
ROM's values cannot report a disagreement with them.

That is a statement about instruments rather than about `.tzx`, and it is the same one Decision 7
makes for snapshots in the other direction. **A machine-level gate reaches further than a vector but
sees only what its own loader is sensitive to.** The turbo gate does not replace `tzx_vectors.rs`;
it is the second instrument that reaches those fields, and the only one of the two that would notice
if the pulses were right and the machine reading them were wrong.

### What this does not move

- **T4.** A turbo game still loads nowhere, and the corpus that would change that may not be
  committed.
- **The timings against hardware**, unchanged and for the unchanged reason. This gate's signal is
  one this project generates, so it cannot be an external check on the numbers.
- **The `EAR` sampling point**, which stands where Decision 5 leaves it. A tight-margin loader now
  runs and has not failed for that reason, and an absence of failure is not a measurement.
- **Contention during a load**, which the marginal row above *depends on* — the 2.08× behaviour is
  produced by the four-case I/O rule varying the poll cost across the frame — without yet being
  asserted against it. Nothing has been mutated in the contention model against this gate, so the
  register row stays open, with a sharper settling condition than it had.
- **`ID 19`**, the generalized data block, which is not implemented. It is refused by ID and byte
  offset at parse time rather than skipped or hung on, and that behaviour is pinned next to the
  turbo work where somebody looking for it will be.
