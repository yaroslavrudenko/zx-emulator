# M8 — the browser

Design for `crates/frontend`. [`MACHINE.md`](MACHINE.md)'s milestone table says **WASM +
macroquad — playable from a URL.** Decision 7 says what the second half of that sentence can and
cannot be made to mean, and Decision 9 disagrees with the first half of what three other documents
say this milestone contains.

Each decision carries the class of evidence behind the claim that forced it, in the vocabulary
[`M6.md`](M6.md) established and [`M7.md`](M7.md) kept — **proven**, **measured**, **derived**,
**observed**, plus **ruling** for a choice no evidence forces, recorded so it is not re-litigated.
A ruling is not evidence, and where one is doing load-bearing work this document says what would
replace it.

> **Every browser behaviour, keyboard-shortcut claim, JS-bundle line and `wasm32` standard-library
> claim below is a pointer to verify, not a specification.** `M6.md` opened with this warning and
> it was **right**: three of its numbers were later found wrong, and one of them — the `.z80`
> compression rule that a literal `ED` is never followed by an escape — was a defect **no round
> trip could have caught, because our own decoder misread it symmetrically**. `M7.md` opened with
> it and inherited the same result. A claim in this document that disagrees with a browser is a
> defect in this document.
>
> **This milestone's version of that hazard is worse in one specific way, and it is the reason the
> warning is longer here than in either predecessor.** M6's and M7's numbers were wrong about a
> *file format* or a *chip*, both of which sit still and can be read. M8's are claims about **four
> browsers on three operating systems, each of which reserves a different set of keys and changes
> the set between releases.** There is no document to transcribe from that is authoritative the way
> a `.z80` format description is, and there is no artefact in this repository that can be consulted
> instead.
>
> **The figures at highest risk, named so they are checked first:**
>
> | Claim | Where it is used | Why it is at risk |
> |---|---|---|
> | Which `Ctrl` chords a page can cancel and which the browser takes first | Decision 2, which the whole keyboard design turns on | Written from familiarity. Browser- and OS-specific, and undocumented as a set anywhere |
> | That `std::fs::write` returns `Unsupported` rather than failing to link on `wasm32-unknown-unknown` | Decision 4, and `host.rs`'s existing claim that the crate already compiles for the target | Asserted in `host.rs` and repeated here. Verified by nobody in this document |
> | That `Path::exists()` returns `false` on `wasm32` rather than panicking | Decision 4's account of what `free_path` degrades into | Same class, and it decides whether `F2` produces a filename or a crash |
> | That a top-level `data:` navigation is blocked by every current browser | Decision 4, where it kills the one route that would need no new `unsafe` | Written from familiarity with a policy change, not from a specification |
>
> **And one hazard that is new to this project: the obvious way to verify the first row is
> invalid.** A key press injected through the Chrome DevTools Protocol — `Input.dispatchKeyEvent`,
> which is what every browser-automation tool in this environment ultimately calls — is delivered
> *to the page* and does not traverse the browser's own shortcut layer. So `Ctrl+P` injected that
> way will be reported by the page as an ordinary cancellable `keydown` **whether or not** a real
> `Ctrl+P` would open the print dialog, and an automated check would return a confident green for
> a claim it never tested. That is `STATUS.md`'s *"a count of zero and an absence of the subject
> are the same observation"* arriving in a new costume, and it is why Decision 2's evidence class
> is **derived** and its settling condition is a person at a physical keyboard.

## What M8 inherits, and the one thing it does not

**Almost all of this milestone was paid for before it started, and by an author who said so.**
`crates/frontend/src/host.rs` opens *"This module is the entire `wasm32` seam"* and lists the
non-portable calls: **two** — *where the arguments come from*, and *how bytes get out*, which are
two **concerns** rather than two functions. Decision 1 turns on that count and is corrected there
for having read it as a count of the module's public surface, which has never held two of anything.
Everything else in the crate is portable by three choices made
deliberately rather than discovered — time comes from `macroquad::time::get_frame_time` and
`get_time` and never from `std::time::Instant`; bytes come in through `macroquad::file::load_file`,
which is `async` on both targets and an HTTP request in a browser; and nothing in the frame loop
touches the filesystem.

**The portability is structural rather than asserted, and the assertion is one command.** Read on
2026-09-01:

```sh
grep -rn "cfg(target" crates/frontend/src/ crates/spectrum/src/ crates/z80/src/
```

It returns nothing. There is **no target-conditional code anywhere in the workspace**, so the code
`cargo test -p frontend` runs on the host and the code the browser runs are the same code, and that
is true by inspection rather than by a test run. This is the shape `STATUS.md` prefers wherever it
is available — *"a property of every build beats an observation about one"* — and Decision 7 leans
on it hard, because it is the only thing that makes host-run tests say anything about a `wasm32`
build.

**What M8 does not inherit is any way to grade what it adds.** M6 had an oracle for the *files*.
M5 got one for the *machine*. M7 asked whether a 128 equivalent existed and answered no. M8 does
not need to ask: **the thing this milestone adds is a browser, a GPU, a keyboard and a person, and
none of those four is gradeable by anything in a repository.** That is not a shortfall of effort
and it is not a research question. `crates/frontend/src/lib.rs` already states it for the native
shell — *"almost everything a person means by 'is it right' … has no oracle here and never will"* —
and every word of it survives the target change. Decision 7 is where that stops being a
disclaimer and becomes a gate design.

## Decision 1 — the browser is a build target, not a second frontend — **ruling, with the count that makes it affordable**

There is one `crates/frontend`, one `BINDINGS` table, one `EXTENSIONS` table, one `viewport::fit`,
one `palette::write_rgba`, one `Pacer`. The browser build is `--target wasm32-unknown-unknown` and
a different implementation of **two functions**. It is not a `frontend-web` crate, not a `web`
feature, and not a second `main.rs`.

**The reason is the one this project states everywhere and has already been bitten by:** two
implementations of one rule is the duplication that guarantees a divergence nobody sees, and the
keyboard is where it would land. A browser keymap and a native keymap would be the same forty rows
copied, and `STATUS.md` records what copying a derivation does — *"three files saying the same
thing reads exactly like corroboration. It was not corroboration: it was one derivation copied
three times, and copying a conclusion is the one operation that cannot detect an error in it."*

**The cost of the ruling, counted rather than felt.** The two concerns enter the crate through
`frontend::host::arguments` and `frontend::host::save`. Everything else the browser needs is a
different *value* of an existing knob or a file beside the page. That is what makes "one crate"
affordable; if the count were twenty the ruling would be wrong and a second crate would be right.

**And the count is a claim with a date on it, so it is checkable — though not by the command this
paragraph offered for it.** That command was the module's whole public surface:

```sh
grep -c "^pub fn \|^pub enum \|^pub const " crates/frontend/src/host.rs
```

It answers **6** today — `arguments`, `arguments_from_query`, `partition`, `SaveError`, `free_path`,
`save` — and it answered **4** at the commit that introduced this paragraph, before M8 added the
first two. **It has never once returned two.** Neither number was wrong; they count different
things, and the sentence joining them with *"exactly"* was the whole of the error. What is two is
the count of **concerns**, which is what `host.rs` counts in its own words — *"keep the count of
non-portable calls small enough to list. It is two: **where the arguments come from**, and **how
bytes get out**"* — and the six public items are three on each side of that line: `arguments`,
`arguments_from_query` and `partition` are the first, `save`, `free_path` and `SaveError` the
second. **The ruling stands because the grouping holds, not because the arithmetic did.**

**So the check is the grouping, and that is the thing to re-run.** List the public surface, assign
each item to *where the arguments come from* or *how bytes get out*, and the ruling has been
overtaken by the first item that belongs to neither — a third **concern**, not a third function.
The one addition that could plausibly have been that third concern was M8's own, and it was not.
Run 2026-09-01:

```sh
grep -niE 'audio|sample|resampl|beeper|sound|device_hz|tinyaudio' crates/frontend/src/host.rs
```

It exits 1. Nothing audio-shaped is in this module: the device reaches the browser through
`crates/frontend/src/audio.rs` and `crates/page`, never through `host.rs`. Decision 9's wiring table
is therefore confirmed by reading the file rather than by being consistent with the documents around
it — which is the weaker thing three agreeing documents can be mistaken for.

**What landed is also stronger than what this decision asked for, and the difference is worth
naming.** The ruling above says the browser build is *"a different implementation of two
functions"*. It is not: both functions are the same source on both targets and **delegate** to
`crates/page`, whose implementation is the part that varies — *"Both non-portable calls now have
browser implementations, and neither of them is in this file."* That is why
`crates/frontend/tests/portability.rs` can assert this crate contains no `cfg(target` at all, which
a genuine second implementation would have made impossible.

> **The shape of this defect, which is not the *"cite the constants, not the integers"* one below.**
> There, a cited constant was right and the prose drifted away from it. Here the citation was a
> **command** — runnable by anyone, from the day it was written — and it disagreed from the day it
> was written. **A count of one thing restated as a count of another survives every check, because
> both numbers are true of something.** Two concerns and four public items were both correct on the
> day; six and two are both correct now; nothing a reader could check would fire, because the two
> quantities were never compared with each other. It is the prose form of a bare line number
> surviving a file's growth: in each case the reference resolves, returns something plausible, and
> is never held up against the claim it was offered as evidence for. The remedy is the one this
> repository already writes down for coordinates — carry an anchor and open the target once, at the
> moment of writing. **A command pasted into a document is an anchor anybody can run, and it is
> worth exactly nothing until somebody does.**

**One thing this ruling does *not* claim.** It does not claim the two targets behave identically.
Decision 2 finds a divergence that is real, is below this crate, and cannot be fixed in it. The
ruling is that there is one *source*, which is a weaker and defensible claim; *"one source"* and
*"one behaviour"* are different properties and conflating them is how a shared table acquires a
reputation it has not earned.

## Decision 2 — `Ctrl` cannot carry `SYMBOL SHIFT` in a browser, and the answer is one more alias rather than a second table — **derived; the deciding evidence is not in this repository**

This is the decision `host.rs` deferred, in those words: *"That is a real conflict with the choice
of `Ctrl` for `SYMBOL SHIFT` and it is not solved here; `preventDefault` on the canvas is the usual
answer and it is a decision to take with the milestone, not in advance of it."* It is taken here.

### First, the half of the conflict that is already solved, and it is the half `host.rs` named

`host.rs` gives two examples and the **`F5` one is already handled by the shipped bundle**. Read on
2026-09-01 from the pinned dependency's own source —
`~/.cargo/registry/src/index.crates.io-*/miniquad-0.4.11/js/gl.js`, which `macroquad`'s
`js/mq_js_bundle.js` carries in minified form:

```js
canvas.onkeydown = function (event) {
    var sapp_key_code = into_sapp_keycode(event.code);
    switch (sapp_key_code) {
        //  space, arrows - prevent scrolling of the page
        case 32: case 262: case 263: case 264: case 265:
        // F1-F10
        case 290: case 291: case 292: case 293: case 294: case 295: case 296: case 297: case 298: case 299:
        // backspace is Back on Firefox/Windows
        case 259:
        // tab - for UI
        case 258:
        // quote and slash are Quick Find on Firefox
        case 39: case 47:
            event.preventDefault();
            break;
    }
```

The same file maps `"F5"` to **294**, which is inside the `F1`–`F10` run. So `F5` does **not**
reload the page, and it was never going to: miniquad has been calling `preventDefault` on the whole
function-key row, the arrows, `Space`, `Backspace`, `Tab`, `'` and `/` since before this project
existed. Every one of those is a key `crates/frontend` binds — `F1`–`F6` as hotkeys, the arrows and
`Backspace` and `Space` as membrane keys or chords, `'` and `/` as `SYMBOL SHIFT` chords — and all
of them are covered.

> **So the deferred conflict was correctly identified and half of it had already been fixed
> upstream, which is worth naming rather than quietly benefiting from.** `host.rs` reasoned from
> what a browser does, and the answer was in a file on this machine that nobody opened. That is not
> the same defect as a wrong number; it is the cheaper one — a claim about a *dependency* treated
> as a claim about the *platform*, when the dependency is vendored, readable, and the first place
> to look. `F11` (300) and `F12` (301) are deliberately **not** in the list, so fullscreen and the
> developer tools stay with the browser, which is the right split and is another reason to believe
> the list was thought about rather than accumulated.

### What the browser genuinely takes, and it is the other example

The `Ctrl` half is real, it is worse than `host.rs` suggests, and `preventDefault` does not fix it.
Browser shortcuts fall into two classes and only one of them is a page's to refuse:

| Class | Examples (Chrome / Firefox, Windows and Linux) | Can a page cancel it? |
|---|---|---|
| Dispatched to the page first | `Ctrl+R`, `Ctrl+P`, `Ctrl+S`, `Ctrl+F`, `Ctrl+O`, `Ctrl+D`, `Ctrl+U`, `Ctrl+G` | **Yes** — `preventDefault` on `keydown` suppresses the browser action |
| Consumed by the browser chrome | `Ctrl+W`, `Ctrl+T`, `Ctrl+N`, `Ctrl+Shift+T`, `Ctrl+Tab`, **`Ctrl+1`…`Ctrl+9`**, `Ctrl+L` | **No** — the page either never sees the event or sees it and cannot stop it |

**Evidence class: derived.** That table is written from familiarity, it is browser- and
OS-specific, and the preamble's warning applies to it in full. What is *not* in doubt is that the
second class is non-empty on every desktop browser, and that is all the argument below needs.

### The chord this repository's own screenshot script types is the one the browser takes

`crates/frontend/src/bin/zx-shot.rs`'s usage example, in its own module documentation:

```sh
--keys 'P;LeftControl+P;H;E;L;L;O;LeftControl+P;Enter'
```

`LeftControl+P` is `SYMBOL SHIFT`+`P`, which is `"`. It appears **twice**, because it is how you
type `PRINT "HELLO"` on a Spectrum and there is no other way. In a browser that is `Ctrl+P`, the
print dialog. Cancellable, so a shim can save it — but the repository's own canonical example of
*using the emulator* is a chord the browser has an opinion about, which is a good measure of how
central these combinations are rather than an unlucky coincidence.

**The second class is where the argument actually turns, and it turns on the digits.**
`keymap.rs`'s founding rule deliberately leaves the shifted punctuation unbound and says what
happens instead:

> *"`SYMBOL SHIFT`+`(` is reachable, but `(` is a *shifted* key on a PC, and binding an unshifted
> host key to it would put the two keyboards' shift states into disagreement. Both are left out.
> **They remain typeable the way the hardware types them, by holding the mapped `CAPS SHIFT` or
> `SYMBOL SHIFT` and pressing the digit.**"*

On a Spectrum, `(` is `SYMBOL SHIFT`+`8` and `)` is `SYMBOL SHIFT`+`9`. In Chrome, `Ctrl+8` and
`Ctrl+9` switch browser tabs and the page does not get a say. **So the fallback the keymap
deliberately relies on for everything it does not bind is precisely the thing a browser destroys,
and it destroys it for the parentheses, which no BASIC program can avoid.** The design is not
inconvenienced at its edges; it is broken at the exact point where it chose to lean on the
hardware.

### Four ways out, and why three of them are worse

**1. Keep `Ctrl` and accept the losses.** Rejected. It is not a degradation, it is a machine on
which `PRINT`'s own argument list cannot be typed, and the failure is silent — a tab switches and
the emulator appears to have ignored a keystroke.

**2. `preventDefault` on everything the keymap claims, via a JS shim.** Rejected **as a
solution**, and adopted as a *supplement*. It is genuinely free — a capture-phase `keydown`
listener in `index.html` needs no Rust at all, no FFI and no `unsafe`, and `preventDefault` does
not stop propagation so miniquad still receives the event. But it cannot reach the second class,
and a fix that covers the cancellable chords and silently misses `Ctrl+8` is **a remedy that grades
less than it appears to** — the same shape this repository keeps catching, in product form rather
than in a test. Ship it, and do not call it the answer.

**3. Move `SYMBOL SHIFT` to `Alt`.** Rejected on a specific mechanism rather than on taste.
`Alt`+`Left` is Back in every desktop browser, the arrows are bound to `CAPS SHIFT` chords, and a
person holding `SYMBOL SHIFT` and pressing left-arrow would navigate away from the page and lose
the machine. That is a **worse** failure than a print dialog, and it is reachable by an ordinary
two-key combination. `LeftSuper`/`RightSuper` are disqualified for the same class of reason —
`Cmd+W` closes the tab on macOS and cannot be cancelled.

**4. Add a third alias for `SYMBOL SHIFT`, in the one table, on a key no browser claims.**
Adopted.

### The ruling

**`Ctrl` stays as `SYMBOL SHIFT` and `Tab` is added as a second alias for it, in `BINDINGS`, on
both targets.** One row, one table, both builds.

Four things make this the small answer rather than a compromise:

- **The mechanism already exists and is already gated.** `Binding::Alias` is in the crate today,
  for exactly this: *"A PC keyboard carries two `Shift`s and two `Ctrl`s and a person reaches for
  whichever hand is free."* Its doc comment explains that it is a separate variant so that *"the
  membrane map is a bijection"* stays a property with no exceptions to name. A third alias adds a
  row to a slice and changes no property: `tests/keymap_table.rs` already asserts the bijection over
  `Membrane` rows only, and already asserts that no host key is bound twice and no hotkey shadows a
  membrane key. ~~**The new row is covered by gates that exist, without editing them.**~~

  > **That last sentence is wrong, and it was wrong in the interesting direction.** Landed
  > 2026-09-01: adding the row turns `the_table_holds_the_three_kinds_and_nothing_else` **red**,
  > because it pins `BINDINGS.len()` against
  > `EXPECTED_MEMBRANE + EXPECTED_ALIASES + EXPECTED_CHORDS`. `tests/keymap_table.rs` had to be
  > edited: `EXPECTED_ALIASES` grows from two rows to three.
  >
  > Five of that file's tests are unaffected exactly as this paragraph predicted — the alias
  > tests iterate their own literal table, and the bijection tests filter `Alias` out by
  > construction. The prediction was made by reasoning about which tests would **pass**, and it
  > missed the one whose entire job is to notice a table it has not been told about. That test's
  > own comment says so: *"an assertion whose failure means 'I was not looking at the thing'"*.
  >
  > **The correction is not that the gate was inadequate — it is that a gate you must edit to
  > accept a change is the only kind that could have caught the change being made by accident.**
  > A design document that predicts "no test will notice" is, if it is right, describing an
  > unguarded edit. Here it was wrong, and being wrong is the good outcome.
- **It does not touch the chord rule.** `keymap.rs` is explicit that the chord rule governs which
  *chords* exist, and that which host keys carry the two shifts is *"the one genuinely free
  choice"*, settled by convention rather than by printed meaning. An alias is inside the free part
  of the design. Nothing about *"a chord exists exactly where the PC key's own printed meaning
  matches the Spectrum legend's meaning"* is weakened, and it must not be weakened, because it is
  what keeps the mapping a translation rather than an invention.
- **`Tab` specifically, and the reason is measured rather than aesthetic.** It is `into_sapp_keycode`
  **258**, which is in the `preventDefault` list quoted above with the comment `// tab - for UI`. So
  the browser's own use of it — moving focus out of the canvas, which would end the session's
  keyboard input entirely — is **already suppressed by the shipped bundle**. It is unbound in
  `BINDINGS` and unbound in `HOTKEYS`. It sits under the left little finger, next to `Q`, which is
  where a hand holding a shift for letter keys already is. And `Ctrl+Tab` remains the browser's,
  which is correct: that is a browser action, not a `SYMBOL SHIFT` combination anyone types.
- **It cannot diverge, because there is nothing to diverge from.** The native build gets the same
  row. A user who learns `Tab` in the browser keeps it on the desktop, and a user with `Ctrl` muscle
  memory from thirty years of other emulators keeps that too, on the platform where it works.

**What the ruling costs, stated plainly rather than apologised for.** `Ctrl` remains bound, so on a
browser it remains a trap for the chords in class two — a person who reaches for `Ctrl+8` still
switches tabs. The alias does not remove the sharp edge, it provides a way around it, and a person
has to know the way around exists. **That is a documentation problem with a real failure mode**, and
the status bar is where it should be answered: the shell already has a message line, and the
browser build should open with the alias named in it rather than requiring a `README` nobody
launched from a URL will read.

### The divergence that is underneath the keymap, and cannot be fixed in it

This is the finding this decision did not go looking for, and it is the more serious one.

**The two builds disagree about which `KeyCode` a key produces, and the disagreement is below
`crates/frontend`.** Read from the pinned `miniquad-0.4.11` source on 2026-09-01:

| Backend | What a `KeyCode` is derived from | Layout-dependent? |
|---|---|---|
| Browser (`js/gl.js:1215`) | `into_sapp_keycode(event.code)` | **No.** `KeyboardEvent.code` is the *physical* key, named after the US layout |
| Windows (`src/native/windows.rs:694`) | `HIWORD(lparam) as u32 & 0x1FF` — the **scan code** from the key message — through `windows/keycodes.rs:3` | **No.** `0x010 => KeyCode::Q`, `0x01E => KeyCode::A` are set-1 scan codes; the file's own comment says *"same as GLFW"* |
| macOS (`src/native/apple/apple_util.rs:154`) | `msg_send![event, keyCode]` — `NSEvent.keyCode` | **No.** A positional virtual-key code; `0x00 => KeyCode::A`, `0x0c => KeyCode::Q` |
| Linux X11 (`src/native/linux_x11/keycodes.rs:10`) | `translate_key(...)` takes a scancode, calls `XGetKeyboardMapping`, and matches on `keysyms[0]` | **Yes.** A keysym is what the current layout says the key means — `97 => KeyCode::A`, `113 => KeyCode::Q` |
| Linux Wayland (`src/native/linux_wayland/keycodes.rs`) | the scancode fed to `xkb`, then `translate_keysym` | **Yes**, and the file's own header warns the keysym is modifier-dependent |

> **This table said Windows was layout-dependent — *"on Windows a virtual-key code follows the
> active layout"* — and it is wrong.** The line it cited, `windows/keycodes.rs:3`, does take a
> `u32`, but the value handed to it at `windows.rs:694` is `HIWORD(lparam) & 0x1FF`, which is the
> **scan code** from `WM_KEYDOWN`'s `lParam` and not the virtual-key code in `wParam`. The table
> it matches on is a set-1 scan-code table. Read on 2026-09-01 from the pinned source, and macOS
> was checked at the same time because it had not been checked at all.
>
> **The correction inverts the finding rather than trimming it**, and that is why it is worth this
> box. The divergence is not *browser versus native*: it is **X11 and Wayland versus the other
> three**. Three of the five backends key off physical position, including **macOS, which is the
> desktop this project is developed on**. So the native build does not "earn" a claim the browser
> then fails to inherit — the native build on this author's own machine has the same behaviour as
> the browser, and it is Linux that differs.

**So on a French AZERTY keyboard, the physical key printed `A` reports `code: "KeyQ"` in a
browser, scan code `0x010` on Windows and `keyCode 0x0c` on macOS — all three `KeyCode::Q` — while
X11 reads keysym `97` and answers `KeyCode::A`.** One keypress, one machine, two answers. The
shared `BINDINGS` table is then correctly consulted and correctly produces two different membrane
keys.

Four things follow and each matters:

- **It is not fixable in `keymap.rs`.** The table is downstream of the divergence. Nothing this
  project writes at that layer can distinguish the two cases, because by the time a `KeyCode`
  arrives the information that would separate them is gone.
- **It is not M8's to fix.** It is a property of `miniquad` 0.4.11's backends. What M8 owes is to
  **name it**, and — now that the direction is known — to stop *any* build claiming a property
  three of the five backends do not have.
- **The rule holds on the layout-following backends and fails on the positional ones, which is
  the opposite of the obvious reading.** `keymap.rs`'s founding rule is *"the PC key's own
  **printed** meaning"*. A keysym **is** the printed meaning; `event.code`, a scan code and an
  `NSEvent.keyCode` are all *where the key is*. So on AZERTY the key printed `,` correctly types a
  comma under X11 and types the membrane `M` in a browser, on Windows and on macOS. The rule is
  honoured by the minority. For a US-layout user every backend agrees and every chord is right,
  which is exactly why nobody has noticed.
- **It is `observed`, and nobody here has observed it.** The mapping tables were read on this
  machine; a non-US keyboard was not pressed. The consequence above is **derived** from five
  tables and a `KeyCode` enum, not seen.

**This is exactly the class `STATUS.md` names — *"an argument that names real quantities, predicts
the right verdict, and identifies the wrong cause"* — caught before it was made rather than
after.** The prediction *"the browser and the native build type the same"* would have been right
for every keyboard anyone here owns and wrong for a large fraction of users, and no test in this
repository could have distinguished those two situations.

### What would decide it, and why the obvious verification is invalid

- **The `Ctrl` table:** a person, at a physical keyboard, in Chrome and in Firefox, on Windows,
  macOS and Linux, pressing each of `Ctrl`+`P`/`O`/`L`/`J`/`K`/`N`/`8`/`9` on a page that logs
  `keydown` and reports whether `preventDefault` suppressed the browser's action. The result is a
  table, it belongs in `STATUS.md`, and it converts this decision from **derived** to **measured**.
- **The layout divergence:** one person on AZERTY or QWERTZ, pressing one key, in both builds, and
  reading the status line. One keypress settles it. Nobody here can perform it.
- **What will *not* decide either:** any browser-automation tool available in this environment. A
  key injected through the DevTools Protocol reaches the page without traversing the browser's
  shortcut layer, and injecting a `KeyboardEvent` from page script sets `code` to whatever the
  script says. **Both produce a confident green for a question they did not ask**, which is the
  preamble's warning and the reason it is in the preamble.

## Decision 3 — the ROM is served beside the page, the query string becomes `argv`, and there is exactly one argument path — **ruling, with the seam that keeps it one**

`host::arguments()` returns `std::env::args().skip(1).collect()`, which on `wasm32` is empty. The
shell then falls back to `DEFAULT_ROM`, `"testdata/roms/48.rom"`, and `macroquad::file::load_file`
fetches it. Read from the shipped bundle, `fs_load_file` opens an `XMLHttpRequest` with `GET` on the
path as given, so **a relative path is resolved against the page and the existing default already
works if the directory structure is served.**

**The ruling: serve the ROM at a path beside the page, and give `host::arguments` a `wasm32` body
that turns the query string into the same `Vec<String>` the native one returns.**

```
https://example.invalid/zx/?rom=roms/48.rom&tape=games/thing.tap
```

becomes `["roms/48.rom", "games/thing.tap"]`, and `partition()` in `main.rs` is not touched. The
last `.rom` still wins, `--rom` still works for an extensionless path, and the media list is still
built by the same function with the same rules.

**Why this shape rather than a `query` module the shell consults.** A second argument source
consulted by a second code path is the divergence of Decision 1 in miniature: two ways to say
*"which ROM"*, which will eventually disagree about `--rom`, about repeats, about case. Routing the
query string into the existing `Vec<String>` means the browser and the command line **cannot**
disagree, because after one function they are the same value.

**The seam that makes it gradeable is one public function, and it is the whole reason to add one.**

```rust
/// The arguments a query string names, in the order a command line would have carried them.
#[must_use]
pub fn arguments_from_query(query: &str) -> Vec<String>;
```

Pure, no browser, no `cfg`, testable headless on any target. `arguments()` calls it on `wasm32`
with whatever the page's location supplies. **And the discriminating test is not "does it parse" —
it is that the two sources agree**, over a table of literal cases:

| Query | Must equal `partition` of |
|---|---|
| `?rom=a.rom&tape=b.tap` | `["a.rom", "b.tap"]` |
| `?rom=a.rom&rom=c.rom` | `["a.rom", "c.rom"]` — last wins, as on a command line |
| `?snapshot=x.z80` | `["x.z80"]` |
| *(empty)* | `[]` — the default ROM path, which is the URL-launched case |

That is Decision 7's T3 and it is named here because the seam exists for it.

**Reading the page's location is a third non-portable *call* and it is not a third *concern*** —
which is the distinction Decision 1's correction turns on, and this sentence used to sit on both
sides of it at once. It is another way of answering *where the arguments come from*, so it joins
that group rather than opening a new one, and the ruling is untouched by it however the query
string is obtained. Where it landed is what changed: the read is `page::query_string`, so it is not
on `host.rs`'s public surface at all, while `arguments_from_query` and `partition` — which are —
run the same code on both targets. Whether it costs `unsafe` is the subject of Decision 4, which it
shares with `save`.

## Decision 4 — bytes leave the page through a `Blob` and a synthetic `<a download>`, and the crate's own lint currently forbids the only mechanism that can do it — **derived; it needs a decision this document cannot take alone**

`host::save` calls `std::fs::write`, which on `wasm32` returns `Unsupported`, which the shell puts
on the status line. `host.rs` calls that *"a better first build than one that does not link"*, and
it is right. It is not a finished `F2`.

### The three routes, and why two of them are dead

| Route | Mechanism | Verdict |
|---|---|---|
| **A `Blob` and a synthetic `<a download>` click** | A JS function registered through `miniquad_add_plugin`, called from Rust through an `extern "C"` import; the JS reads the bytes out of `wasm_memory.buffer` given a pointer and a length | **The only one that works.** Needs `unsafe` — see below |
| **A `data:` URL opened as a navigation** | Build a `data:application/octet-stream;base64,…` and navigate to it | **Dead.** Top-level `data:` navigation is blocked by current browsers, and the string still has to leave `wasm` memory, so it does not even avoid the FFI |
| **A JS-only route with no Rust change at all** | The page's own script reaches into `wasm_exports` and pulls the snapshot out | **Dead.** It still requires an exported Rust function to hand over a pointer and a length, and in edition 2024 an export is `#[unsafe(no_mangle)] extern "C"`. The `unsafe` moves, it does not disappear |

**The mechanism the bundle already provides is `sapp_jsutils`, and it is in the shipped file.**
`macroquad`'s `js/mq_js_bundle.js` registers a plugin exposing `js_create_buffer`,
`js_unwrap_to_buf`, `js_free_object` and the rest, over `wasm_memory.buffer`. So the JS half of the
download is small and the Rust half is an `extern "C"` block. **The route is not exotic; it is the
one macroquad's own ecosystem uses.**

### `unsafe_code = "forbid"` is the blocker, and it is doing real work

`crates/frontend/Cargo.toml`:

```toml
[lints.rust]
unsafe_code = "forbid"
```

**`forbid` is not `deny`.** An `#[allow(unsafe_code)]` or `#[expect(unsafe_code)]` inside a
`forbid`den crate is a hard error, not an override. So the download cannot be written in this crate
as it stands, and this is not a style preference to argue past — it is a compile error.

Three ways out, and the choice is genuinely open:

| Option | What it costs | What it keeps |
|---|---|---|
| **A. `forbid` → `deny`, one `#[allow]`, one `// SAFETY:`** | The crate loses a *structural* guarantee and gains a *checked* one. Every future reviewer of every future module now has to notice an `#[allow]` rather than rely on the manifest | One crate, one seam, the smallest diff |
| **B. A new crate that owns the FFI** | A crate for two functions, which this project's own rules warn against | `crates/frontend` stays `forbid`-clean, and the `unsafe` is in a module small enough to read in one screen |
| **C. A dependency that contains the `unsafe`** | A fourth dependency, pinned and re-verified at every audit, for one call | `forbid` survives untouched and nothing here is written |

**This document does not choose, and says why rather than picking to look decisive.** The choice
turns on how much `unsafe_code = "forbid"` is worth to the person who set it, which is not a fact
in the repository. What *is* in the repository is the argument for taking it seriously:
`ARCHITECTURE.md` pins every dependency to a stated verification date, which prices option C
higher than it looks; and `crates/frontend/src/palette.rs` shows what this crate does with
structural guarantees — *"there is no run in which it can be false"* — which prices option A's loss
higher than it looks.

**A recommendation, so the absence of a choice is not mistaken for an absence of an opinion:
option B, with the crate named for the seam rather than for the target.** It keeps `forbid` where
`forbid` is earning something, it puts the `unsafe` in the one place a reviewer would look for it,
and the "a crate for two functions" objection is weaker here than usual because the two functions
are precisely the two `host.rs` was written to isolate. If the answer is A, the `#[allow]` belongs
on the module and not on the function, so that a second `unsafe` cannot be added without moving it.

### The ruling — **option B**, taken 2026-09-01 by the owner this document deferred to

**`unsafe_code = "forbid"` stays on `crates/frontend`, and the wasm glue moves into a small
dedicated crate of its own.** The recommendation above is adopted; what follows is the reasoning,
recorded so it is not re-litigated by whoever next finds the `forbid` inconvenient.

**`forbid` on `crates/z80` and `crates/spectrum` is load-bearing and is not negotiable.** Those
crates parse attacker-controlled files and run guest-controlled code, and this project has already
shipped **one guest-triggered process abort** — the `u8` `t_states` counter whose *"loud panic
rather than a silent wrap"* turned out to be reporting a legal instruction stream, with
`panic = "abort"` underneath it. `crates/frontend` takes the same files from the same strangers,
now including files a browser lets a stranger drop onto the page (Decision 5), so it inherits the
posture for the same reason and not by analogy.

**The trade is not "safety versus a download button", it is where the exception is legible.**
Option A buys one small diff and pays for it by converting a *structural* guarantee into a
*checked* one — after which every reviewer of every future module in this crate has to notice an
`#[allow]` rather than read the manifest. That is the trade `palette.rs` refuses in the other
direction when it prefers *"there is no run in which it can be false"* to an observation about one
run. A crate whose **entire contents** are the few `unsafe` lines needed to hand a `Blob` to the
browser, each with a `// SAFETY:` comment discharging its invariant, keeps `forbid` everywhere it
protects something and confines the exception to a surface a person can read in one sitting.

**The "a crate for two functions" objection is answered rather than waved away**, because this
project's own rules do warn against it. It is weaker here than usual for a specific reason: the
two functions are not an arbitrary pair, they are **exactly the seam `host.rs` was written to
isolate** — that module's opening sentence is *"This module is the entire `wasm32` seam"*, and it
counted the non-portable calls precisely so this question could be decided by the count. A crate
that draws its boundary around a boundary somebody else already drew is not a new abstraction.

**That sentence is left as it was argued; what has changed since is the crate, not the argument.**
`crates/page` has grown `handoff`, the `wasm32`-only `zx_page_crate_version` export and the audio
pair `audio_rate` / `audio_push`, so *"two functions"* describes it on the day it was created and
not today. The answer survives the growth for exactly the reason it was given: the audio pair
reaches the browser through `crates/frontend/src/audio.rs` rather than through `host.rs`, so it is a
second boundary somebody else had already drawn, and a crate that draws its boundary around two such
boundaries is no more a new abstraction than one that draws it around one. What does not survive is
the arithmetic. *"Two"* was the whole of the objection and the whole of the answer, and it is now a
figure in prose with nothing behind it — the defect the blockquote below records as *"cite the
constants, not the integers"*, and the reason this crate's size is asserted by `EXPECTED_BLOCKS` in
`tests/unsafe_inventory.rs` rather than counted in a sentence. **Decision 1's count is a separate
claim, and it needed a correction of its own rather than the acquittal this paragraph gave it.**
What it said — *"`host.rs` still isolates exactly `arguments` and `save`"* — is the same conflation
in a shorter sentence: those two are the **concerns**, while the module's public surface was four
items when Decision 1 was written and is six now. It is corrected there. What survives untouched,
and is the half this paragraph actually needed, is that the audio device never passed through that
module at all — checked in it directly, and the `grep` exits 1.

~~**What is not settled, and stays open:** the crate's name, and the exact `SaveError` variant it
forces.~~ ~~**The crate does not exist yet**~~ — settled and landed 2026-09-01.

> **`crates/page`**, named for the seam rather than the target, with `SaveError::Download`. Its
> entire `unsafe` surface is **five blocks, two `unsafe extern "C"` blocks and one
> `#[unsafe(no_mangle)]`** — three blocks for the argument and download seam and two for audio,

> each with a `// SAFETY:` comment. The count is asserted by `crates/page/tests/unsafe_inventory.rs`
> as `EXPECTED_BLOCKS`, `EXPECTED_EXTERN_BLOCKS` and `EXPECTED_UNSAFE_ATTRIBUTES`, so *"small
> enough to read in one sitting"* is a property rather than a hope.
>
> **Cite the constants, not the integers, and the reason is that this paragraph got it wrong.**
> It read *"three blocks, one extern block"* for as long as the browser had no audio device; the
> surface then grew to five and two, the test's constants grew with it and stayed green, and the
> prose did not. The result is the worst configuration available: **a passing guardian named as
> the authority for a number it does not hold.** A reader who checks the sentence finds a test,
> sees green, and stops — which is exactly the confidence the citation was added to earn, spent
> on a figure nothing was defending. An uncited number invites the count; a cited one forbids it.
>
> **Both halves of the inventory were mutation-proved** — removing a `SAFETY:` comment reddens
> `every_unsafe_block_is_preceded_by_a_safety_comment`, and adding a block reddens
> `the_unsafe_surface_is_the_size_it_is_documented_to_be`. **The verdicts stand and the wording
> did not survive the growth**: it said *"adding a **fourth** block"*, which was the boundary when
> the constant was three and now sits inside the pinned five, where it would redden the count in
> the opposite direction — one too few rather than one too many. The mutation is real and the
> record of it is not reproducible as it was written; it wants re-taking against `EXPECTED_BLOCKS`
> as it now stands, and until somebody does that, this is a described mutation rather than a
> measured one.
>
> **Two things the build taught that this decision could not have known**, both in the class the
> preamble warns about — a claim about the platform that was really a claim about the dependency:
>
> - **`#[link(wasm_import_module = "env")]` is required.** Without it `rust-lld` does not make
>   the declarations wasm imports at all: `undefined symbol: zx_query_length`, and the build
>   fails. `miniquad-0.4.11` carries the same attribute over both of its own extern blocks
>   (`src/native/wasm/fs.rs:1`, `src/native/wasm/webgl.rs:316`) — the answer was in the pinned
>   source, again. **This failure is the loud kind**, which is worth recording next to rule 3
>   below: a missing import *module* is a link error, while a missing import *function* is a
>   silent stub. Only one of the two hazards on this route can be shipped.
> - **`cargo clippy` on a desktop host lints none of the `unsafe` blocks**, because they are
>   behind `#[cfg(target_arch = "wasm32")]` and a lint fires only on code the current target
>   compiles. So `clippy::undocumented_unsafe_blocks`, set to deny in that crate precisely to
>   make the `SAFETY:` convention a compile error, is **silent on the machine anyone will run it

>   looks at rather than by trusting a deny-level lint to deny. Two mitigations, failing
>   differently on purpose: `web/gate.sh` runs clippy with `--target wasm32-unknown-unknown`

> table makes the **root** unresolvable, which was measured in a scratch tree rather than guessed
> at, and it costs the whole workspace's test run.

**Whichever is chosen, three rules hold and they are not negotiable:**

1. **A `// SAFETY:` comment that discharges the invariant**, per pointer and length, naming what
   makes the slice valid for the duration of the call.
2. **The JS side is vendored and hashed** — Decision 6.
3. **A missing JS import does not fail.** `gl.js`'s `add_missing_functions_stabs` replaces any
   import the JS does not provide with a stub that logs a warning to the console. So **a download
   whose shim was not deployed produces a page where `F2` reports success and nothing is saved.**
   That is a gate that grades less than it appears to, in the product, and the mitigation is that
   the Rust side must not report `saved …` on the strength of having made the call — the JS must
   return a value the Rust side checks.

### What `free_path` becomes

`free_path` probes `snapshot-1.z80`, `snapshot-2.z80` … for the first that does not exist, because
*"clobbering the previous save is the more expensive mistake by a wide margin"*. On `wasm32`
`Path::exists()` has no filesystem to consult and returns `false`, so **the first candidate always
wins and every save is offered as `snapshot-1.z80`.**

That is the right outcome by accident, and it should be made deliberate:

- **The stated reason survives.** Nothing is clobbered. The browser resolves the collision, in the
  download directory, by appending its own counter.
- **The mechanism does not.** The loop runs a thousand `exists()` calls that can only answer
  `false`. `host.rs` already predicts this — *"`free_path`'s collision probing has no meaning there
  and would be dropped in favour of a fixed suggested filename"* — and it is right.
- **So `save` on `wasm32` takes the name as a *suggestion*, not a path**, and `SaveError::NoFreeName`
  becomes unreachable on that target. Unreachable, not impossible: it stays, because it is reachable
  natively and `SaveError` is `#[non_exhaustive]` so nothing about the type needs to move.

## Decision 5 — a user's own file arrives by drag-and-drop, which already works on both targets — **measured, in the shipped bundle**

A person with a `.tap` on their disk needs it in the page. The answer costs almost nothing, because
it is already built.

**`gl.js` implements the drop handler.** Read on 2026-09-01:

```js
window.ondragover = function (e) { e.preventDefault(); };
window.ondrop = async function (e) {
    e.preventDefault();
    wasm_exports.on_files_dropped_start();
    for (let file of e.dataTransfer.files) { /* name, then await file.arrayBuffer() */ }
    wasm_exports.on_files_dropped_finish();
};
```

**And macroquad exposes it.** `macroquad::input::get_dropped_files() -> Vec<DroppedFile>`, where
`DroppedFile { path: Option<PathBuf>, bytes: Option<Vec<u8>> }`, implemented over
`miniquad::window::dropped_file_count` / `_path` / `_bytes`. The native backends fill both fields;
in a browser the `path` is the file's *name*, which is all `media::kind_of` needs.

**So the whole feature is one call in the frame loop and one existing function:**

```rust
for file in get_dropped_files() {
    // kind_of on the name, media::insert on the bytes — the same two functions
    // the command line already routes through.
}
```

`media::kind_of` takes a `&str` and looks at the extension. `media::insert` takes bytes somebody
else fetched — the module's own documentation says so: *"Nothing in this module performs I/O; every
entry point takes bytes that somebody else fetched."* **The design anticipated this without being
told to**, and drag-and-drop is the case that proves it, because it is a byte source that is
neither a command line nor an HTTP fetch.

**This is `Kind::Rom`'s first genuinely reachable failure.** `media::Error::RomAfterStart` exists
and is documented as reachable from `zx --rom a.rom b.rom`. Dropping a `.rom` onto a running page
is the second route, it is far more likely, and the existing error is already the right one:
*"A ROM is what the machine is made of; swapping it means building a different machine, which is
what starting the emulator again does."* In a browser, "starting the emulator again" is reloading
the page, which is a thing a person can actually do.

### The file input, and what it would cost

A `<input type="file">` is the accessible route — it works with a keyboard, it works on a phone,
and it is what a person looks for when drag-and-drop does not occur to them. It is also **not
free**: the element lives in the DOM outside the canvas, its `change` event is JS, and getting the
bytes to Rust is the same FFI problem as Decision 4 in the opposite direction.

**Ruling: drag-and-drop at M8; the file input is named, not built.** It is one route to the same
`media::insert` call, and it should not be built before Decision 4's `unsafe` question is settled,
because it would be the second consumer of an FFI mechanism that does not yet exist. If Decision 4
lands as option B, the file input costs one more function in that crate and is worth adding
immediately after.

### What the browser will and will not permit

| | |
|---|---|
| Read a file the user **drops** | **Yes**, and it needs no permission prompt — the drop is the user's gesture |
| Read a file the user **picks** from `<input type="file">` | **Yes**, same reason |
| Read a file by **path** | **No.** There is no path. `DroppedFile::path` in a browser is a name, and a name is not a location |
| Read a directory, or re-read a file later | **No**, not without the File System Access API, a permission prompt, and a browser that has it |
| **Write** a file to a path | **No.** Decision 4 — a download is an offer, and the user's download directory is not addressable |
| Fetch `48.rom` from `file://` | **No.** `fs_load_file` is an `XHR`; opening `index.html` from disk fails on cross-origin rules. **The page must be served over HTTP**, which is why Decision 8 has a local-server line in it even though deployment is out of scope |

## Decision 6 — `index.html` and the JS bundle are vendored from the pinned crate and recorded like a corpus — **ruling**

macroquad's own `README.md` gives an `index.html` whose script tag is:

```html
<script src="https://not-fl3.github.io/miniquad-samples/mq_js_bundle.js"></script>
```

**That is a third-party CDN in the trust path of a page that runs a ROM, and it is refused.** Three
reasons, in descending order:

1. **It is a supply chain.** The page executes whatever that host serves, forever, with no pin.
2. **It cannot be version-matched.** The bundle and the crate must agree; a URL cannot be pinned to
   the `miniquad` version in `Cargo.lock`.
3. **It makes the page depend on a host being up**, which is a strange property for an emulator
   whose entire dependency set is otherwise vendored and hashed.

**Ruling: `mq_js_bundle.js` is copied out of the pinned `macroquad` crate source, committed beside
`index.html`, and recorded with its size, SHA-256, the crate version it came from and the date it
was taken** — in the shape `testdata/README.md` already uses for every corpus, because it is the
same kind of artefact: bytes from outside this project whose provenance is the whole point.

```sh
# The source is the pinned dependency, not the internet.
shasum -a 256 "$(ls -d ~/.cargo/registry/src/*/macroquad-0.4.16)/js/mq_js_bundle.js"
```

**`index.html` needs exactly one thing from macroquad's template and it is easy to get wrong:**
`gl.js` selects `document.querySelector("#glcanvas")`. The canvas id is not configurable. The
template's `tabindex='1'` is not decoration either — miniquad binds `canvas.onkeydown`, not
`window.onkeydown`, so **the canvas must be focusable and focused or no key reaches the emulator at
all.** A fresh page load does not focus it; the user clicks first. `window.ondrop` is on the
window, so dropping a file works whether or not the canvas has focus — an asymmetry worth knowing
before someone reports that the keyboard is dead.

### The version check is a `console.error`, which is the failure mode to design against

`gl.js` carries `const version = 2` and compares it against the wasm module's `crate_version()`; the
plugin loader compares each plugin's declared version against `wasm_exports[name + "_crate_version"]()`.
**Both mismatches are `console.error` and neither stops the page.** So a bundle from a different
miniquad produces an emulator that starts, draws, and misbehaves somewhere, with the explanation in
a console nobody has open.

**That is why the hash is the gate and the version check is not.** A recorded SHA-256, compared in
CI against the file in the pinned crate's source, fails loudly at build time. The runtime check
fails quietly at the only moment it cannot help.

## Decision 7 — the gate, and the part of this milestone no test can reach — **the most important decision in this document**

`MACHINE.md` says **playable from a URL**. M6's row said *"a real game runs"* and M6 corrected it;
M7's said *"128-only software runs"* and M7 corrected it in advance. **M8's row needs the same
correction and for a stronger reason than either**, so it is made here in the open rather than by
quietly narrowing what the row meant.

**The difference from M6 and M7 is not one of degree.** M6's *"a real game runs"* was
unautomatable because the corpus could not be committed — a licensing accident, which a different
repository could fix. M7's was unautomatable for the same reason. **M8's gate cannot include
"playable" because *playable* is not a property of an artefact.** It is a property of a browser
rendering a canvas, a GPU compositing it, a keyboard delivering keys, and a person forming an
opinion. No corpus, no licence and no amount of engineering makes that automatable, and a document
that implies otherwise is setting up the next reader to write a gate that grades the build and
reports on the experience.

### What is automatable, precisely

| Claim | How | Class |

## Decision 8 — deployment is out of scope — **ruling (YAGNI)**

"Playable from a URL" implies a URL, and a URL implies a host. M8 does not acquire one.

**What M8 is responsible for:** a directory that is a working page. `index.html`, the vendored
bundle, `zx.wasm`, and `48.rom` at the path the default names. Anything that can serve static files
over HTTP serves it, and that is the whole contract.

**What M8 is not responsible for:** a domain, a CI deployment job, a hosting provider, a cache
policy, a CDN, an analytics tag, or a `Cross-Origin-Opener-Policy` header. None is needed to satisfy
the milestone and every one is a decision with an owner who is not this document.

**One line belongs in `README.md` and nothing else does**, because Decision 5 established that
`file://` will not work and a person who tries it will conclude the build is broken:

```sh
cargo install basic-http-server && basic-http-server .
```

**What would change this ruling:** somebody wanting the page to be at an address. That is a request,
not a design question, and it is cheap to satisfy afterwards precisely because M8 produces a static
directory and nothing else. Building a deployment pipeline first, in the hope of that request,
would be scaffolding — and `M6.md` refused `.szx` and `M7.md` refused a `Model` accessor on exactly
this reasoning.

## Decision 9 — sound is not in this milestone, and three documents say it should be — **ruling, and it contradicts `M6.md`, `M7.md` and `MACHINE.md`'s own row**

**State the disagreement first, because the ruling is only defensible if the disagreement is
visible.** Four places assign audio to M8:

| Where | What it says |
|---|---|
| `M6.md`'s *What M6 deliberately does not do* | a row reading **Sound** — the speaker bit of a `0xFE` write — against **M8** |
| `M7.md` Decision 6 | *"the audio **device**, the mixing of beeper and AY, and the resampling to a host rate are all frontend concerns and belong in the milestone that owns the frontend"* |
| `M7.md` Decision 10 (scope) | a row reading **The beeper** — **out**, M8, per `M6.md` |
| `M7.md`'s *Deliberately absent* | `Ay::sample_rate` / any resampling — *"M8 owns the audio device"* |

**Ruling: M8 is the browser build, and audio is not in it.** Three reasons, and the first is
decisive on its own:

1. **The AY does not exist.** `ls crates/spectrum/src/` on 2026-09-01 lists `keyboard.rs`,
   `lib.rs`, `memory.rs`, `model.rs`, `screen.rs`, `snapshot/`, `tape/`, `timing.rs`, `ula.rs` —
   and no `ay.rs`. M7 is in flight. A milestone whose scope includes mixing two sources cannot be
   designed while one of them is unwritten, and `M7.md` Decision 6 has already imposed a design

2. **The beeper is not in the machine either.** `crates/spectrum/src/ula.rs:528` reads

   simpler half is a `crates/spectrum` change, not a `crates/frontend` one, and this document is a
   design for `crates/frontend`.
3. **Bundling them makes one milestone that cannot be finished.** The browser build is finishable
   this week and its value does not depend on sound. Audio depends on M7 landing and on a design
   nobody has written. Tying them means the browser build waits for the AY.

**So the honest statement is that M8 as designed here is *half* of what those four rows describe,

- **Split the row.** M8 is the browser; M9 is sound. The rows in `M6.md`, `M7.md`, `MACHINE.md`,

**The second is cheaper and is what the milestone tables already imply**, so it is the

because a reader arriving at `M7.md` Decision 6 and then at `M8.md` finds one saying M8 owns the

describes in its symmetrical form — *"a reader checking two sources would have found them agreeing
that the other was stale, which reads exactly like corroboration."*

### The ruling — **neither of the two**, taken 2026-09-01, and the rows are corrected

**Sound belongs to M7. The AY is a 128 device and the beeper is a ULA feature, so both are the
machine's, and `crates/spectrum` is where the machine is modelled. M8's job is to route audio the
machine already produces to a browser's audio device.**

This document offered *split the row* or *finish M8 in two halves*, and both share a premise the
ruling rejects: that "sound" is one indivisible lump that must sit in one milestone. It is not.
There are two questions in it and they have different owners:

| Question | Whose | Why |

| What does the hardware emit? | **M7** — `crates/spectrum` | The beeper is bit 4 of a `0xFE` write, decoded by the same `Ula::out_port` that already takes the border out of bits 0–2 of the same byte. The AY is a 128 chip. Neither becomes a frontend concern by being audible |
| How does that reach a speaker? | **M8** — `crates/frontend` | The device, the mix of the two sources, the resampling to a host rate. `M7.md` Decision 6 already said this half was the frontend's and it was right about this half |

- **Decision 9's first two reasons are answered rather than deferred.** *"The AY does not exist"*

- **The third reason survives intact and is now free.** *"Bundling them makes one milestone that

- **`M7.md` Decision 6's constraint gets easier.** It requires the AY's frame hash to cover *"the

### How to build so that sound is a change and not a rewrite

Three properties, and all three are free if they are decided now:

- **The frame loop already has the right shape.** `pacer.advance(elapsed)` returns whole frames and
  the loop runs exactly that many. Audio needs samples per frame at a fixed rate, which is the same
  quantity in different units. **Nothing about the pacing needs to change**, and that is worth
  stating because the tempting alternative — driving the frame loop from an audio callback, which
  is what a latency-sensitive emulator eventually does — **would** be a rewrite. It is not needed
  and it should not be pre-built.
- **`Video` is the model for `Audio`.** Buffers allocated once, filled in place, handed to the
  device. `main.rs` already says why: *"a texture rebuilt 50 times a second is a GPU allocation 50
  times a second, and that is a leak-shaped mistake rather than a slow one."* The same sentence
  will be true of a sample buffer.
- **The source is `crates/spectrum`, and the mix is `crates/frontend`'s.** `M7.md` Decision 6
  requires that the AY's hash cover *"the AY's own output, not 'the machine's audio'"*, precisely so
  that adding the beeper does not falsify an M7 gate. That constraint is a constraint on **this**
  crate: whatever mixes them must live here, downstream of both, and must not be pushed into
  `spectrum` for convenience.

### Mobile and touch

**Out, and the reason is the machine rather than the effort.** A Spectrum is a forty-key membrane
on which the useful characters are *two-key combinations*. An on-screen keyboard that can express
`SYMBOL SHIFT`+`P` needs a shift-state model, which is a stateful input mode, which is a second
input path — and Decision 1 exists to say what a second input path costs.

Three things follow:

- **Nothing in M8 should prevent it.** `keymap::apply` takes `impl FnMut(KeyCode) -> bool`, a seam
  that already exists and is already used by `zx-shot` to drive the machine from a script. A touch
  keyboard is another implementation of that closure. **The seam is the whole preparation and it is
  already there.**
- **`viewport::fit` already handles a portrait window** — it floors the scale on the limiting axis
  and centres — so a phone shows the whole screen, small, with the border filling the rest. That is
  the correct behaviour and it was not designed for phones.
- **What it would need, so the next person does not re-derive it:** an on-screen keyboard with a
  sticky-shift model, and a decision about whether the emulator's `CAPS SHIFT`/`SYMBOL SHIFT` are
  sticky *on the touch keyboard only* or everywhere. The second would change the native build's
  behaviour and is the trap.

## Decision 10 — a standalone build embeds its media, and the payload is never committed — **ruling, taken 2026-09-01 on the owner's request**

One artefact that boots straight into a game: no arguments, no files to find. It is the **third**
answer to the question Decision 3 was already answering, and it must not fork the path.

| Source | Names arrive by | Bytes arrive by |
|---|---|---|
| a command line | `std::env::args` | the filesystem |
| a URL | `host::arguments_from_query` | an HTTP fetch |
| **a bundled build** | **`bundle::arguments`** | **`include_bytes!`** |
| a file dropped on the window | `get_dropped_files` | the drop event |

**All four end at the same `host::partition` and the same `media::accept`, and none of them is
told which it is.** `crates/frontend/tests/byte_sources.rs` asserts that as machine state — four
routes, one snapshot, compared byte for byte, with a fifth machine that was never fed the payload
as the assertion whose failure means *"I was not looking at the thing"*.

### The licensing constraint is what shapes the design

`testdata/README.md` records that this repository redistributes **nothing** except the Sinclair
ROMs, on a permission quoted there with its author and date. **A game is covered by nothing**, so
a binary with one compiled in is a redistribution nobody here is entitled to make.

So the *mechanism* is committed and gated, and the *payload* never is:

- A `bundled` Cargo feature, **off by default**, whose payload comes from `ZX_BUNDLE_ROM` and
  `ZX_BUNDLE_MEDIA`.
- `build.rs` **fails the build** — not the run — when the feature is on and there is nothing to
  embed, when the file is missing or empty, or when it is a format this emulator cannot load. A
  standalone that starts and shows nothing is the outcome the check exists to prevent, and each
  of the three refusals has a failing case in `crates/frontend/gate-bundled.sh`.
- The default build neither needs the payload nor looks for it, and
  `tests/byte_sources.rs` asserts that an ordinary build embeds **nothing** — because a default
  build that quietly carried a game is the licensing failure itself.

### Why a build script rather than `include_bytes!(env!(…))`

The one-liner works and gets one thing wrong: nothing tells `cargo` to rebuild when the variable
changes, so re-pointing it at a different game can produce a binary containing the **previous**
one. A stale payload is exactly the failure this mechanism exists to avoid. `rerun-if-env-changed`
and `rerun-if-changed` can only be emitted from a build script.

### Where the acknowledgement goes, and why it is not `--about`

Decision 3 put the Amstrad notice in `index.html` because **for a URL-launched emulator the page
is both the program and the manual**. A standalone binary is the same question with the same
answer and a different surface: there is no README on the path between a double-clicked artefact
and its user, so **the window is both**, and the notice is a permanent line under the picture
that `F1` does not hide. A `--about` flag is the case `Status::new` already rejects in its own
words — *"a readout somebody has to know to switch on is the silent case with extra steps."*
`zx-shot` has no picture, so it prints it.

**It is shown only when the embedded ROM is actually Sinclair's**, decided by looking: all three
committed ROMs contain the bytes `Sinclair` (`LC_ALL=C grep -qa Sinclair testdata/roms/*.rom`,
run 2026-09-01). Printing Amstrad's notice over a ROM they did not write would be a false
statement in the one place this repository is most careful not to make one — and the gate's own
synthetic ROM is exactly such a ROM, so the case is not hypothetical.

### The gate is the mechanism, and it needs no corpus

`crates/frontend/gate-bundled.sh` generates its own payload: a 16 KB ROM assembled from six Z80
instructions that fill the screen and halt, and a `.z80` the emulator writes of itself. It then
asserts that a bundled `zx-shot` with **no arguments at all** photographs the same image as an
ordinary `zx-shot` handed the same ROM by name — and, as the control, that a *different* ROM
photographs differently, so the comparison is capable of failing. No game is involved and none
could be.

## Decision 11 — a dropped file is the fourth source and the only one that is the same on both targets — **ruling**

Decision 5 built drag-and-drop and named a file input as *"named, not built"*. That still holds
and the reasons have got stronger, so they are recorded rather than re-argued:

**A file picker is refused.** `rfd` or an equivalent is a **new dependency**, pinned and
re-verified at every audit, for one call; it does not exist in a browser, where the route is
`<input type="file">` and therefore a *second* implementation and a second consumer of
`crates/page`; and drag-and-drop is one call that already works on both targets. **What that
costs, stated plainly:** the only way to load a file is a mouse gesture. It is not
keyboard-reachable and not reachable on a phone, and that belongs in the ungraded table rather
than in a footnote.

**The verbs differ by kind and the message names which was applied.** A tape is *inserted* and
the machine keeps running; a snapshot *replaces the state*; a ROM is refused. All three go
through the one `media::insert` dispatch. The tape is the case that must not be silent: it is
inserted **stopped**, deliberately, so the visible effect of dropping one is *nothing at all*
until `F3` — and a drop that appears to do nothing is indistinguishable from a broken build.

**A model mismatch is where the library's correct answer and the frontend's genuinely differ,
and neither is a bug.** `Spectrum::restore` refuses a 128 snapshot on a 48K, which is right for a
library: silently dropping five banks is the defect `M6.md` refused for duplicate pages. The
frontend's ideal answer is the opposite — build the machine the snapshot describes, since the
snapshot carries its own model — and **it is not reachable**: constructing a 128 needs two ROM
images the process may never have been given, and reusing the 48K ROM or guessing which of two is
the editor would be inventing a machine and calling it the user's. So the refusal stands and the
message names the one thing that would fix it. **If ROM images are ever available to the shell at
that moment, this decision should be revisited**, and that is the condition, not a preference.

**`.tzx` is refused by name, in a table, so that support is a deletion.** `.tap` cannot represent
a turbo loader at any speed and most commercial games ship as `.tzx`, so it is the likeliest thing
to be dropped here — and *"not a .rom, .tap, .z80 or .sna"* reads as a broken emulator rather than
an unfinished one. `media::NOT_YET` names it. **`M6.md` Decision 5's choice of a pulse train over
a block list is what makes the fix small**: `crates/spectrum` is gaining `tape::tzx::parse`
producing the same `Tape` that `tap::parse` produces, and supporting it is a row in `EXTENSIONS`,
an arm in `insert`, and **deleting the refusal row** — plus one entry in `build.rs`'s `LOADABLE`,
which is the second place and is named here so it is not missed. My view, asked for: `.tzx` was
right to defer under YAGNI and is right to do now, because the deferral's premise (*nobody has a
turbo tape*) stopped being true the moment somebody wanted to play a real game.

## Decision 12 — macroquad cannot stream generated samples, and the producer must not resample — **measured in the pinned dependency; the device is not built**

The question asked was whether `macroquad`'s own audio can carry a buffer of samples the machine
generates each frame. **It cannot**, and this is read rather than recalled.

**`macroquad-0.4.16/src/audio.rs`, in full, exposes:** `load_sound(path)`,
`load_sound_from_bytes(data)` — *"Attempts to automatically detect the format of the source of
data"*, i.e. an **encoded file** — `play_sound`, `play_sound_once`, `stop_sound`,
`set_sound_volume`, and `PlaySoundParams { looped, volume }`. Grepping that file for `f32`,
`sample`, `frames`, `pcm` matches **nothing**. There is no entry point that accepts samples.

**The wasm backend says the same thing from the other side.** The vendored
`web/mq_js_bundle.js` registers `audio_init`, `audio_add_buffer`, `audio_play_buffer`,
`audio_source_*` and `audio_playback_*` — and `audio_add_buffer` is:

```js
function r(t, s) { let a = wasm_memory.buffer.slice(t, t + s), i = o; o += 1;
    e.decodeAudioData(a, function (e) { n.set(i, e) }, …); return i }
```

`decodeAudioData` — an **encoded file**, again. No `getChannelData`, no `AudioBuffer` built from
samples, no `ScriptProcessor`, no `AudioWorklet`, no scheduling. And `audio` is **not a default
feature**: `quad-snd` appears **zero times** in this workspace's `Cargo.lock`, so today the
workspace links no audio backend at all and any route is a dependency decision.

### The three routes, with their costs

| Route | What it costs | Verdict |
|---|---|---|
| **A. macroquad's `audio` feature, synthesising a WAV per chunk** | The one thing it accepts is an encoded file, and WAV is trivial to build. But `decodeAudioData` is **asynchronous** — macroquad's own code awaits `is_loaded()` across frames — and there is no way to schedule chunk *N+1* to begin exactly where chunk *N* ended. **Gaps are structural, not a tuning problem**, and it allocates and deletes a decoded buffer fifty times a second | Rejected. It would make a noise; it would not make the tune |
| **B. A dedicated crate (`cpal`, `tinyaudio`, `rodio`)** | `cpal` is the right *shape* — a device callback draining a ring buffer — and a large tree (`coreaudio-sys`, `alsa`, `windows-sys`) against a workspace with four direct dependencies. Its wasm backend needs **`wasm-bindgen`**, which miniquad's bundle-based loading deliberately does without; mixing them is an integration risk, not a preference. `tinyaudio` is far smaller and has no wasm at all | Native only, and it needs the owner's approval on the dependency ledger |
| **C. The device written here, per target, in `crates/page`** | On `wasm32` an `AudioWorklet` pulling from a ring buffer in wasm memory is another `miniquad_add_plugin` — no new dependency, no `wasm-bindgen`, and it is the crate that already owns the FFI and the `unsafe`. It is real JavaScript to write and to gate. It does **not** answer the native side | The right answer for the browser |

**Recommendation: C for the browser, B for the desktop, and the split is honest rather than
untidy** — the constraint genuinely differs by target, which is the same reason drag-and-drop was
the right answer for *loading* and a file picker was not.

### What the consumer needs from the producer, which is the part that had to be settled now

`crates/spectrum`'s in-flight API already has three of the four right, read on 2026-09-01:

- **`Spectrum::take_samples(&mut self) -> &[Sample]`** — a borrow into a machine-owned buffer,
  drained per frame. Correct: a `Vec` returned per frame is fifty allocations a second, which is
  the *"leak-shaped mistake rather than a slow one"* `main.rs` already refuses for the texture.
- **`SAMPLE_PERIOD_T_STATES = 32`** — one sample every 32 T-states, so **109,375 Hz**, a rate
  defined by the machine and not by a device. This is the load-bearing one and it is right.
- **`SAMPLE_CAPACITY`**, sized to the longest frame. Correct: the buffer cannot be a function of
  what a device asked for.

**The fourth is a constraint on both sides and it is this: resampling belongs in
`crates/frontend`, never in `crates/spectrum`.** `M7.md` Decision 6 requires the AY's frame hash
to cover *"the AY's own output, not 'the machine's audio'"* so that adding the beeper cannot
falsify an M7 gate. A producer that resampled to a host rate would make its own output a function
of the device it happened to run on — and the gate would then move with the machine it ran on,
which is the same defect one level up. So the machine emits at 109,375 Hz and the frontend
decimates to 44,100 or 48,000. Neither is an integer ratio, so a box filter with a fractional
accumulator is the floor, not nearest-neighbour.

### What happens when the emulator cannot keep 50 Hz, which is now audible

`Pacer` already runs at most `MAX_CATCH_UP` frames and **counts the rest as lost** rather than
carrying them, and the status bar turns red when it does. Audio is what makes that count audible:
a dropped frame is 20 ms of samples that were never generated, and a ring that starves clicks.
The honest design is a ring of three or four frames — 60–80 ms — so that a single dropped frame
is absorbed, and `Pacer::dropped()` remains the thing that says it happened. **Do not paper over
it in the audio path**: a resampler that stretches to hide an underrun turns a visible, counted
failure into an inaudible-but-wrong one, which is the trade this project refuses everywhere else.

### It is wired, and here is what that does and does not mean

~~**Nothing is wired.**~~ Landed 2026-09-01, both targets.

| Piece | Where | Note |
|---|---|---|
| Mix and resample | `crates/frontend/src/audio.rs` | Pure, `cfg`-free, gated |
| Browser device | `web/zx_audio_worklet.js` + `crates/page` | An `AudioWorklet` fed by `postMessage` |
| Desktop device | `crates/page`, `tinyaudio 1.1.0` | Target-gated in the manifest, so `wasm32` never resolves it |

**Three things the implementation settled that this decision could not.**

- **`SharedArrayBuffer` is unavailable, so the worklet is fed by `postMessage`.** The obvious
  design — a ring buffer in wasm memory the audio thread reads directly — needs
  `Cross-Origin-Opener-Policy` and `Cross-Origin-Embedder-Policy` headers, and **Decision 8 rules
  headers out of scope** on the grounds that *"anything that can serve static files over HTTP
  serves it, and that is the whole contract."* A design needing two response headers would have
  quietly broken that contract. The cost is one copy of ~960 floats per frame.
- **The mix ratio stopped being a guess.** It was a plain sum divided by four, with a paragraph
  explaining that the code *declined* to claim the beeper and an AY channel were equally loud.
  The 128's own board answers it: the beeper and the AY reach the MC1376 through **R112 = 6K8**
  and **R132 = 18K**, and contribution goes as `1/R`, so the beeper is **2.65×** the AY. That is
  now the implemented weight and `tests/audio_resampling.rs` asserts it against the resistances
  rather than against the implementation.
- **The backlog needed a ceiling and the browser did not have one.** Observed in a real browser:
  `snd 10080` after four minutes — 210 ms of latency, still climbing, because the emulator ran at
  50.2 Hz against a device consuming exactly one second per second. The cap now lives in
  `main.rs` on the depth the device returns, so both targets share one number. Re-measured after:
  `snd 293`.

### What it still does not mean

**Nobody has heard it.** This environment has no audio device and no way to capture one.
*"Samples reached a buffer"* is not *"a person heard the tune"*, and that distinction is the same
one that makes M8's gate a build gate. What exists instead, and it is worth more than a green
suite:

- **An end-to-end gate with an oracle from outside this repository.** `BEEP 1,0` is middle C by
  the Sinclair BASIC manual. `tests/audio_from_the_machine.rs` types it through the real keymap,
  drains the real samples, mixes and resamples them, and measures the pitch — with an idle
  machine asserted **silent** as the control, so a tone measured from noise cannot pass.
- **A waveform on disk**, 48 kHz 16-bit mono, written by the same path.
- **A finding the oracle produced, and it was about the ruler rather than the machine.** The gate
  first read 246.65 Hz — 5.7 % flat, very nearly exactly a semitone — and the natural reading was
  a T-state defect in the beeper's loop, because `BEEP` derives its period from one. There was no
  defect. The probe took its crossing *count* from the crossings and its *duration* from the
  amplitude envelope, and the resampler's DC blocker rings down for 34 ms after the note stops:
  1653 samples carrying no crossings, divided in as though they were period. Measured from the
  crossing spacing alone, the same buffer carries **261.71 Hz** against the manual's 261.63 —
  **0.03 %**, a two-hundredth of a semitone, inside what the beeper's T-state quantisation allows
  and agreeing with the ROM's own arithmetic (`HL = 1642` ⇒ 261.69 Hz). The gate now grades at
  0.2 % where it allowed 10 %, and the rule the episode paid for is **suspect the measurement
  before the machine**.

## Decision 13 — the arrow keys are a choice, and the choice is on the screen — **ruling, from the games**

**The Spectrum has no arrow keys.** Nothing on the membrane means *move left*, so the founding
rule — *a chord exists where the PC key's printed meaning matches the legend's* — has nothing to
match, and games do not agree. Six of the owner's own games were **disassembled** on 2026-09-01
rather than read from their instruction text, and the text turned out to be misleading:

| Game | What its code reads | Basis |
|---|---|---|
| **Manic Miner** | Left `Q E T U O`, right `W R Y I P` — **interleaved**, not two halves — plus bare `5`/`8`, `7`/`0` for jump, the whole bottom row for jump, and Kempston when detected | Decoded at `0x8BFB`–`0x8C7F`, identical across five images |
| **Cybernoid II** | `O` `P` `Q` `SPACE`, redefinable | Four decoded slots at `0x2181`–`0x219F` |
| **Cybernoid I** | Same engine; this snapshot's slots all read `6` | Decoded |
| **Exolon** | Redefinable; one default readable, `O` | Decoded at `0x2056` |
| **Mario Bros** | **Nothing fixed** — scans all eight half-rows into a buffer | Decoded at `0xB79F` |
| **Batty** | Nothing readable; body is compressed, 7.97 bits/byte | Measured |

**Three of the six read no fixed keys at all**, which settles it: there is no single mapping to
find. So the arrows are a **scheme**, `F7` cycles it, and the current one is on the status bar and
in `index.html` — because a person who presses an arrow and sees nothing move concludes the
emulator is broken, which is the same class as a drop that does nothing.

**The hazard the disassembly found, which a plausible design would have shipped.** Manic Miner's
jump check is `LD BC,7EFEh : IN A,(C)`, and `B = 0x7E` pulls A8 and A15 low **together** — so the
read merges the row containing `CAPS SHIFT`. Binding the arrows to the machine's real cursor keys
(`CAPS SHIFT` + `5`) would therefore make Willy **jump continuously while walking left**. Hence
two separate schemes: `cursor` (the chord, correct for BASIC) and `5678` (the bare digits, correct
for games). `tests/keymap_under_a_game.rs` asserts both against that literal port.

**It is still one table and one path.** `apply_with` is the only function that presses anything,
`BINDINGS` still holds every non-arrow row, and a scheme replaces what four host keys do and
nothing else. Both targets run it.

**Kempston is in the cycle and is the cleanest of the six**, because it is a port rather than the
membrane: a game reading the joystick cannot be confused by a keypress and vice versa. It is
**last** rather than first, because it reaches nothing on a game that does not read it, and a
person cycling should meet the answers that can visibly do something before the one that can be
silently inert. `apply_with` **returns** a freshly built `Joystick` rather than mutating one —
partly because `Spectrum` hands out `keyboard_mut` and `joystick_mut` separately and two `&mut`
borrows would not compile, and partly because Kempston is **active high with no interlock**, so
*rebuilt from the host every frame* is exactly the property needed and exactly what a returned
value is.

## Implementation order

Each step is independently reviewable and each has a gate that goes red without the next.

1. **`arguments_from_query`, and the agreement table.** Pure, headless, no browser, no `unsafe`. It
   is the whole of T3's first half and it lands before anything target-specific.
2. **The `Tab` alias.** One row in `BINDINGS`. `tests/keymap_table.rs` covers it as it stands;
   `main.rs`'s key table and `lib.rs`'s documentation need the row.
3. **`index.html` and the vendored bundle**, with the SHA-256 recorded, the acknowledgement in the
   page, and the canvas id and `tabindex` from macroquad's template. At this point the page runs
   and boots, with no download and no drag-and-drop.
4. **`get_dropped_files` in the frame loop.** Works on both targets immediately, needs no FFI, and
   is the first genuinely new capability.
5. **`DEFAULT_ROM`'s failure message**, which says *"on the command line"* and should name the query
   parameter.
6. **The `unsafe` decision** — Decision 4, options A, B or C — taken by its owner before anything is
   written against it.
7. **The download**, with the JS returning a value the Rust side checks, and the failure path gated.
8. **T4**, by a person, recorded in `STATUS.md` with browser, version, operating system and date.

Steps 1, 2 and 4 need no decision from anybody and no `unsafe`; step 6 blocks only step 7. **A page
that boots a ROM, takes a keyboard and loads a dropped tape is reachable without resolving Decision
4 at all**, which is the argument for this order.

## What this document could not settle

- **Every claim in Decision 2's `Ctrl` table.** It is the load-bearing evidence for the largest
  decision here and its class is **derived**. The design survives being wrong about *which*

  grade — *"A person typing `PRINT "HELLO"` is the instrument."* One person trying it for ten
  minutes settles it, and if the answer is no the fix is one row.
- **Which of Decision 4's three routes to take.** Recorded with a recommendation and left open,
  because it turns on how much `unsafe_code = "forbid"` is worth to the person who wrote it, and
  that is not a fact in the repository.
- **Whether M8 is one milestone or two.** Decision 9 recommends one milestone in two halves and
  cannot make the change, because every affected row is in a file this document does not own.
- **Whether the acknowledgement placement satisfies the permission.** The permission says
  *"the program/manual"*; a page is plausibly both and unambiguously the only thing the user sees.
  The reading here is that this makes the requirement *stronger* rather than ambiguous. It is a
  licensing judgement and `testdata/README.md`'s own note applies — for a licensing claim the
  quotation *is* the thing relied on, and this document has quoted rather than summarised.
- **Whether `requestAnimationFrame` and `Pacer` interact well.** `Pacer` was written against
  `get_frame_time` and is arithmetically gated. A browser tab that is backgrounded stops calling
  the frame callback entirely, and `Pacer` will then be handed a very large elapsed time and report
  a very large number of dropped frames — which is the designed behaviour and is exactly right, and
  has never been seen. It is the first thing to look at if the emulator behaves oddly after a tab
  is left in the background.

**A bare line number is unverifiable in principle rather than merely fragile, and the audio row
above is this repository's cleanest demonstration of it.** No sentence was edited on either side of
those four citations — the files they point into simply got longer, and the numbers went from

ordinary stale citation, because a drifted number still *resolves*: some line is always there, it
reads plausibly, and nothing announces the substitution. It is the same failure Decision 1's

something true of *something* and is never held up against the claim it was offered as evidence

figure — that ten of a hundred and twenty-two resolvable line citations in this repository carry an
