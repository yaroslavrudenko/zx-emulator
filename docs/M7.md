# M7 — the 128

Design for `crates/spectrum`. [`MACHINE.md`](MACHINE.md)'s milestone table says **128: paging,
second ROM, AY-3-8912, per-bank contention — gate: 128-only software runs.** Decision 8 corrects
the second half of that sentence.

Each decision carries the class of evidence behind the claim that forced it, in the vocabulary
[`M6.md`](M6.md) established — **proven**, **measured**, **derived**, **observed**, plus **ruling**
for a choice no evidence forces, recorded so it is not re-litigated.

> **Every port bit, frame length, contention figure and AY register width below is a pointer to
> verify, not a specification.** They are written from familiarity with the hardware, not
> transcribed from it in front of the implementer. `M6.md` opened with the same warning and it was
> **right**: three of its numbers were later found wrong, and one of them — the `.z80` compression
> rule that a literal `ED` is never followed by an escape — was a defect **no round trip could
> have caught, because our own decoder misread it symmetrically**. A number in this document that
> disagrees with a source is a defect in this document. The implementer transcribes; this document
> only says which numbers the *design* turns on, and therefore which ones are worth the
> transcription.
>
> The figures at highest risk, named so they are checked first: **the `0x7FFD` bit layout and its
> partial address decode** (Decision 2), **`FIRST_CONTENDED_T_STATE` for the 128** (Decision 4),
> **the AY's per-register write masks and its noise polynomial** (Decision 6), and **the `.z80`
> hardware-mode numbers for the 128 in each of versions 2 and 3** (Decision 7) — the last because
> `M6.md` already found that the two versions *renumber* the modes and that accepting mode 3
> unconditionally *"would load a 128 snapshot as a 48K and silently lose five banks."*

---

## What M7 inherits, and the one thing it does not

**Most of this milestone was paid for at M5.** [`ARCHITECTURE.md`](ARCHITECTURE.md) Decision 5 built
paged memory two milestones early — *"48K is a special case of the 128: paging locked, banks
fixed. Cost: about thirty lines."* Decision 1 below **counts** what that bought — in fields and
methods, not in adjectives — because a claim about a saving is worth as little as any other
uncounted claim.

**M6 built the instrument M7's state needs.** `Snapshot` is bank-keyed rather than address-keyed,
and `M6.md` Decision 2 gives the reason in the present tense — the 48K's three `.z80` page numbers
*"are neither contiguous nor derivable from the 128's rule"* — with *"that M7 needs it anyway"*
explicitly demoted to a bonus. It is now the requirement, and the design is already the right shape.

**What M7 does not inherit is an oracle.** M6 had one for the *files*: a `.z80` we write either
loads in somebody else's emulator or it does not. M5 ended without one for the *machine*, and then
got one — `crates/spectrum/tests/timing_oracle.rs`, 68 hardware-measured numbers, 0 disagreements.
**Whether a 128 equivalent exists is the first question in this milestone**, because the answer
decides what M7's gate can be and whether its contention figures are transcribed or established.
The survey is Decision 8; Decision 4 says what turns on it.

## Decision 1 — one machine, and a 48K is a 128 that powered on with the lock already set — **derived**

The candidates were a configuration of `Spectrum`, a sibling type, and a trait.

### What actually differs

| | 48K | 128 | Where it lands |
|---|---|---|---|
| RAM | 3 banks reachable | 8 banks, slot 3 pageable | `Memory::slots` — **already a slot map** |
| ROM | one page | two: 128 editor, 48 BASIC | `ROM_COUNT` — **already 2** |
| Contended | bank 5 | banks 1, 3, 5, 7, in *any* slot | `Memory::contended` — **already a `[bool; 8]` field** |
| Screen | bank 5 | bank 5 or shadow bank 7 | `screen::render` — a real change, Decision 3 |
| Paging port | — | `0x7FFD` | one new method, Decision 2 |
| Sound | beeper | + AY-3-8912 | a new peripheral, Decision 6 |
| Frame | 69888 T | 70908 T | `Clock` — a real change, Decision 4 |
| First contended T-state | 14335 | different, and **the value is the milestone's open question** | Decision 4 |

Four of the eight rows are **already fields on types that exist**. That is Decision 5's payoff and
it is checkable rather than aesthetic: the diff to `crates/spectrum/src/memory.rs` for the whole
memory half of the 128 is *two `u8` fields and two methods*, derived below.

### The finding that collapses the memory half

`SPECTRUM_48K_SLOTS` is `[Rom(0), Bank(5), Bank(2), Bank(0)]`. Derive a slot map from a `0x7FFD`
value the way a 128 does — bits 0–2 select the bank at `0xC000`, bit 4 selects the ROM at `0x0000`,
slots 1 and 2 are wired to banks 5 and 2 on both machines — and ask which value produces that map:

```text
  0x20 = 0b0010_0000
         bits 0-2 = 000  ->  bank 0 at 0xC000     matches
         bit  3   = 0    ->  screen is bank 5     matches
         bit  4   = 0    ->  ROM page 0           matches
         bit  5   = 1    ->  paging locked        matches: a 48K cannot page
```

**A 48K's memory map is exactly what port value `0x20` derives, and its inability to page is
exactly the lock bit already being set.** So `Memory` needs no model discriminator at all. It needs
the port byte and the value to restore on reset:

```rust
struct Memory {
    ram: Box<[[u8; PAGE_SIZE]; BANK_COUNT]>,
    rom: Box<[[u8; PAGE_SIZE]; ROM_COUNT]>,
    slots: [Slot; SLOT_COUNT],
    contended: [bool; BANK_COUNT],
    paging_port: u8,          // new: the SSOT for slots, screen, ROM and the lock
    paging_port_at_reset: u8, // new: 0x20 for a 48K, 0x00 for a 128
}
```

`write_paging_port` returns early while `paging_port & LOCK != 0`, so **a 48K absorbs a write to
`0x7FFD` with no model check anywhere** — and the existing test
`writing_a_port_the_ula_does_not_own_leaves_the_border_alone`, which writes `0x7FFD` to a 48K and
asserts nothing moved, keeps passing unchanged. `reset` assigns `paging_port_at_reset` and re-derives
the map, which is correct on both machines for the same reason.

This is the strongest single argument in the document and it is worth stating as such: **the
sentence "48K is a configuration of the 128" stops being a slogan and becomes an equation.**

### Why not a sibling type, and why not a trait

**A sibling `Spectrum128` duplicates the frame loop**, and the frame loop is the part of this crate
with the subtlest rule in the project: `MACHINE.md` Decision 1 (the bus owns the clock, never the
sum of `step()` returns) and Decision 2 (one step can overrun the frame, so watch the counter and
never try to land on the budget). `lib.rs` carries a test whose whole job is to prove the first of
those — `the_frame_loop_is_driven_by_the_bus_and_not_by_step_returns` — and a second copy of that
loop is a second place for it to be got wrong, with the copy's failure invisible until a 128 game
runs 20 % long with nothing failing. It also doubles every test helper in `tests/common/mod.rs`.

**A trait, or a `Ula<M: Model>` generic, is worse than either.** It buys runtime polymorphism
nothing needs — a machine does not change model mid-run — and pays for it by monomorphising the
entire `Cpu<Ula<M>>` instantiation twice. `ARCHITECTURE.md`'s codegen section measures that
instantiation (three jump tables of 124 + 119 + 64, 15 bounds checks, one indirect call), and
doubling it to express a two-element set is exactly the over-engineering a two-variant enum
answers for free.

### What it costs callers

| | |
|---|---|
| `Spectrum::new(&rom)` | **unchanged.** Still a 48K, still one ROM |
| `Spectrum::spectrum_128(&editor, &basic)` | new |
| `Spectrum::restore(&Snapshot)` | **becomes fallible** — the one breaking change, argued in Decision 7 |
| every existing 48K test | **unchanged**, which Decision 4 exists to guarantee |

There are ten `Spectrum::new` call sites, all in this workspace, and `crates/frontend/src/main.rs`
is `fn main() {}`. The break is therefore cheap in practice — and it is still a semver event, and
it is still listed and needs approval, because *"adding public fields is free with zero consumers
and breaking with one"* and the consumer count is a fact about today.

## Decision 2 — the port value **is** the paging state — **ruling**, with one structural consequence

### The layout

| Bit | Meaning | On a 48K |
|---|---|---|
| 0–2 | RAM bank paged into `0xC000` | — |
| 3 | screen: 0 = bank 5, 1 = shadow bank 7 | — |
| 4 | ROM: 0 = 128 editor, 1 = 48 BASIC | — |
| 5 | **paging disable** — once set, every further write is ignored until reset | set at power-on |
| 6–7 | unused on a 128 (the +2A/+3 use `0x1FFD` instead) | — |

Every row above is confirmed verbatim against the
[World of Spectrum *128K Technical Information*](https://worldofspectrum.org/faq/reference/128kreference.htm)
reference, including bit 5: *"If set, memory paging will be disabled and further output to this
port will be ignored until the computer is reset."*

**The address decode is confirmed from the same source and it is partial**, which is the part that
produces "works here, not there" bugs:

> *"the hardware will respond to any port address with bits 1 and 15 reset."*

So **A15 = 0 and A1 = 0**, and nothing else is decoded — the port answers at a large family of
addresses and not only at `0x7FFD`. Two things follow:

- `ula.rs` already decodes the ULA on **A0 = 0 alone** (`ULA_PORT_SELECT`), and its module
  documentation explains why that is not a simplification: *"this is why the port is written `0xFE`
  but responds at `0x7FFE`, `0xBFFE` and every other even address."* The same reasoning applies
  here, and the two decodes **overlap**: an address with A0 = 0, A1 = 0 and A15 = 0 is claimed by
  both the ULA and the paging port, and on the hardware both respond. The `out_port` arm must
  therefore be **two independent `if`s, never a `match` on the port**, or one device silently
  stops answering.
- Software that pages with `LD BC,0x7FFD : OUT (C),A` is the common case and any decode gets it
  right. Software that reaches the port some other way is what distinguishes a correct decode from
  a lucky one, and it is the reason to write the mask rather than an equality.

### Three partially-decoded devices on one bus, and where they collide

M7 puts a third device on a bus where every device decodes only a few address lines. Writing the
three rules next to each other is the cheapest way to see the interactions, and two of them are
real:

| Device | Responds when | Overlaps |
|---|---|---|
| ULA (`0xFE`) | A0 = 0 | paging, AY |
| Paging (`0x7FFD`) | A15 = 0, A1 = 0 | ULA |
| AY select / read (`0xFFFD`) | A15 = 1, A14 = 1, A1 = 0 | ULA |
| AY write (`0xBFFD`) | A15 = 1, A14 = 0, A1 = 0 | ULA |

- **Paging and the AY cannot collide**: they disagree on A15, always. That is a genuine structural
  guarantee and it is worth asserting once so nobody re-derives it.
- **Paging and the ULA collide** on any address with A0 = 0, A1 = 0, A15 = 0. On a write both act,
  which is well defined and is why the `out_port` arm must be two independent `if`s rather than a
  `match` on the port.
- **The AY and the ULA collide** on any address with A0 = 0, A1 = 0, A15 = 1, A14 = 1. On a *read*
  that is two devices driving the data bus at once, and the result is a hardware conflict with no
  clean model. **`in_port` must therefore fix an order and say so at the site**, and the choice is
  a ruling rather than a measurement until some software is observed to depend on it. There is no
  right answer to be discovered by thinking harder about it.

`ula.rs`'s existing `in_port` returns `FLOATING_BUS_BYTE` for every port with A0 set, which today
includes `0xFFFD`. The AY read arm therefore goes **before** that fallback, not after it — an
ordering bug here reads as "the AY is write-only", which is silent and plausible.

### No value is hostile, and that is a property rather than a hope

This crate builds with `panic = "abort"` in release, so a guest-triggered panic kills the process —
and this project has shipped exactly that defect once already (`M6.md` Decision 6 records the `u8`
T-state accumulator that a 63-byte prefix run overflowed). A paging port is guest-controlled input
by definition: any of 256 values, at any moment, from any program.

**All 256 are legal and none of them can panic**, and the reason is that `M5` already paid for it.
`BankIndex::new` masks to three bits and `RomIndex::new` to one, on construction *and* at the point
of use, and `memory.rs` gives the reason in the present tense: *"on a 128, bits 0–2 of port
`0x7FFD` are the bank number, so every three-bit value is a legal selection and there is nothing to
reject."* That sentence was written about hardware the machine did not yet have. It is now the
specification, and the assertion that discharges it is a loop over all 256 values checking that the
machine is still coherent — **exhaustive on the axis that matters, and cheap**, which is the
combination `M6.md` Decision 6 used for the truncation sweep.

There is no `PagingError`. Adding one would be a type asserting a failure mode that does not exist,
which `STATUS.md` catalogues as *"the type-level form of a comment claiming a protection that does
not exist."*

### The lock is absorbing, and a restore must go around it

Once bit 5 is set, `0x7FFD` is dead until a hard reset. That is one line in `write_paging_port` and
one line in `reset`.

**It is also a trap for the snapshot applier, and it is the same trap `set_border` already
documents.** A `.z80` v3 records the last value written to `0x7FFD` — lock bit included — so a
snapshot of a locked machine restores a locked machine, correctly. But `restore` cannot get there
by *calling* `write_paging_port`, because the machine being restored into may already be locked
from whatever it was running before, and the write would be silently ignored. The applier needs
`pub(crate) fn set_paging_port(&mut self, value: u8)` that assigns and re-derives, bypassing the
lock — exactly as `Ula::set_border` bypasses `out_port` and for a directly analogous reason: a
restore is not a machine cycle, and routing state-setting through a guest-facing path charges
effects that never happened.

`M6.md`'s note that a restore routed through `out_port` *"leaves the round trip green and turns the
contention-after-restore assertion red"* is the template for the gate here: **restore into a locked
machine, then assert the paging took.** A restore that silently did nothing is otherwise invisible,
because every field the round trip compares would still match.

### Reset acquires a job it does not have today

`Spectrum::reset` reaches `Ula::reset`, which touches the clock, the border and the cycle
bookkeeping and **deliberately does not touch `Memory` at all** — *"a reset button does not clear
RAM, does not lift the keys, and does not rewind a cassette."* That is still right about RAM, and
it is now incomplete: **reset clears the paging lock and restores the power-on map**, which is the
only way a locked 128 ever pages again.

So `Ula::reset` gains a call to `Memory::reset`, and that call is **a no-op on a 48K by
construction** — `paging_port_at_reset` is already `0x20`, which is already the value. The existing
`reset_returns_the_clock_to_the_start_without_disturbing_memory`, which writes `0x8000` and asserts
the byte survives, keeps passing unchanged, and it is worth running it deliberately rather than
noticing later that it still does. The AY is reset in the same place and for the same reason.

### One representation, derived once

`Memory` stores the **port byte** and derives `slots`, the screen bank and the lock from it. It
never stores both. The alternative — keeping a `paging_locked: bool` and a `screen_bank: BankIndex`
alongside the byte — is three representations of one datum that can disagree, and the snapshot
writer would then have to choose which to serialise. `slots` is a derived cache and is rebuilt by
the one function that reads the byte, so there is exactly one place where the bit layout is
written down.

## Decision 3 — contention follows the bank; the screen follows the port — **derived**

### The hot path does not change

`Memory::is_contended(address)` already asks the slot map rather than the address range, and
`memory.rs` says why in a sentence written at M5: *"Getting this wrong is not a bug that shows up
as a crash; it shows up as a demo tearing three years later."* It already carries the test that
proves it — `contention_follows_the_bank_and_not_the_address_range` moves bank 5 into an
uncontended slot and asserts contention moved with it, and its own comment says it was written
*"at M5 while it is still cheap to fix."*

So the whole of per-bank contention is **one array literal**: `contended` becomes
`[F, T, F, T, F, T, F, T]`. `Ula::tick`, `Ula::contend` and `Ula::port_delay` are unchanged, and
**the branch count on the hot path does not move** — which matters, because `tick` is the
emulator's hottest function and its branches were deliberately reduced when the machine-cycle
heuristic was retired.

> **One honest cost, stated rather than glossed.** Decision 4 turns `delay()`'s inputs from
> compile-time constants into fields of a `Timing` value, so the frame length, the first contended
> T-state and the pattern stop being immediates folded into the instruction stream and become loads
> from a struct that lives inside `Ula`. Same branches, a few more loads, from a line that is hot by
> construction because `tick` runs every T-state. **This is a change to the hot path and calling it
> "byte-identical" would be an unmeasured claim of exactly the kind `ARCHITECTURE.md`'s *Measured*
> section exists to catch.**
>
> It is affordable and the affordability is already measured, not assumed: the paged, contended bus
> runs at ~160× real time and spends **~125 µs of a 20,000 µs frame — 0.6 % of the budget** — and
> `ARCHITECTURE.md`'s standing position is that performance is a non-goal and nothing is optimised
> until measured. `cargo bench -p z80 --bench step` is the command if anyone wants the delta;
> nobody should chase it, and nobody should assert it is zero either.

### The case a 48K never has, and a gate that already anticipates it

On a 128 a contended bank can be paged into `0xC000`, so **the stack, the refresh address `IR`, and
the program counter can all sit in contended memory at once** — a configuration a 48K cannot
reach, because its only contended bank is nailed to `0x4000`.

`STATUS.md` already names this: the internal-run case *"requires arriving from an uncontended cycle
onto a contended address, which happens only when the internal cycles ride the refresh address
`IR`… **M7 makes that case routine, because a 128 contends banks in whichever slot they are paged
into.**"* `contention_magnitude.rs` grades it today for one arrangement. The M7 addition is not a
new mechanism — it is the same gate run with a contended bank at `0xC000`, and it is close to free.

### The screen the ULA actually draws

`screen::render` reads through `Memory::read(DISPLAY_FILE + offset)`. On a 128 that is wrong in a
way that is invisible until bit 3 of `0x7FFD` is set: **the ULA draws from bank 5 or bank 7
directly, not through the slot map**, and bank 7 usually has no address at all.

The fix reads from the bank the port selects, which is *the same code on both machines* because a
48K's screen bank is 5 and bank 5 is at `0x4000`:

```rust
pub fn render(memory: &Memory, border: Colour, flash_phase: bool, frame: &mut Frame)
//            ^ unchanged signature: `Memory` already knows which bank the ULA is drawing
```

**`screen::render`'s public signature does not move**, and neither do `DISPLAY_FILE`,
`ATTRIBUTE_FILE` or any other public constant, because they are still the true addresses at which
bank 5 appears. What changes is one indirection inside the function. This is the second independent
caller for `Memory::bank`, and Decision 7 shows the first.

Three properties to gate, because each is a plausible independent wrong answer:

- switching bit 3 changes what `render` draws, **and changes nothing else** — not the slot map, not
  contention, not what `Memory::read(0x4000)` returns;
- **the contended set does not follow the screen select.** Banks 1, 3, 5 and 7 are contended
  whichever one the ULA is drawing. A model that contended "the screen bank" would be right for
  bank 5 and wrong for the other three, and would pass any test that only ever selects bank 5;
- writing to bank 7 while it is paged into `0xC000` **and** selected as the screen is visible on
  the display, which is the whole reason the shadow screen exists.

## Decision 4 — the frame's geometry is a value, the 48K's constants do not move, and the 128's number is the milestone's open question

This decision has two halves. The first is a design choice with a measured cost. The second is a
research result and it is the most important paragraph in the document.

### The number

The 128's frame is **70908 T-states**, and unusually for this project that figure has two
independent transcriptions in the repository that agree. `MACHINE.md`'s 48K/128 table states it,
and the `.z80` format description states the T-state counter's low word *"counts down from 17471 to
0 (17726 in 128K modes), which make a total of 69888 (70908) T states per frame"* — quoted in
`M6.md` Decision 7 for an unrelated purpose. `(17726 + 1) × 4 = 70908` exactly, and
`70908 = 228 × 311`. Two sources, one arithmetic identity, agreeing. That is better than most
figures here start out.

**`FIRST_CONTENDED_T_STATE` for the 128 is a different matter and is not settled by this
document.** The figure in circulation is 14361. What this repository knows about it is precisely
one thing, and it is easy to over-read:

> `timing_oracle.rs`'s mutation table has a row *"`FIRST_CONTENDED_T_STATE` 14335 → 14361 (the
> 128's figure) — **RED, 23 of 68**"*.
>
> **That establishes that 14361 is not the 48K's number. It is not evidence that it is the 128's.**
> The two claims share a numeral and nothing else. A mutation that reddens a 48K oracle tells you
> about a 48K; it is silent about a machine the oracle does not describe. Writing it up as
> *"the strongest evidence available that the two machines are genuinely different"* is the correct
> reading — the machines **are** different, by 23 rows — and the step from there to *"and 14361 is
> what the 128 uses"* is unsupported. Distinguishing those two readings is the entire content of
> this paragraph, and `STATUS.md` catalogues the failure of not distinguishing them as
> *"an argument that names real quantities, predicts the right verdict, and identifies the wrong
> cause."*

The derivation does not transfer either. The 48K's is `64 × 224 − 1 = 14335`; the 128's would have
to be `63 × 228 − 3 = 14361`, which is a different offset from the line boundary (−3, not −1) and a
different pre-display line count. **A derivation whose *shape* changes between two machines is not
a derivation, it is a fit.** And the phases differ: `14335 mod 8 = 7` against `14361 mod 8 = 1`, so
the pattern's alignment within its eight-T-state group is not preserved either.

**And the source is thinner than it looks.** The survey in Decision 8 found 14361 in two places —
the [World of Spectrum *128K Technical Information*](https://worldofspectrum.org/faq/reference/128kreference.htm)
page (*"the 6,5,4,3,2,1,0,0 pattern starts at 14361 T states after the interrupt"*, *"repeats every
228 T states"*, *"Memory banks 1,3,5 and 7 are contended"*) and the
[Sinclair Wiki](https://sinclair.wiki.zxnet.co.uk/wiki/Contended_memory), which says the same thing.
**The wiki page cites no source at all for the 128 figures and reads as a descendant of the FAQ**,
so this is one ancestor seen twice rather than two witnesses — the shape `STATUS.md` names as
*"a derived figure repeated across documents acquires authority it never earned."* No primary
posting or measurement for 14361 was found.

The one thing the source does well: it states the figure **relative to the interrupt**, which is
exactly and only the frame the 48K oracle established as meaningful. So the transcription needs no
reinterpretation, and reinterpretation is where a silent error would live.

**So the 128's contention phase is exactly where the 48K's was before `timing_oracle.rs` landed,
and everything `STATUS.md` says about that state applies verbatim:** *"a gate that fails when a
constant changes says nothing about whether the constant was right."* Decision 8 says what would
change it, and how far — which is not all the way.

### The design: `Timing` is a value, and nothing existing moves

`timing::T_STATES_PER_FRAME`, `FIRST_CONTENDED_T_STATE`, `INTERRUPT_T_STATES`, `T_STATES_PER_LINE`,
`LINES_PER_FRAME` and `delay()` are `pub`. The obvious move is to replace them with model-aware
equivalents. **It is measurably the wrong move**, and this is the one place in the document where
the cost was counted rather than felt:

```sh
grep -rln 'FIRST_CONTENDED_T_STATE\|T_STATES_PER_FRAME\|INTERRUPT_T_STATES' crates/spectrum/tests/ | wc -l
ls -1 crates/spectrum/tests/*.rs | wc -l
```

On 2026-09-01 that was **14 of 19**, and in every case the reference is the positioning device —
`advance_to(&mut machine, FIRST_CONTENDED_T_STATE + phase)`. Each of those gates is *correct for a
48K* and each one says so in its own header. Changing the constants means rewriting fourteen
correct test files to express a 48K fact in a more general vocabulary: churn with a defect budget
and no gate to show for it.

> **Run the command; do not quote the ratio.** It read **13 of 16** when this paragraph was first
> drafted and **14 of 19** roughly twenty minutes later, because other agents were landing M6's
> tests in the same working tree throughout. The *design* conclusion is not sensitive to the exact
> figure — it is that these constants are the positioning device for most of the suite, and that
> ratio is going up, not down. The number is recorded with its date because a bare integer here is
> the same defect `MACHINE.md`'s milestone table just had corrected out of it, and watching it
> change mid-paragraph is the cheapest possible demonstration of why.

So: **the constants stay, unchanged, as the 48K's — and they are redefined as projections of a new
value type, so there is still one source.**

```rust
/// A machine's frame geometry: everything that differs between a 48K and a 128.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Timing { /* line length, lines per frame, first contended T-state,
                      interrupt window, delay pattern */ }

impl Timing {
    pub const SPECTRUM_48K: Self = /* ... */;
    pub const SPECTRUM_128: Self = /* ... */;
    pub const fn delay(&self, frame_t_state: u32) -> u32 { /* today's `delay`, parameterised */ }
}

pub const T_STATES_PER_FRAME: u32 = Timing::SPECTRUM_48K.frame_t_states();
pub const FIRST_CONTENDED_T_STATE: u32 = Timing::SPECTRUM_48K.first_contended_t_state();
// ...and so on: derived, not repeated.
```

**SSOT is then enforced by the compiler rather than by discipline**, which is the same instrument
`memory.rs` and `timing.rs` already use for their power-of-two assumptions (`const _: () =
assert!(...)`). The free `delay(frame_t_state)` keeps its signature and becomes
`Timing::SPECTRUM_48K.delay(frame_t_state)` — a one-line body change, no public signature moved,
**zero public removals**.

`Clock` carries a `Timing` by value. `Clock::new()` keeps its signature and yields the 48K clock,
which is what it already means. `Clock` grows from 16 bytes to roughly 32; it is `Copy`, it is
returned by value from `Ula::clock()`, nothing hot copies it, and nothing asserts its size.

Two knock-on effects that must be handled rather than discovered:

- **`snapshot/z80.rs`'s quarter arithmetic is model-dependent.** `QUARTER_T_STATES` is
  `T_STATES_PER_FRAME / 4`, and the compile-time assertion
  `QUARTER_T_STATES * QUARTERS_PER_FRAME == T_STATES_PER_FRAME` holds for both machines
  (17472 × 4 = 69888, 17727 × 4 = 70908) — which is a relief and also a warning, because it means
  **the assertion cannot detect the frame length being wrong for the model**. `M6.md` named this
  field *"the single field where a confident-sounding formula is most dangerous"* and its
  exhaustive-over-69888 test must become exhaustive over both frame lengths.
- **`tape/tap.rs` derives its inter-block pause from `T_STATES_PER_FRAME`**, deliberately, *"the
  machine's own constant rather than the clock speed."* On a 128 that yields a pause 1.5 % longer.
  It is far inside the ROM loader's tolerance and it is named here so it is not later found and
  mistaken for a bug.

## Decision 5 — the interrupt acknowledge: the 128 does **not** make it decidable, and something that already exists does

`ula.rs` records a known model defect and hands it to this milestone:

> *"An interrupt acknowledge has no callback — it reads no memory, asserting `/IORQ` in place of
> `/MREQ` — so `crates/z80` delivers it as seven bare `Bus::tick` calls at the refresh address…
> The hardware performs **one** machine cycle there — M1 stretched by two wait states — so a
> contended `IR` would be charged seven stalls where it owes one.*
>
> ***It is unobservable on a 48K, and that is why it is written down rather than fixed.*** *…What
> makes this worth recording now: the 128 has a different frame geometry, and `docs/STATUS.md`
> already lists interrupt acceptance as having **no oracle in this project at all**. This is the
> shape that gap has."*

### The 128's geometry does not deliver, and the arithmetic is short

The acknowledge is unobservable on a 48K because `/INT` is asserted for the first 32 T-states of
the frame and contention does not begin until 14335, so an accepted interrupt always lands in the
top border where every stall is zero. **On a 128 the two numbers change and the gap does not
close:**

| | 48K | 128 |
|---|---|---|
| `/INT` asserted from | frame T-state 0 | frame T-state 0 |
| interrupt accepted no later than | ~32 + one instruction | ~32 + one instruction |
| first contended T-state | 14335 | ≈14361 |
| **gap** | **≈14300 T-states** | **≈14300 T-states** |

Both machines raise the frame interrupt at the top of the frame and both begin contending roughly
14300 T-states later. Acceptance cannot be deferred past the window's end — if the line has dropped
the offer is not made — so the acknowledge lands in the top border on **both** machines, for the
same structural reason, and the shadow screen, the second ROM and the per-bank rule are all
irrelevant to it because none of them moves either endpoint.

**The argument does not depend on the disputed number, which is the point of stating it this way.**
Decision 4 says the 128's `FIRST_CONTENDED_T_STATE` is transcribed rather than established. This
conclusion survives that: contention begins roughly sixty display lines into the frame on any
Spectrum, so the figure would have to be **under about forty** for an acknowledge to reach it, and
no candidate value for any machine in this family is remotely near that. A conclusion that holds
across the whole plausible range of an unsettled input is worth more than one that needs the input
settled first — and noticing which kind you have is the difference between this paragraph and the
one in `ula.rs` it corrects.

**So the hand-off is answered in the negative, and that is the finding.** `ula.rs`'s sentence *"the
128 has a different frame geometry"* is true and does not imply what it was written to suggest. It
is the shape `STATUS.md` names: an argument that names real quantities and identifies the wrong
mechanism.

There is no second route through software either, and it is worth closing them all explicitly:
a snapshot cannot help (`Spectrum::step` offers an interrupt only while the ULA asserts one); the
NMI cannot help (this machine has no NMI source); a long instruction cannot help (acceptance is at
instruction end, and the line has dropped); and lengthening `INTERRUPT_T_STATES` cannot help,
because the ungraded uncertainty there is single-digit T-states against a gap of fourteen thousand.

### What **does** decide it, and it has been available since M5

*"No test can currently tell the two models apart"* is true of **software running on the machine**
and false of **a test driving the bus**. `Cpu::new`, `Cpu::interrupt` and `Ula::new` are all public;
`ula.rs`'s own unit tests already position a ULA at a chosen frame phase and synthesise tick
streams by hand. A test that builds a `Cpu<Ula>`, puts the clock inside the contended window, points
`IR` at a contended bank and offers an interrupt separates the two models by a measurable number of
T-states.

That test **pins** the model; it cannot **grade** it. What says which model is right is the hardware
rule, and this repository has already written it down with its reasoning
([`Z80-REFERENCE.md`](Z80-REFERENCE.md)): *"The Z80 asserts `/M1` together with `/IORQ` in place of
`/MREQ`… What the address bus carries is `IR` — the refresh address, not an address to fetch
from."* One machine cycle, therefore one contention point.

Note what is **not** in dispute: the acknowledge's *length*. `crates/z80` charges 7 T-states for a
maskable acknowledge and 5 for an NMI, and those totals are inside the FUSE-graded envelope. The
only question is whether those 7 T-states are one cycle or seven, and the hardware rule answers it.

### The fix, and why it is not the guess it was called

```rust
/// The acknowledge cycle of an accepted interrupt: one machine cycle, `t_states` long,
/// with the refresh address on the bus and no transfer. Defaulted, so implementing it
/// is optional and adding it breaks nothing.
fn acknowledge(&mut self, addr: u16, t_states: u8) {}
```

This is the `fetch` precedent exactly — a seventh defaulted method on `Bus`, non-breaking by
construction, which `ARCHITECTURE.md` records was *checked rather than asserted* when `fetch`
landed. `Ula` implements it as the contention charge plus arming `covered_t_states`, which is what
every other cycle already does.

**The length travels with the call, and that is deliberate.** `crates/z80` keeps
`INTERRUPT_ACKNOWLEDGE` and `NMI_ACKNOWLEDGE` private today with a stated reason: *"An acknowledge
has no callback… exporting its length would hand out a number a `Bus` cannot act on."* A callback
falsifies the premise, not the rule — so rather than exporting two constants, the callback carries
the figure and the constants stay private. The reasoning that justified hiding them is preserved in
a stronger form.

**Ruling: fix it at M7.** The argument for leaving it was *"a fix would be an unverifiable guess"*,
and on inspection it is not a guess in the sense that phrase usually carries. It is not a
*magnitude* being invented; it is a *structural* question — one cycle or seven — that a documented
hardware rule already answers, and the current model knowingly contradicts a rule this repository
states in its own reference. Leaving a known contradiction in place because nothing can see it is
the mirror image of `MACHINE.md`'s standing lesson about *"reporting the absence of a distinguishing
test as evidence of correctness."*

**And the fix closes a model defect while closing no verification gap. Both halves go in the
register.** Nothing grades the acknowledge against hardware, nothing in this milestone will, and —
newly, and this is the part worth carrying forward — **nothing can, because no software on either
machine can reach the case.** That is a stronger and more useful statement than "it is currently
ungraded", and it converts an open row into a closed question with a permanent asterisk.

## Decision 6 — the AY-3-8912, and the only honest answer to "what grades sound" — **ruling**

This is the hardest verification problem in the milestone and it deserves the plainest statement.
**A wrong tone is audible to a human and invisible to every test this repository can write.** There
is no oracle for sound, there is no round trip, and there is no equivalent of "a demo tears or it
does not" because a listener cannot tell a 2 % pitch error from a correct one.

The way through is not a better ear. It is to notice that **the AY is not a sound problem. It is a
state-machine problem that happens to drive a speaker**, and a state machine is exactly what this
project can grade.

### What is actually checkable, and at what tier

| Property | Tier | Why |
|---|---|---|
| **Register write masks** — several registers are narrower than 8 bits and the excess is dropped | **derived** | Transcribed from the datasheet. Grading against the transcription cannot discover the transcription is wrong — but software *reads registers back*, so a wrong mask is a wrong value returned to a guest |
| **Port decode** — `0xFFFD` select/read, `0xBFFD` write, and the address lines actually decoded | **derived** | Same class as the `0x7FFD` decode. Verify against a source; the *shape* (two `if`s, not a `match`) is forced by the overlap argument in Decision 2 |
| **Noise LFSR period** | **proven**, and its strength is measured below | Run the register and count until it repeats. **This needs no external source at all** |
| **Envelope shape aliasing** — of the 16 four-bit shape values only 8 are distinct behaviours; the lower eight collapse into two blocks of four | **proven** | A structural property of the CONT/ATT/ALT/HOLD decode, checkable as an equivalence over all 16 without knowing what any shape *sounds* like. **Which two upper shapes they alias to is a transcription** — the structure is provable, the targets are not |
| **Counter periodicity** — a tone register value of *n* produces a square wave of a period that is an exact function of *n* | **proven** | Pure arithmetic over the state machine, exhaustively checkable over all 4096 tone-period values |
| **Mixer polarity** — the enable bits are **active low** | **proven**, once the convention is fixed | Inverting it is a classic emulator defect. With every channel disabled the output is silent; the test is a boolean, not a magnitude |
| **The volume table** — 16 levels, roughly logarithmic | **derived**, and the magnitudes are unverifiable here | Nothing this project can build distinguishes a right table from a plausible one |
| **That it sounds correct** | **observed**, T4, and not automated | A human listens to a 128 tune |

**The register file has fifteen registers, not sixteen, and that asymmetry is a trap for the
snapshot.** The `-8912` is a cut-down `-8910` with **one** 8-bit I/O port rather than two — the 128
wires it to an external keypad almost nobody owned — so `R15` does not exist. The World of Spectrum
128K reference states the range directly:

> *"OUT (0xfffd) - Select a register 0-14"*, *"IN (0xfffd) - Read the value of the selected
> register"*, *"OUT (0xbffd) - Write to the selected register"*.

But **`.z80` v3 reserves sixteen bytes at offsets 39–54 regardless.** So the format has a slot the
machine has no register for, and whatever the model puts there **round-trips perfectly and is
invisible to every round trip** — the exact defect shape `M6.md` Decision 7 is about, arriving in a
new field. Decide what `R15` holds and what a read of it returns, write the decision down, and gate
it with a transcribed vector rather than a round trip, because a round trip cannot see it.

**Not confirmed, and it should be:** which address lines actually decode the AY ports. The
addresses `0xFFFD` and `0xBFFD` are well attested; the decode rule behind them — the `A15`/`A14`/`A1`
pattern assumed in Decision 2's overlap table — **was searched for and no source stating it was
found.** It is consistent with those two addresses and with the `0x7FFD` decode's style, and that
is inference, not a citation. Treat the overlap table's AY rows as the least-supported claim in
this document.

**The dividing line runs between structure and magnitude.** Every *structural* property above is
provable in-repo with no corpus; every *magnitude* is a transcription that nothing here can
adjudicate. M7 should grade the first list exhaustively and state the second as untested, and it
must not blur them. Blurring them is how a gate comes to grade less than it appears to, which
`STATUS.md` records three times already and calls the most recent *"the worst form so far"* — and
an AY gate is an unusually easy place to do it, because a suite of green sound tests reads as
"the sound chip works" whatever it actually asserted.

### What the LFSR period test is worth, measured rather than asserted

The noise generator is reported to be a 17-bit LFSR with taps at bits 0 and 3. A period test needs
no source for that: run the register from a non-zero seed and count until it repeats. But *how much*
it is worth is a question with an exact answer, and this project's habit is to take it rather than
gesture at it. Sweeping all sixteen tap pairs `(0, t)` for a 17-bit Fibonacci LFSR and measuring
each period:

| Period | Tap pairs `(0, t)` |
|---|---|
| **131071 — maximal** | t = **3**, 5, 6, 11, 12, 14 |
| everything else (273, 1023, 4599, 35805, 114681) | t = 1, 2, 4, 7, 8, 9, 10, 13, 15, 16 |

**So a green period test eliminates 10 of the 16 candidate tap positions and cannot distinguish
the remaining 6 from each other.** That is a real gate with an exactly enumerated blind spot, which
is a different thing from either "the noise generator is tested" or "there is no test". It is worth
having, it costs one loop, and it must be described as what it is — the temptation to let a gate
that kills five-eighths of the error space stand in for one that pins the answer is the same move
`STATUS.md` catalogues as letting a good account of the majority stand in for the whole.

What would pin it: a published measured trace from real hardware, or software whose output audibly
depends on the noise sequence rather than merely on its statistics. Neither is in reach here.

### The output is a test instrument, not a product

**M7 models the AY's state machine and produces a deterministic sample stream. It does not open an
audio device.** `M6.md` assigns the beeper — bit 4 of a `0xFE` write — to M8, and M7 does not
overturn that: the audio *device*, the mixing of beeper and AY, and the resampling to a host rate
are all frontend concerns and belong in the milestone that owns the frontend.

What the sample stream buys is the one instrument that works on an output with no oracle:
`MACHINE.md`'s verification item 4, **frame-hash regression** — *"does not prove correctness —
proves change, which is what catches a regression once something works."* That is precisely the
right strength of claim for the AY, and naming it as such is the whole point.

**One design consequence follows and must be built in from the start: the hash must be over the
AY's own output, not over "the machine's audio."** If it covered a mix, M8's addition of the beeper
would change every hash and falsify an M7 gate that was never wrong — a gate that goes red for a
reason unrelated to what it grades is a gate that gets muted, which `ARCHITECTURE.md` gives as the
reason its timing rows are refused rather than asserted.

### What nothing grades, stated in the same breath

- **Any magnitude.** Volume levels, the exact envelope period divisor, the tone prescaler's
  constant. Transcribed, and nothing here can adjudicate a transcription.
- **The mapping from register values to a pitch a human recognises.** No test in this repository
  distinguishes correct from consistently-wrong-by-a-factor.
- **Timing of AY writes relative to the frame.** Music drivers write the AY from the interrupt
  handler; the *audible* result depends on when in the frame the writes land, and nothing grades
  that.
- **Whether it sounds right.** T4, manual, and the honest bottom of this table.

## Decision 7 — `.z80` version 3 already carries everything M7 needs, so still no `.szx` — **ruling, and it overturns `M6.md`**

`M6.md` Decision 9 deferred `.szx` with a forward-looking reason: *"Its extensibility pays off at
**M7**, where the AY registers, the paging port and the second ROM all need somewhere to live and
`.z80` v3 carries them awkwardly."*

**That guess does not survive contact with the format, and the reason is already in this
repository.** `crates/spectrum/src/snapshot/z80.rs` reads the additional header field by field and
names them:

```rust
let _paging = extra.u8()?;      // 35: last OUT to 0x7FFD, on a 128
let _ay_selected = extra.u8()?; // 38: last OUT to 0xFFFD
extra.skip(AY_REGISTER_COUNT)?; // 39-54: the sound chip's registers
```

Those are named fields at fixed offsets, and `AY_REGISTER_COUNT` is already a constant in the file.
Pages 3–10 already map to banks 0–7 — verified against the format description by M6's implementer.
**`.z80` v3 carries the paging byte, the AY select latch, all sixteen AY registers and all eight
RAM banks, in dedicated fields.** There is nothing awkward about it. What `.szx` would add is
`MEMPTR` — which `M6.md` itself notes *"buys nothing measurable today: nothing in this project can
grade `wz`"* — and extensibility for requirements that do not exist.

**Ruling: no `.szx` at M7.** M6's reason for deferring it to M7 is retired rather than inherited,
which is the correction being made in the open. The three-parsers-tripling-the-hostile-surface
argument stands unchanged.

### What `.z80` support at M7 actually requires

- **`Model` gains its second variant and `Snapshot` gains a `model` field.** `M6.md` predicted
  exactly this — *"at M7 those rejections become support, and that is where a `Model` enum earns
  its second variant. A one-variant enum today would be scaffolding"* — and the prediction holds.
- **The hardware-mode check becomes version-dependent in both directions.** M6 found that v2 and v3
  *renumber* the modes. `Version::is_48k` becomes `Version::model(mode) -> Option<Model>` and the
  existing test `the_versions_disagree_about_hardware_mode_three` becomes the anchor for a table
  over both versions and both models. **This is the trap M6 flagged and it is the highest-risk line
  in the parser**: accepting a mode unconditionally *"would load a 128 snapshot as a 48K and
  silently lose five banks."*

  Half of the table is already established in this repository and half is not, and the difference
  should be respected rather than smoothed over. **`z80.rs` already asserts that mode 3 is a 128K
  in v2 and a 48K + M.G.T. in v3**, checked against the format description by M6's implementer — so
  the v2 side of the 128 row is transcribed and verified. **The v3 128K mode number is not**, and
  the current code only knows it is *not* 48K. Transcribe it; do not infer it from the v2 value,
  because renumbering is the whole hazard.
- **`Spectrum::restore` becomes fallible, and the rule is symmetric.** A 128 snapshot restored into
  a 48K has five banks with nowhere to go; dropping them silently is the *"silent last-write-wins"*
  M6 rejected for duplicate pages. The other direction is broken too and less obviously: a 48K
  snapshot restored into a 128 leaves 48K code running against the **128 editor ROM**, because a
  48K file carries no paging byte to select the 48 BASIC ROM. So the check is `snapshot.model ==
  machine.model`, both ways. `restore(&Snapshot) -> Result<(), ModelMismatch>` — the one breaking
  change in this milestone.

  > A 128 *can* legitimately host a 48K image: that is what the ROM's own **48 BASIC** menu entry
  > does, and it is one paging value (48 BASIC ROM selected, paging locked). Making `restore` do it
  > automatically is a plausible convenience and it is **not** built — it is a second meaning for
  > one method, it needs a rule for what the un-restored five banks contain, and no caller wants
  > it. Named here so that if someone later wants it, they add a separate entry point rather than
  > weakening this one.
- **M6's bank-set guard must be redesigned, and it is easy to miss.** `M6.md` closes the
  dropped-bank seam with a test comparing *"the parser's bank set against the set the slot map
  exposes."* **On a 128 that premise dissolves**: banks legitimately exist outside the slot map —
  that is what makes `Memory::bank` unavoidable. The replacement compares the parser's bank set
  against the set the **model** has, not the set currently addressable.

## Decision 8 — the gate, and what "128-only software runs" would add that it cannot

### Whether a 128 timing oracle exists — the test to apply, before the answer

`MACHINE.md`'s timing-oracle section closes with *"Anything about a 128. The site states that 128K
and +2 (Grey) editions of these tests exist. Neither was fetched or verified here; M7 should."*

**Before reporting what the survey found, it is worth fixing what would count**, because the
temptation with an artefact like this is to accept "a 128 timing suite exists" as the answer to
"does a 128 oracle exist", and those are different questions. What moved the 48K suite from
*derived* to **measured** was three things, and they are not equally strong:

1. the text attributes its expected values to hardware — *"we ran the tests on real Spectrums"*;
2. its results database is hardware-only by policy — *"Only submit results from genuine hardware no
   emulators!"*;
3. **decisively: the file carries two expected-result tables, and 25 of 28 submitted real machines
   from 9 independent people sort cleanly into exactly those two classes.**

Only (3) is evidence that does not require believing the author. (1) and (2) are the author's own
statements about the author's own process. A table fitted to one emulator has no reason to predict
a second class of machine, and no reason for twenty-five real machines to fall into the two.

> **And here is the asymmetry that decides how much to expect, whatever the survey turns up: (3)
> may be structurally unavailable for a 128, through nobody's fault.** The 48K's two tables exist
> because real 48Ks genuinely come in two contention classes — the early/late split — so the suite
> *had* to carry two, and the sorting of real machines into them is a prediction that could have
> failed and did not. **If 128s are uniform in this respect, a 128 suite carries one table, and the
> single strongest anti-circularity argument cannot be made about it at all.** Not because its
> author was careless, but because the evidence available has a different shape.
>
> The practical consequence: **a 128 suite can be entirely honest and still only reach *derived*
> in this project's vocabulary, unless it has an independent hardware results database.** That
> possibility must be admitted in advance, so that finding one table is read as what it is rather
> than as a defect in the artefact or as grounds for accepting it anyway.

So the survey asks, in order: **(a)** does a self-checking 128 edition exist and can it be fetched;
**(b)** is there a results database of *genuine hardware* submissions, from more than one person;
**(c)** if there is one table rather than two, is there anything else that rules out an emulator
origin? Failing (b) and (c) together means the artefact is a second implementation's opinion — which
is worth more than our own arithmetic and much less than the 48K oracle, and must be labelled
accordingly rather than promoted by association with its 48K sibling.

### The survey, taken 2026-09-01

**Result: no usable 128 oracle is in hand, and the shortfall is on the decisive leg rather than on
availability.** Candidates, in the same shape as `MACHINE.md`'s 48K table:

| Candidate | What it is | Obtainable? | Hardware results database | Tier |
|---|---|---|---|---|
| **`timing_tests-128k_v1.0.z80`** — the ZXSpectrum4.net 128K edition, by the same author as the 48K suite this project already uses | **Yes, and a live mirror was found.** Not at the origin: `zxspectrum4.net/downloads/timing_tests/` **302-redirects to the site root**, so the whole download directory is gone — worse than the 404 this document's 48K section records. Not in the [MrKWatkins mirror](https://github.com/MrKWatkins/EmulatorTestSuites) either; its `Timing/` directory was enumerated through the GitHub API and contains exactly one `.z80`, the 48K file. **It is on [SoftSpectrum 48's test-results page](https://softspectrum48.weebly.com/test-results.html)**, at `https://softspectrum48.weebly.com/uploads/6/6/7/5/66753101/timing_tests-128k_v1.0.z80` | **None.** `spectrum128k_timing_results.htm` returns **404** — probed, not inferred — and neither `op_timing.php` nor the site's front page links to any 128 equivalent. The only results page is [`spectrum48k_timing_results.htm`](https://www.zxspectrum4.net/downloads/spectrum48k_timing_results.htm) | **derived at best**, and it cannot climb higher on present evidence — see below |
| Patrik Rak's **`ptime`** and Weiv's **`Ptime-128`** | 128K **screen-switching** timing tests — the shadow-screen bit's own timing, which nothing else here would grade | Listed on the SoftSpectrum 48 page | Unknown | **Not investigated.** The highest-value follow-up after the suite itself, because they test a property that is 128-only by construction |
| *ULA 128 Timing Test*, *IR Contention 128* | Catalogued by [redcode](https://github.com/redcode/ZXSpectrum/wiki/Tests) as 128 contention tests | Not fetched | — | Redcode's list *"does not specify whether these tests are self-checking"*, and their 48K siblings are classified **observed** in `MACHINE.md` — mostly on-screen patterns, several needing a floating bus this machine does not model |
| [World of Spectrum, *128K Technical Information*](https://worldofspectrum.org/faq/reference/128kreference.htm) | The community reference document | Yes | n/a — it is prose | **derived** |
| [Sinclair Wiki, *Contended memory*](https://sinclair.wiki.zxnet.co.uk/wiki/Contended_memory) | The community's contention page | Yes | n/a | **derived**, and `MACHINE.md` already classifies it as *"this project's own source. Grading against it would be circular by construction"* |

**Two things follow, and the second matters more than the first.**

**1. The artefact exists and can be had — so M7 should fetch it and run it.** It would be a genuine
instrument: self-checking, running on the real machine, with expected numbers this project did not
write. That is strictly more than we have now and the fetch costs minutes.

**2. It cannot reach *measured*, and that is not fixable by looking harder.** The three legs that
carried the 48K suite were the author's hardware attribution, a hardware-only submission policy, and
— decisively — 25 of 28 real machines from 9 independent people sorting into the file's two expected
classes. **For the 128 the third leg has no counterpart at all** (there is no results page: 404,
probed) and the second applies to a database that does not exist. The two hardware-policy quotes on
`op_timing.php` are **site-wide and not model-scoped**; they do not establish that any 128 was ever
submitted.

What is left is the author's own statement about his own process — which is exactly what the 48K's
third leg exists so that nobody has to rely on. So running the 128 suite green would say *"this
emulator agrees with an artefact of unverified provenance"*, and running it red would be a real
finding. **An asymmetric instrument: its failures are informative and its successes are not.** That
is worth having and it must be labelled that way, because a green run reads as vindication whatever
the header says.

**There is weak evidence it carries only one table, which would settle the question structurally.**
SoftSpectrum 48's own note is that the 128 file *"must be run with late timings in 48K mode"* — a
single named timing mode, with none of the early/late auto-detection the 48K suite advertises. That
fits the prediction above: real 48Ks split into two contention classes and 128s do not, so a 128
suite has no second class to predict and cannot make the argument that rescued its sibling.
**Confirming the table count is the single most decisive thing anyone can do here**, it needs only
the downloaded file, and it is implementation step 0 below.

> **One thing that would partially rescue it, recorded because it is unverified and worth chasing.**
> A report surfaced in search that Fuse fails 128K tests 4, 17, 18, 26 and 33, and that JSpeccy and
> the MiSTer core fail those plus two more. **If true, the tables disagree with at least three
> independent emulators, which is hard to explain if they were fitted to one.** That would be real
> anti-circularity evidence of a different kind from the 48K's. The source thread returned HTTP 403
> and **this was not verified** — it is a lead, not a finding, and it is written here as a lead.

So: **M7's contention figures are transcribed, from a *derived* source, and this milestone does not
change that.** Precisely, from the World of Spectrum 128K reference, quoted:

> *"the 6,5,4,3,2,1,0,0 pattern starts at 14361 T states after the interrupt"*, *"repeats every 228
> T states"*, *"There are 70908 T states per frame"*, *"228 T-states per scanline"*, and *"Memory
> banks 1,3,5 and 7 are contended."*

**One genuinely good property of that transcription, worth noticing because it is not automatic.**
The figure is stated **relative to the interrupt** — *"14361 T states after the interrupt"* — which
is exactly and only what `MACHINE.md` established the 48K oracle can speak to: *"the first contended
T-state falls exactly 14335 T-states after `/INT`… the origin of the frame is still a convention."*
So the 128 figure arrives in the right coordinate system, and this project's convention of asserting
`/INT` at frame T-state 0 makes it directly usable without a change of frame. A source stating it
as an absolute frame position would have needed reinterpreting, and the reinterpretation would have
been a place to be silently wrong.

**And 70908 has three transcriptions that agree** — this reference, `MACHINE.md`'s table, and the
`.z80` format description's *"17726 in 128K modes"*, whose `(17726 + 1) × 4` is 70908 exactly.
`228 × 311 = 70908` closes it, and the format description is a genuinely independent lineage from
the hardware FAQ. That figure is as solid as a transcribed number gets here.

**14361 is not, and the two should not be quoted with the same confidence merely because they
arrive in the same sentence.** The Sinclair Wiki page carrying it **cites no source at all** for
the 128 figures — checked specifically — and reads as a descendant of the World of Spectrum FAQ
rather than an independent witness. So the apparent two-source agreement is **one ancestor seen
twice**, which is the failure mode `STATUS.md` names as *"a derived figure repeated across
documents acquires authority it never earned"* — and *"copying a conclusion is the one operation
that cannot detect an error in it."* No primary posting or measurement for 14361 was found.

The 128's contention **pattern** is on firmer ground than its offset: both sources state it is the
identical `6,5,4,3,2,1,0,0`, with only the offset and the 228-T-state line period differing. That
is a claim about *sameness*, which is much harder to get wrong by transcription than a five-digit
constant.

### What the 48K oracle does and does not license us to say about the 128

One result from the 48K gate bears directly on this and is easy to over-read, so it is stated twice
in this document — once in Decision 4 where the number lives, and once here where the gate is
decided. `timing_oracle.rs`'s mutation of `FIRST_CONTENDED_T_STATE` to **14361, the 128's figure,
went red by 23 rows of 68**.

**That is strong evidence that the two machines are genuinely different, and it is not evidence of
what the 128's number is.** It is a fact about a 48K measured on a 48K oracle. The most it licenses
is the negative: *a single shared contention constant across both models is refuted*, which is
worth having — it forecloses the cheapest wrong design, and it is why `Timing` is a per-model value
in Decision 4 rather than a constant with an exception in it.

### The tiers, in `M6.md`'s vocabulary

| Tier | What it is | Evidence class | Corpus |
|---|---|---|---|
| **T1** | The paging port over all 256 values × the decode axis; the lock's absorbing behaviour; the derived slot map; the AY's structural properties (Decision 6); `Memory::bank` against the slot map; the snapshot round trips R1/R2/R3 extended to 128 fields; the hostile-input sweeps; the frame-position conversion exhaustive over **both** frame lengths | **proven** — deterministic, self-contained | none |
| **T2** | The real 128 ROMs boot to the 128's own menu; the menu's *48 BASIC* entry is selected **from the keyboard** and reaches `© 1982 Sinclair Research Ltd` **through the second ROM** | **measured** — binary pass/fail against a program we did not write | the two 128 ROMs, Decision 9 |
| **T3** | **A program we wrote that a 48K gets demonstrably wrong** | **measured** | the same ROMs |
| **T4** | A real 128-only game; one of our 128 `.z80` files opening in a third-party emulator | **observed** | user-supplied, absent by default |

**T3 is the load-bearing tier and its design is what makes M7's gate honest.** A program that writes
a signature into a bank, pages a different bank into `0xC000`, writes a different signature, pages
the first back and verifies both is genuinely 128-only: on a 48K the paging writes are absorbed and
both signatures land in the same bank, so the second overwrites the first.

**Run it on both machines and assert both outcomes.** A gate that says *"this passes on the 128"* is
much weaker than one that says *"this passes on the 128 **and fails in a specific, asserted way on
a 48K**"*, because only the second proves the paging is what made the difference. Without the
negative half, the program could be passing for a reason unrelated to paging and nothing would
show it — which is `STATUS.md`'s *"a gate can pass vacuously, and only a positive control catches
it"* applied to a milestone rather than to a probe.

**T2's keyboard step is not decoration either.** Selecting a menu entry exercises the ULA keyboard
read, the second ROM, and the ROM-select bit of `0x7FFD` in one motion, and it lands on a string
this project already knows how to assert against glyphs read from the ROM's own character set. It
is the 128's equivalent of the boot gate, and — following the boot gate's own hard-won lesson — the
**frame it lands on** is asserted, not printed.

### So what is M7's gate

**M7's gate is T1 + T2 + T3. `MACHINE.md`'s "128-only software runs" is T4.**

That is the same correction `M6.md` Decision 8 made for M6, made in advance rather than after the
fact, and the milestone table in `MACHINE.md` has been updated to match. `ARCHITECTURE.md`'s copy
of the table is owned elsewhere and still carries the old wording.

**What T4 adds that T1–T3 cannot**, stated plainly rather than apologised for:

- **A program written by someone who did not know how this emulator works.** Every tier below is
  authored here, and an expectation authored here cannot discover a misunderstanding shared by the
  code and its test. This is the same asymmetry `M6.md` measured: the third-party corpus stayed
  green under a symmetric mutation of the T-state formula, and only a hand-derivation and an
  independent implementation went red.
- **Breadth.** A commercial 128 title exercises the AY continuously, pages under interrupt, uses
  the shadow screen for double-buffering, and depends on timing in ways nobody enumerates in
  advance.
- **The AY's magnitudes.** T4 is the *only* tier in this milestone with any purchase on whether the
  sound is right, and it is a human ear.
- **Whichever `FIRST_CONTENDED_T_STATE` the 128 actually uses**, if no oracle exists for it — via
  the classic observation instrument, a multicolour effect landing one character cell out.

## Decision 9 — the second ROM, and a `.gitignore` glob that commits by default — **ruling**

`.gitignore` ignores all of `testdata/` and then un-ignores the ROM directory:

```
testdata/**
!testdata/roms/
!testdata/roms/*.rom
```

with the comment *"The Sinclair ROMs are the one corpus that may be redistributed — Amstrad has
explicitly permitted shipping them with emulators."*

Two questions follow and they have different answers.

### A finding that stands whatever the permission turns out to say

**This repository redistributes a copyrighted ROM on the strength of a permission whose text
appears nowhere in it.** `.gitignore`, `ARCHITECTURE.md` and `testdata/README.md` each assert that
*"Amstrad has explicitly permitted redistributing the Sinclair ROMs with emulators"* — three
copies of one claim, with **no quotation, no author, no date and no URL** between them. Compare
what the same `testdata/README.md` demands of a ROM's *bytes*: size, SHA-1, CRC-32, two independent
mirrors fetched and compared, and a stated reason (*"a ROM is the one corpus here whose contents
nothing else validates"*). The provenance of the **bytes** is documented to this project's usual
standard; the provenance of the **right to ship them** is a sentence.

That is the same shape as the defects this project catalogues — a claimed protection with nothing
behind it that a reader can check — and it is worse here in one specific way: **a wrong technical
claim produces a bug, and a wrong licensing claim produces a redistribution nobody was entitled to
make.** It is also cheap to fix, which is why it is raised rather than filed: the permission is a
short, widely-quoted statement, and recording it verbatim with its author, date and source next to
the SHA-1 costs one paragraph.

**M7 must not add a second ROM to that footing.** So the permission was looked up, and it is quoted
below with its conditions and its scope.

### The permission, quoted, with the condition this repository does not currently meet

The statement is from **Cliff Lawson of Amstrad plc**, posted to **comp.sys.sinclair on 31 August
1999**, and reproduced ever since — including in Debian/Ubuntu's [`spectrum-roms` copyright
file](https://launchpad.net/ubuntu/noble/+source/spectrum-roms/+copyright), which is a
distribution's own legal record rather than a fan page, and in
[`z00m128/zxs-rom`](https://github.com/z00m128/zxs-rom/blob/master/LICENSE.md):

> *"Amstrad are happy for emulator writers to include images of our copyrighted code as long as the
> (c)opyright messages are not altered and we appreciate it if the program/manual includes a note to
> the effect that 'Amstrad have kindly given their permission for the redistribution of their
> copyrighted material but retain that copyright'."*

Four conditions travel with it: **the copyright messages must not be altered**; **the acknowledgement
note is requested**; distribution is **for emulator use**; and the ROM code is **not to be sold**,
though a shareware fee for the emulator author's own work is explicitly fine. Modification is
permitted — *"If they choose to modify the behaviour in any way then that's entirely up to them"* —
and modified ROMs may be redistributed under the same copyright proviso.

> **Caveat on the sourcing, and it should be discharged before this goes into a licence file.**
> The canonical [World of Spectrum permits page](https://worldofspectrum.net/permits/) returned
> **HTTP 403** and could not be read, so the wording above comes from two reproductions rather than
> from the primary posting. For a *technical* claim two agreeing reproductions would be plenty; for
> a **licensing** claim the primary text is what should be quoted, because the quotation is the
> thing being relied on. Pull it from a source that can be read in full, then quote it in
> `testdata/README.md`.

**Scope covers the 128's ROMs, and it is enumerated rather than inferred.** The statement names the
covered machines: **Spectrum 48/128, +, +2, +2A and +3**. It also names what it does **not** cover —
**the ZX80, the ZX81, and the Interface 1 and Interface 2 ROMs**, which Amstrad does not hold the
rights to, along with third-party clones such as Timex. Corroboration that this is how it is read in
practice: Debian/Ubuntu's `spectrum-roms` ships `48.rom`, **`128-0.rom` and `128-1.rom`**, the
Spanish 128 variants and the `plus2`/`plus3` images under exactly this copyright file, and a
distribution's licensing review accepted it.

**So committing the two 128 ROMs stands on precisely the same footing as the 48K ROM already
does** — and the exclusion list is not a footnote, because of what it does to the next paragraph.

> **The exclusions make the glob argument concrete rather than hypothetical.** An `if1-2.rom`
> dropped into `testdata/roms/` matches `!testdata/roms/*.rom` and would be committed — and
> **Interface 1 and Interface 2 ROMs are named in this permission as ROMs Amstrad cannot grant
> rights to.** That is no longer a story about a file that might someday have a different licence;
> it is a specific, plausible file, of a kind an emulator project acquires in the normal course of
> its work, which the pattern would commit and the permission does not reach.

> **Two corrections to this document, made where a reader will meet them.**
>
> **The +3 claim below was mine and I did not check it.** The scope paragraph in Decision 10's
> neighbourhood asserted that *"the +3's ROMs are commonly reported to have a different status from
> the 48K's and the 128's."* **The evidence found points the other way** — `spectrum-roms` ships
> `plus3` images under the same permission. The claim is withdrawn. It is left visible rather than
> deleted because it is a clean example of the failure this document opens by warning about: a
> confident, plausible, licence-shaped sentence written from familiarity, in the very section
> arguing that licensing claims must be quoted rather than asserted.
>
> **The argument for replacing the glob does not depend on it and is unchanged.** The problem with
> `!testdata/roms/*.rom` was never that some *Sinclair* ROM has a different licence. It is that the
> pattern accepts **any** file ending in `.rom` — a game cartridge, a third-party interface ROM, a
> Multiface image — none of which this permission touches at all. The glob turns "may we
> redistribute this?" from a decision into an accident, and that is true whatever the +3's status
> turns out to be.

**And the acknowledgement note is missing.** The permission asks that *"the program/manual includes
a note"* in specific terms, and this repository has no such note anywhere: `ARCHITECTURE.md`,
`.gitignore` and `testdata/README.md` each state that *permission exists*, which is a different
thing from making the acknowledgement the permission requests. It is a *"we appreciate it if"*
rather than a hard condition, and it costs one sentence in `README.md`. **M7 should add it in the
same change that commits the second and third ROM**, because a repository that is about to double
the number of ROMs it ships is exactly the wrong moment to still be skipping the courtesy the
permission asked for.

### Should the 128 ROMs be committed?

**Yes, if the permission's scope covers them**, and for the reason `M6.md` Decision 8 gives: *"a
gate whose corpus is absent by default is a gate that runs nowhere."* T2 and T3 both need the ROMs,
and a committed
corpus is what makes them run on every clone. This is also the consistency answer: the 48K ROM is
committed under the same permission and there is no principled line between them.

**Should the glob stay?** **No, and this is a real defect that M7 exposes rather than creates.**
`!testdata/roms/*.rom` is *permissive by default*: any file ending in `.rom` dropped in that
directory is committed with no further thought. ~~The licensing status of Spectrum ROMs is **not
uniform** — the +3's ROMs are commonly reported to have a different status from the 48K's and the
128's~~ — **withdrawn, see the correction above; the evidence points the other way** — but a game
cartridge, a third-party interface ROM or a Multiface image is not covered by Amstrad's permission
at all, and each of them ends in `.rom`. A glob turns "may we redistribute this?" from a decision
into an accident.

**Replace the glob with explicit filenames.** Then adding a ROM requires editing `.gitignore`,
which is exactly where the licence check belongs and exactly where a reviewer will see it. The cost
is one line per ROM, forever; the thing it prevents is a redistribution nobody decided to make.

`.gitignore` is not this document's to edit; it is implementation step 1 below, and
`testdata/README.md` gains a 128 section in the shape its 48K one already has — size, SHA-1,
CRC-32, two independent mirrors compared byte for byte, and the absence-policy table.

## Implementation order

Each step is independently reviewable and each has a gate that goes red without the next.

0. **Fetch `timing_tests-128k_v1.0.z80` and count its expected-result tables** (Decision 8). Step
   zero because it is minutes of work and it decides how much of this milestone can ever be
   *measured*: one table confirms the structural argument and caps the artefact at *derived*; two
   would be a genuine surprise worth investigating properly. Either way the file is worth running,

1. **`.gitignore` explicit filenames, the two 128 ROMs, `testdata/README.md`, and the Amstrad

7. **`Bus::acknowledge` and `Ula`'s implementation** (Decision 5). Gate: a direct `Cpu<Ula>` at a

9. **`.z80` 128 support**: the model-dependent hardware-mode table, the paging byte, the AY

  `0xFFFD` and `0xBFFD`.** Decision 2's overlap table infers them from the two addresses, the
  overlap it predicts with the ULA follows from that inference, and the *shape* of the fix (two
  independent `if`s, AY read before the floating-bus fallback) is right whether or not the mask is.
  Named as this design's least-supported claim.
- **The full primary text of the Amstrad permission.** Two reproductions agree and enumerate the
  scope; the canonical World of Spectrum permits page returned 403. For a licensing claim the
  quotation *is* the thing relied upon, so it should be pulled from a readable primary source
  before it goes into `testdata/README.md`.
- **Whether the AY's structural gates are worth their weight** if no 128-only software in reach
  uses the chip heavily. They are cheap, and the argument for them is that a wrong AY is silent —
  in both senses.
- **Whether T4 is reachable at all.** Most commercial 128 titles are turbo-loaded and `.tap` cannot
  carry them, which is `M6.md`'s unresolved question inherited unchanged. If the answer is no,
  `.tzx` moves from *later* to *required*, and Decision 5 of `M6.md` is what makes that cheap.
- **Whether `Spectrum::restore` should reconfigure the machine to the snapshot's model** rather
  than refuse. Refusing is chosen because reconfiguring needs the other model's ROMs, which the
  machine does not hold. A frontend that owns both ROM pairs could reasonably do it at its own
  level, and if one ever does, this ruling should be revisited rather than worked around.
